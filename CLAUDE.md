# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository Purpose

This is the Claude Code Toolbox - a community project providing automated installers and environment configuration tools for Claude Code across Windows, macOS, and Linux. The toolbox enables users to quickly set up specialized environments with custom agents, MCP servers, slash commands, and hooks.

## Key Architecture

### Two-Tier Installation System

1. **Platform-specific bootstrap scripts** (minimal ~60 lines each)
   - Windows: PowerShell scripts in `scripts/windows/`
   - Linux/macOS: Bash scripts in `scripts/linux/` and `scripts/macos/`
   - These install `uv` (Astral's Python package manager) and run Python scripts

2. **Cross-platform Python scripts** (comprehensive installers)
   - `scripts/install_claude.py`: Installs Git Bash (Windows) and Claude Code via native installers with npm fallback
   - `scripts/setup_environment.py`: Configuration-driven environment setup from YAML (sources: repo name, local file path, or remote URL)

**Setup-time installer dispatch:** `install_claude()` in `setup_environment.py` runs the sibling `install_claude.py` (shipped in the wheel and staged by every bootstrap wrapper) with `sys.executable` on every platform, and downloads the platform bootstrap script only when no sibling exists. The sibling is NEVER launched through `uv run`: under `uvx` it lives inside uv's cache, and uv >= 0.11.21 refuses to run a script whose directory is inside the cache (`The project directory ... is inside the cache directory ...`). The installer needs only the standard library, so the interpreter already running the setup always suffices. The `package-smoke` CI job proves the dispatch inside a real `uvx` environment via `tests/fixtures/packaging_smoke_step1.py`.

### Native Claude Code Installation Support

The installer uses a native-first approach with automatic npm fallback. Entry point: `ensure_claude()` → `install_claude_native_cross_platform()` → platform-specific `install_claude_native_{windows,macos,linux}()`. Platform-specific fallback chains: Windows uses Native installer (with HTTP retry) → GCS direct download → npm; macOS/Linux use Native installer → GCS direct download → npm. In `native` mode, npm is excluded from the chain. A specific version otherwise falls back to the official installer at `latest` when the exact-version methods fail; `install_claude_native_cross_platform(..., exact_version_only=True)` (threaded to every per-OS function) uses the direct download alone -- on Windows it also skips winget, whose install is not native -- and returns `False` instead, and `ensure_claude()` uses it for the npm->native migration when the installed version already equals `CLAUDE_CODE_TOOLBOX_VERSION`, so a failed exact download keeps the npm installation at its version (migration-failed warning) rather than moving it to the latest release.

**DISABLE_UPDATES refusal:** the official `install.ps1`/`install.sh` scripts run `<binary> install [target]`, which Claude Code (>= 2.1.118) refuses under `DISABLE_UPDATES` -- read from the process environment AND from the `env` block of every settings source it loads at startup, including the user settings file (`$CLAUDE_CONFIG_DIR/settings.json`, else `~/.claude/settings.json`), project settings in the working directory (`.claude/settings.json`, `.claude/settings.local.json`), managed settings, the global config (`$CLAUDE_CONFIG_DIR/.claude.json`, else `~/.claude.json`), and a `--settings` file -- by printing `Updates are disabled by your administrator` and exiting 0, so the script reports success having installed nothing and a previously installed binary still verifies. `_install_claude_native_{windows,macos,linux}_installer()` therefore check every exit-0 run with `_installer_refused_by_disable_updates()` (`CLAUDE_UPDATES_DISABLED_MESSAGE` in stdout or stderr) and, on a refusal, call `_warn_installer_refused_by_disable_updates()` and return `False` before the success line, PATH update, verification, recovery, and finalization, so the caller continues its chain (every latest/`None` request -- Windows CASE 1 and macOS/Linux latest, which also serve unpinned fresh installs and the npm→native migration -- falls through to GCS direct download; the pinned last-resort `'latest'` fallback falls through to npm in `auto` mode). `_warn_installer_refused_by_disable_updates()` also sets the module flag `_disable_updates_refusal_observed`; once it is set, the failure guidance of `ensure_claude()` (item 1) and `install_claude_npm()` (item 3 on Windows, item 4 elsewhere; both lists name the platform's installer command, `irm ... | iex` on Windows and `curl ... | bash` elsewhere) prints `_info_official_installer_blocked()` in place of the recommendation to run the official installer directly (which the same `DISABLE_UPDATES` refuses): change the pin and re-run the setup when a setup configuration pins `claude-code-version`, otherwise remove `DISABLE_UPDATES` first; without a recorded refusal the plain recommendation prints. The installer never removes `DISABLE_UPDATES` from the installer's environment: a settings-sourced value would survive such a scrub, and the fallback chain already reaches methods `DISABLE_UPDATES` does not gate. The toolbox's own pinned install (GCS direct download) never runs `claude install`, and every `DISABLE_*` write in `setup_environment.py` happens after Step 1, so a pin cannot block its own installation. The real-binary E2E locks the refusal text against the actual CLI for both the process-environment and the settings-`env` source.

**Corrupt-binary detection and quarantine:** `get_claude_version()` delegates to `_probe_claude_version()`, which classifies exec-format launch failures via `_is_exec_format_error()` (Windows `winerror` 193/216, POSIX `errno.ENOEXEC`) as a WARNING ("cannot execute on this machine (corrupt or architecture mismatch)") instead of the generic `[FAIL]`; `FileNotFoundError` is never classified as corruption. `run_command()` is untouched (its contract for other callers is preserved). `ensure_claude()`'s initial probe runs `get_claude_version(quarantine_corrupt=True)`, so a corrupt native binary is moved aside via `_quarantine_corrupt_native_binary()` BEFORE any installation dispatch -- Windows renames to `.exe.old` (swept by `_cleanup_old_claude_files()` on the next run), Unix unlinks -- so it can no longer shadow npm installs through `find_command()`'s native-first priority. Quarantine acts only on the native target `~/.local/bin/claude[.exe]`. Post-install verification executes the installed binary via `_verify_installed_binary_executes()` (probe + quarantine on corruption) on the native-installer and all GCS install paths across Windows, macOS, and Linux; on the Windows native-installer primary path a non-executing binary enters the existing recovery chain.

**GCS download integrity and architecture selection:** `_download_claude_direct_from_gcs()` verifies the downloaded binary against `{gcs_base}/{version}/manifest.json` from the same GCS bucket (`_verify_gcs_download_integrity()`: exact byte size + streamed sha256 via `_sha256_file()`). Fail-closed: a manifest fetch failure or any size/checksum mismatch rejects the download and deletes the temp file. `_get_gcs_platform_path()` returns `tuple | None`: Windows ARM64 (`arm64`/`aarch64`) → `win32-arm64`, Alpine/musl Linux (detected via `/etc/alpine-release`) → `linux-{arch}-musl`, and any unrecognized architecture produces an explicit error and `None` (the caller aborts the GCS download instead of fetching a wrong-architecture binary).

**installMethod values:** `update_install_method_config()` writes `installMethod` to `~/.claude.json` with values `'native'` (native installer or GCS direct download), `'global'` (npm `-g` fallback installs), or `'winget'`. Claude Code itself recognizes `'native'`/`'global'`/`'local'` and reports a missing value as `'unknown'`.

### Standalone Script Policy

`install_claude.py` and `setup_environment.py` MUST be fully standalone -- NEVER import from each other. Users may run either script without the other being present.

`scripts/cli.py` is the packaging dispatcher and the ONLY module permitted to import both standalone scripts; neither standalone script may import it (CI enforced via `TestNoCliImports`, which checks import statements, not substrings -- `setup_environment.py` legitimately builds a `<package>.cli` module path as a runtime string for its UAC relaunch). `cli.py` uses relative imports so the same file serves as `scripts.cli` in-repo and `cc_toolbox.cli` inside the wheel; it is NOT a standalone script.

**Identical Code** (CI enforced via `tests/test_standalone_policy.py`): `Colors` class, `find_command()`, `_prefer_windows_executable()`, `get_real_user_home()`, `_dev_tty_sudo_available()`, `_run_with_sudo_fallback()`, `needs_sudo_for_npm()` (EXACT body match), shell config file list (7 files + conditional filtering), Fish config detection (`'fish' in str()`), marker block constants (`# >>> claude-code-toolbox >>>`).

**Intentionally Different** (MUST NOT synchronize): `info()`/`success()`/`warning()`/`error()` (different formatting), `run_command()` (different encoding/error handling), `find_bash_windows()` (setup_environment.py has debug_log), `is_admin()` (different implementations).

**Native Path Priority:** `find_command()` and `verify_claude_installation()` check the native path (`~/.local/bin/claude[.exe]`) first, before `shutil.which()` PATH search. This ensures native binary is preferred even when PATH would resolve to npm first. Validates file exists with `st_size > 1000` to skip empty/corrupt files.

**Windows Executable Resolution:** On Windows, `shutil.which()` can resolve a command (e.g. `npm`/`npx`) to the extensionless Unix shell shim Node.js ships beside its `.cmd` wrapper; `subprocess.run(shell=False)` launches resolved paths via `CreateProcess`, which cannot execute that shim and raises `WinError 193` (`%1 is not a valid Win32 application`). This bites on Python builds before the gh-109590 fix (Windows `shutil.which` on CPython 3.12.0 and every 3.11-or-earlier release), which probe the bare name ahead of the PATHEXT variants. The shared `_prefer_windows_executable(cmd, resolved)` helper (identical in both scripts) swaps a non-executable resolution for the `.exe`/`.cmd`/`.bat`/`.com` wrapper and is applied in `find_command()`'s primary search and in `setup_environment.py`'s `run_command()` Windows resolution. `setup_environment.py`'s `run_command()` also catches `OSError` (alongside `FileNotFoundError`) so a single non-launchable command is recorded as a failure instead of aborting the whole run.

**Environment Variables:** `CLAUDE_CODE_TOOLBOX_INSTALL_METHOD` (`auto`/`native`/`npm`, default `auto` -- unknown sources → native-first with npm fallback), `CLAUDE_CODE_TOOLBOX_VERSION` (installs a specific Claude Code version; all methods support version pinning -- native via GCS download and npm; winget is used only for specific version requests and the upgrade_source=='winget' branch), `CLAUDE_CODE_TOOLBOX_ALLOW_ROOT` (`1` only -- see Root Detection Guard).

**Native Path Detection:** `verify_claude_installation()` classifies the binary location for upgrade strategy:

| Path Pattern                                      | Source               | Upgrade Method                        |
|---------------------------------------------------|----------------------|---------------------------------------|
| Contains `npm` or `.npm-global`                   | `npm`                | npm directly                          |
| Contains `.local/bin` or `.claude/bin`            | `native`             | Native installer                      |
| Windows: `Programs\claude` (legacy winget/native) | `winget` or `native` | Via `_classify_localappdata_claude()` |
| Windows: `WinGet\Links` or `WinGet\Packages`      | `winget`             | winget upgrade, then npm fallback     |
| Other / `/usr/local/bin`                          | `unknown`            | Native-first, npm fallback            |
| Not found                                         | `none`               | Fresh install                         |

In `auto` mode, `native` and `unknown` sources attempt native first with npm fallback. Confirmed `npm` sources go directly to npm. Confirmed `winget` sources try `winget upgrade` first, falling back to npm on failure.

### PyPI Distribution

The repository publishes to PyPI as `cc-toolbox` via an in-place hatchling remap: `[tool.hatch.build.targets.wheel]` `only-include`s exactly four files (`scripts/{__init__,cli,setup_environment,install_claude}.py`) and `[tool.hatch.build.targets.wheel.sources]` rewrites `scripts` → `cc_toolbox`, so the wheel ships `cc_toolbox/` while not one byte moves on disk and the curl|bash bootstrap path stays untouched. `scripts/models` is excluded from the wheel, keeping the runtime dependency closure to `pyyaml` plus `questionary` (`pydantic` lives in the dev group). The single console script `cc-toolbox = "cc_toolbox.cli:main"` dispatches `setup`/`install` subcommands (`uvx cc-toolbox setup <config>`). The PEP 723 headers are inert comment blocks when the files are imported as modules, so identical bytes serve both `uv run --no-project` and the wheel.

**Editable-install limitation:** hatchling refuses dev-mode installs when `sources` changes a path prefix, so `[tool.uv] package = false` keeps `uv sync` from installing the project; the dev venv imports via pytest's `pythonpath = ["."]` (`scripts.cli`), and the packaged import path is exercised by `uv build` plus the `package-smoke` CI job (`uvx --from dist/*.whl` on all three OSes, deliberately NOT skipped on release-please branches).

**UAC relaunch under entry points:** `_elevation_launch_args(__name__, sys.argv[0])` in `setup_environment.py` relaunches elevation via `-m <package>.cli setup` when the module runs from an installed package with a non-`.py` `argv[0]` (a console-script shim `python.exe` cannot re-run); every direct-script invocation keeps relaunching through `sys.argv[0]`.

**Publishing:** `.github/workflows/publish.yml` (same pattern as mcp-context-server) triggers on `release: published`; a `build` job (checkout defaults to the release tag, `uv build`, version assert, artifact upload) is permission-isolated from a `publish-to-pypi` job (`id-token: write`, `environment: pypi`, `pypa/gh-action-pypi-publish` with trusted publishing). The PyPI trusted publisher is registered against workflow `publish.yml`, environment `pypi`.

### Node.js Compatibility

`ensure_nodejs(check_claude_compat=True)` checks Node.js v25+ SlowBuffer incompatibility for npm Claude Code; `False` checks only minimum >= 18.0.0. `install_claude.py` uses `True`; `setup_environment.py` uses `False` (needs Node.js for MCP servers/npx, not Claude Code).

`CLAUDE_NPM_SLOWBUFFER_FIXED_VERSION`: when `None` (default), v25+ always rejected; when set to a version string, v25+ accepted if installed Claude Code npm version meets threshold. Monitor [#9628](https://github.com/anthropics/claude-code/issues/9628).

### Root Detection Guard

All Linux/macOS scripts refuse to run as root/sudo by default (`id -u == 0` in shell, `os.geteuid() == 0` in Python). Applies to all 6 entry points. Override: `CLAUDE_CODE_TOOLBOX_ALLOW_ROOT=1` (only exact value `1`; `true`/`yes` do NOT work). Rationale: root creates config under `/root/` instead of user's home. Use override for Docker/CI environments.

### Single Interface Invariant (Scripts, CLI, Wrappers)

The standalone Python scripts, the `cc-toolbox` CLI, and the platform bootstrap wrappers expose ONE interface: identical flags, identical environment variables, identical behavior. The wrappers forward ALL user arguments to `setup_environment.py` verbatim -- no allowlists, no wrapper-built flags, and `CLAUDE_CODE_TOOLBOX_ENV_CONFIG` never placed on the command line, because `resolve_args()` reads the variable through `ENV_TWINS` and records `origins['config']` as `env`, which the switch guard's remedy and the `--profile all` conflict message depend on. The wrappers only check that a configuration is present (a non-flag first argument, else the variable, the precedence argparse applies) and run without one when `--profile` (or `--profile=NAME`) is among the arguments or `CLAUDE_CODE_TOOLBOX_PROFILE` is set, because a `--profile` re-run reads its configuration from the manifest. Anything expressible in one entry path MUST be expressible identically in every other, and any interface change lands in all entry paths (Python scripts, `cli.py`, all three wrappers, docs) in the same PR.

**Present-tense only, no backward compatibility:** code, comments, docstrings, and docs describe ONLY the current interface -- never prior behavior, removed elements, migrations, or compatibility notes. Superseded interface elements are deleted outright, never kept as shims, aliases, or deprecated fallbacks. The conventional commit message is the only record of change.

### Installation Confirmation

The setup script requires explicit user confirmation before installing. CLI flags: `--yes`/`-y` (auto-confirm), `--dry-run` (preview and exit), `--skip-install` (skip Claude Code installation), `--no-admin` (skip Windows admin elevation), `--command-names NAME[,ALIAS...]` (install as the isolated profile `~/.claude/NAME` under these command names, `NAME,none` under the one command; see Command names below), `--profile NAME` (re-run the installed profile NAME from its manifest with no configuration argument; `base` for the base profile, `all` for every installed profile, each as a child run with `--yes`, the hidden `--refresh-all-child` and, outside `--dry-run`, `--no-admin`, after the parent decided Windows elevation once for all of them), `--switch-config` (accept a different configuration for an existing profile and remove what the previous one left behind), `--link-dirs ENTRIES` and `--link-from SOURCE` (take entries of the isolated profile through a directory link from another profile; see Profile links below), `--env KEY=VALUE` (repeatable; sets an environment variable for the run before any env read, identically in every shell, and is forwarded through UAC elevation). Env vars: `CLAUDE_CODE_TOOLBOX_CONFIRM_INSTALL=1` (auto-confirm), `CLAUDE_CODE_TOOLBOX_DRY_RUN=1` (preview), `CLAUDE_CODE_TOOLBOX_SKIP_INSTALL=1` (skip installation), `CLAUDE_CODE_TOOLBOX_NO_ADMIN=1` (skip elevation), `CLAUDE_CODE_TOOLBOX_SWITCH_CONFIG=1` (accept a configuration switch); the switches accept only exact value `'1'`, `CLAUDE_CODE_TOOLBOX_PROFILE` carries the `--profile` value, and `CLAUDE_CODE_TOOLBOX_LINK_DIRS`/`CLAUDE_CODE_TOOLBOX_LINK_FROM` carry the link values. Auth is environment-driven with no dedicated flag: `GITHUB_TOKEN`/`GITLAB_TOKEN` (per-host), `REPO_TOKEN` (generic), `CLAUDE_CODE_TOOLBOX_ENV_AUTH` (string, `header:value` format) -- all settable via `--env`.

**Profile re-runs (`--profile`, `resolve_command_names()`, the guards):** `resolve_profile_rerun()` locates `~/.claude/NAME/manifest.json` (`~/.claude/manifest.json` for `base`) and `rerun_config_source()` supplies the recorded `config_source` when no configuration is given; `refresh_all_profiles()` handles `all` before anything else loads (a conflicting configuration is named `CLAUDE_CODE_TOOLBOX_ENV_CONFIG` when `origins['config']` is `env`) and decides elevation ONCE, in the parent, before consent and before any child: `refresh_all_elevation_reasons()` returns nothing off Windows, in an elevated process, under `--no-admin` or under `--dry-run`, otherwise `admin_elevation_reasons({}, args)` without `--skip-install` (the binary install) or, with it, the union over each profile's `resolved-config.yaml` (`read_resolved_config_snapshot()`; a missing or unreadable snapshot counts as needing elevation); with reasons the parent prints them and calls `request_admin_elevation()`, which forwards `sys.argv` and every twin (`PROFILE=all` included) and exits, and a denied request returns 1. It then runs each profile of `order_profiles_source_first(installed_profiles())` (base first, then sorted, every content-link source before its dependents) as a child `[sys.executable, *_elevation_launch_args(__name__, sys.argv[0]), '--profile', NAME, '--yes', REFRESH_ALL_CHILD_FLAG, <the parent's --dry-run/--skip-install>, '--no-admin']` -- `--no-admin` on every child outside `--dry-run`, so no child can relaunch through UAC and exit 0 unobserved; a dry run forwards only the parent's `--no-admin`, so each child keeps printing its would-elevate block -- with `child_run_environment()` (every `ENV_TWINS` variable except `CHILD_RUN_INHERITED_TWINS` and `CLAUDE_CONFIG_DIR` removed), asking consent once when interactive and ending with a per-profile report and exit 1 on any failure. `main()` passes `was_elevated_via_uac` as `elevated_via_uac=`, and a parent that is itself the window a UAC relaunch opened then calls `_hold_elevated_window()` after the report: the one helper behind every `Press Enter to exit...` pause, which prints the success or errors banner single runs use and returns at once under pytest (`is_running_in_pytest()`), so the report outlives a console that closes on exit. `--refresh-all-child` (`REFRESH_ALL_CHILD_FLAG`, `help=argparse.SUPPRESS` like `--elevated-via-uac`) makes a child skip the `unrefreshed_profile_lines()` block and the Step 23 dependent refresh, which the parent covers; `--link-dirs`/`--link-from` beside `--profile all` are conflicts like a configuration. `main()` reads the target profile's manifest (`_read_target_manifest()` via `profile_target_name()`) before the selector validation so `apply_remembered_component_delta()` can fill absent selectors from a remembered delta (which then counts as supplied: no picker), checked against the configuration's current components before `_validate_component_selector_args()` sees it -- a remembered `--without` naming a component the configuration no longer declares is dropped with a warning and the cleaned delta is what the manifest records next; a remembered `--select` or `--with` naming one refuses with an error naming the manifest and the remedy (pass the flag explicitly, or `--select all`) -- then `resolve_command_names(args, config, manifest)` ranks per key: typed, environment, remembered (only a manifest `origins` value of `cli`/`env` is remembered), configuration, default. Typed-list rules: `NAME,ALIAS...` sets the aliases, `NAME,none` drops them (`DROP_ALIASES_TOKEN`, valid only second and last), a single `NAME` on an installed profile selects it and takes the aliases from the next source, on a new profile it is the whole list recorded as typed. `--profile NAME` with a typed primary other than NAME, and `--profile base` with any typed name or a configuration declaring `command-names`, are errors naming what to clear. `CommandNames.remembered` and `ComponentSelection.remembered` drive the `[remembered]` marker (`origin_marker()`), and `remembered_value_warnings()` warns when a remembered value overrides a configuration value that changed since the install (`yaml_values` in the manifest). Two guards run before the ambient-`CLAUDE_CONFIG_DIR` check and the summary, both through `guard_decision()` (accepted by a flag; interactive y/N where no exits 0; `--yes`, `--dry-run` or no terminal exits 1 with the remedy): `guard_environment_name_change()` when a `CLAUDE_CODE_TOOLBOX_COMMAND_NAMES` value differs from the manifest's names (a typed value proceeds), and `guard_configuration_switch()` when `config_identity_of(config_source)` differs from `manifest_config_identity()` (which derives an identity for manifests without one: `config_source_url`, else the resolved source; an unresolvable relative local source records the given configuration's identity with an info line), listing `profile_residue()` -- recorded `files_written` the new configuration does not plan (`planned_profile_files()`), recorded `mcp_servers` it does not declare, a base profile's `os_env_written` and `settings_keys_written` it does not set (never a `MACHINE_WIDE_ENV_CONTROLS` key, bare or as an `env.<VAR>` entry: those belong to the pin gate and the Step 16 sweep, and a switch away from a pin while another profile still pins must leave them in place), and `machine_wide_destinations` whose file still holds the recorded sha256 and which no other installed profile's manifest records (`_destinations_recorded_elsewhere()`; a destination another profile records is listed as `kept_destinations`, rendered `file outside ~/.claude kept: <path> (recorded by profile <names>)`, and never removed) -- which `--switch-config` accepts and `remove_profile_residue()` removes after consent, deleting `env.<VAR>` entries one by one through a single null-as-delete `_write_merged_json()` write (an emptied `env` object is dropped) so the other variables stay. The guard's remedy undoes the source the configuration came from: clear `CLAUDE_CODE_TOOLBOX_ENV_CONFIG` (`unset`, or `Remove-Item Env:` in PowerShell) for the `env` origin, drop the configuration argument for `cli`, then `--profile NAME`. Step 21 calls `remove_dropped_command_wrappers()` with the previous manifest's names before `register_global_command()`, so a dropped alias loses its `~/.local/bin` wrappers (toolbox wrappers only). The summary adds `pin_effect_line()` (a pin that holds or moves the binary names the other installed profiles; the installed version is probed only then), `shared_destination_warnings()` under ATTENTION, and the closing `unrefreshed_profile_lines()`; `handle_resource()` leaves a destination untouched when the fetched content is identical. `tests/conftest.py` stubs `_read_target_manifest` and `installed_profiles` for unit tests the way it stubs `command_name_conflicts`, because both read the real `~/.claude`; E2E tests run the real readers in their isolated home (`tests/e2e/test_profile_rerun.py` with `tests/e2e/profile_support.py`, whose `run_main()` restores the environment after every run because `export_setup_time_config_dir()` leaks `CLAUDE_CONFIG_DIR` into the process).

**Environment Variable Resolution:** All CLI flags and their env var equivalents are merged in `resolve_args()`, called immediately after `parse_args()`. `--env` overrides are applied to `os.environ` first (explicit beats ambient, matching `VAR=x command` shell semantics), then CLI flags take precedence over env vars. The `ENV_TWINS` registry of `EnvTwin(variable, dest, kind)` entries is the single source for those fallbacks and for the variables `request_admin_elevation()` forwards as `--env-VAR=value` arguments (the elevated process does not inherit the environment); `UAC_FORWARDED_ENV_VARS` adds the credentials and `CLAUDE_CODE_TOOLBOX_VERSION`. A `switch` twin turns its flag on only with the exact value `1`; a `value` twin fills its argument only when the argument is absent, treats an empty export as absent, and records `'cli'` or `'env'` in `args.origins`. `CLAUDE_CODE_TOOLBOX_ENV_CONFIG` is the twin of the positional config (`dest='config'`). `tests/test_env_twin_registry.py` records every variable `resolve_args()` reads and asserts each is registered and forwarded through UAC, so a new twin MUST be added to `ENV_TWINS`, never read ad hoc. The going-forward naming convention is: `--flag-name` becomes `CLAUDE_CODE_TOOLBOX_FLAG_NAME` (direct mechanical mapping). `CONFIRM_INSTALL` is a preserved historical exception.

**Command names:** `resolve_command_names(args, config)` decides a run's names right after the `--list-components` exit and returns a `CommandNames(names, origin)`: `--command-names` (`'cli'`) beats `CLAUDE_CODE_TOOLBOX_COMMAND_NAMES` (`'env'`, origin from `args.origins`) beats the YAML `command-names` (`'yaml'`). A typed or environment value replaces the YAML list whole and never merges (a single NAME is the complete list, no aliases), and `main()` writes the effective list back into `config['command-names']`, so every later reader (the plan, the launchers, the manifest, the isolated/base routing) sees it; a configuration without `command-names` therefore installs as the isolated profile `~/.claude/NAME`, which receives every section the toolbox places itself (agents, commands, rules, skills, the system prompt, hook files and `hooks.helpers`, launchers, `config.json`, manifest), while `files-to-download` destinations and dependency commands run as written, so a literal `~/.claude/...` destination still lands in the base `~/.claude`. `command_name_errors()` validates every source identically (empty, spaces, `validate_command_name_for_path()`, and `RESERVED_COMMAND_NAMES` compared with `casefold()`: `none`, `base`, `all`, and the profile directory entries `skills`, `agents`, `commands`, `rules`, `hooks`, `output-styles`, `prompts`, `projects`), naming the flag, the variable, or the key in each message. Valid names then go through `command_name_conflicts(names, home)`, which refuses a name another isolated profile holds (`_command_names_of_other_profiles()` reads every `~/.claude/*/manifest.json`, skips the one whose `name` casefolds to this run's primary, and keeps the directory name of an unreadable manifest as taken) and a name `~/.local/bin` holds as an entry the toolbox did not create (`is_toolbox_wrapper()`: a Unix symlink to a `launch.sh`, or a Windows `.cmd`/`.ps1`/extensionless file whose first lines carry the `register_global_command()` comment naming that command; Windows also checks `name.exe`/`.bat`/`.com`), each message naming the owner and the remedy. A toolbox wrapper no other manifest lists, such as one a dropped alias left behind, is free to reuse. Any error exits 1 before the ambient `CLAUDE_CONFIG_DIR` guard, the summary, and any write, also under `--dry-run`; `tests/conftest.py`'s autouse `_mock_command_name_conflicts` turns the check off for unit tests (it reads the real home), and E2E tests run it inside their isolated home. The installation summary (`InstallationPlan.command_names_origin`) and the completion summary's `Global command(s): ... registered` and Quick Start lines (`effective_command_names.origin`) both mark the names `[cli]`/`[env]`/`[yaml]` through `command_names_origin_marker()`, so a leftover `CLAUDE_CODE_TOOLBOX_COMMAND_NAMES` under `--yes`, where nobody reads the installation summary, still shows after the run; the Components `Replay:` line appends `--command-names` for `cli`/`env` names. `tests/conftest.py`'s autouse `_isolate_argument_twins` clears every `ENV_TWINS` variable before each test, because `--env` writes into the process environment for the rest of the session.

**Default:** Interactive → `[y/N]` prompt (deny default). Piped with `/dev/tty` → prompts via tty. Non-interactive → refuses (exit 1). Exit `0` for success/dry-run/cancellation, `1` for errors (including download and dependency-installation failures).

**Windows elevation:** `request_admin_elevation_if_needed()` runs in `main()` after component selection and before remote file validation. `admin_elevation_reasons()` lists what needs administrator rights (installing Claude Code unless `--skip-install`, every `winget ... --scope machine` and global npm dependency of the Windows and common lists, in installation order); an empty list, an elevated process, or `--no-admin` (`CLAUDE_CODE_TOOLBOX_NO_ADMIN=1`) skips elevation. A real run prints the "Administrator Privileges Required" banner with those reasons and relaunches through UAC (`request_admin_elevation()`); a denied relaunch exits 1. A dry run (`--dry-run` or `CLAUDE_CODE_TOOLBOX_DRY_RUN=1`) NEVER requests elevation: it prints `Dry run: administrator elevation is not requested.` with the same reasons and continues to the summary and exit 0. This gate is the ONLY elevation point: no installation step requests elevation on its own, so `--no-admin` means no UAC prompt anywhere in the run -- Step 1 runs the installer and Step 6 runs `winget ... --scope machine` and global npm dependencies in the non-elevated process, and a failure goes through the usual installation-failure and dependency-failure reporting. In the window a UAC relaunch opened (`--elevated-via-uac`), `main()` holds every failed or completed outcome on screen through `_hold_elevated_window()`: the success and errors banners of a finished run, and, through its `except SystemExit` handler, a `Setup Failed` banner for any non-zero exit no step held itself (a validation error, a refused guard); an exit 0, such as a declined confirmation, closes the window at once.

**Interactive-read hardening:** `_read_user_input()` sanitizes every line via `_sanitize_interactive_input()` (CSI/OSC/SS3/charset escape sequences and control characters stripped, any remaining bare ESC stripped ALONE so Alt+y reduces to `y` — a queued cursor-position report left by the full-screen picker glued `ESC[24;80R` onto a typed `y`, cancelling the install; verified with a real pty). `_finalize_interactive_line()` returns `_CONTAMINATED_INPUT_MARKER` (`<terminal-noise>`) for a line whose content was ENTIRELY garbage, so it can never masquerade as a deliberate Enter. `_get_user_confirmation()` first discards queued unread terminal input via `_flush_pending_terminal_input()` (POSIX `termios.tcflush`, Windows `msvcrt` drain). The shared `_ask_yes_no()` loop backs EVERY consent gate — `confirm_installation()` and `prompt_for_credentials()` — re-prompting up to three times on an unrecognized answer (the marker included) instead of silently cancelling; Enter/`n`/`no` still deny immediately. Real-path coverage: `tests/e2e/test_confirmation_tty.py` drives `_get_user_confirmation`, `confirm_installation`, and the numbered picker through an actual pty with piped stdin (POSIX-only), with discriminating assertions on the re-prompt warnings.

**Known Config Keys:** The setup script validates config keys against `KNOWN_CONFIG_KEYS` constant. Unknown keys are flagged with `[?]` in the installation summary. When adding new config keys to `setup_environment.py`, remember to update `KNOWN_CONFIG_KEYS`.

**Sensitive Path Detection:** Files-to-download destinations are checked against `SENSITIVE_PATH_PREFIXES`. Sensitive paths (e.g., `~/.ssh/`, `~/.bashrc`) are flagged with `[!]` in the installation summary.

### Environment Configuration System

YAML configs define complete environments: dependencies, agents, MCP servers, slash commands, system prompts (append/replace modes), hooks, OS environment variables, user settings (`settings.json` content via `user-settings`), global config (`~/.claude.json` via `global-config`), and selective inheritance via `merge-keys` directive.

**List Inherit (`inherit: [list]`):** `inherit` accepts `str | list[str | InheritEntry] | None`. Single-element plain-string lists normalize to string (recursive resolution -- the entry's own `inherit` IS resolved). Single-element structured lists (`[{config: ..., merge-keys: [...]}]`) route to `_resolve_list_inherit()` (composition mode). Multi-element lists use flat left-to-right composition via `_resolve_list_inherit()`. Four mandatory rules:

1. **Own inherit stripped (Rule 1):** Each listed file's own `inherit` key is completely ignored in list composition mode. Users must explicitly include all configs in the desired order.
2. **Separate-file equivalence (Rule 2):** `inherit: [A, B, C]` behaves identically to a virtual chain where C inherits B which inherits A. First entry = base (lowest priority), last entry overrides earlier ones, leaf overrides everything.
3. **Own merge-keys stripped, per-entry from leaf (Rule 3):** Each listed file's own `merge-keys` key is stripped and ignored. Per-entry merge-keys are specified in the leaf config using structured `{config: ..., merge-keys: [...]}` entries. merge-keys are a property of the relationship between the leaf and each listed entry, not an intrinsic property of the listed config.
4. **Leaf merge-keys for final step (Rule 4):** The leaf config's top-level `merge-keys` applies to the final composition step (leaf on top of accumulated base). Orthogonal to per-entry merge-keys.

`_validate_merge_keys()` is a DRY helper extracted from the former inline validation, reused for both leaf and per-entry merge-keys validation. `InheritEntry` is a Pydantic model (`config: str`, `merge_keys: list[str] | None` with alias `merge-keys`, `extra='forbid'`) containing an inline `mergeable` frozenset (DRY violation covered by parity test `test_mergeable_config_keys_parity.py`). `_resolve_list_inherit()` threads `auth_param` through `load_config_from_source()` for each entry, extends the existing `visited` set for circular dependency detection, and builds `InheritanceChainEntry` entries for each loaded config.

**Env Loader Files:** `generate_env_loader_files()` creates Rustup-style shell scripts containing the `os-env-variables` of an isolated run (distinct from the session-scoped `user-settings.env` written into `config.json`). Per-command files in the profile directory (`~/.claude/{cmd}/` by default): `env.sh`, `env.fish` (if Fish installed), `env.ps1` (Windows), `env.cmd` (Windows). Files are generated only when `command_names` is provided; without `command_names`, the function returns `{}`. A `None`-valued (deletion) entry is rendered as an unset line in each shell's syntax (`unset NAME`, `set -q NAME; and set -e NAME`, `Remove-Item -Path Env:NAME -ErrorAction SilentlyContinue`, `SET "NAME="`), so a value the profile's sessions inherit from the OS environment is removed at session start. Loader files are toolbox-owned and rebuilt on every run, header-only when the dict is empty, so stale lines from a prior run stop being applied by the launcher. `main()` Step 7 first splits the resolved `os-env-variables` with `partition_os_env_variables(os_env_variables, isolated=...)`: a base run hands every entry to `set_all_os_env_variables()` (shell profiles, Windows registry) and generates no loader; an isolated run hands ONLY the `MACHINE_WIDE_ENV_CONTROLS` entries (`DISABLE_AUTOUPDATER`, `DISABLE_UPDATES`, `CLAUDE_CODE_IDE_SKIP_AUTO_INSTALL` -- the controls holding the one Claude Code binary, built from `AUTO_UPDATE_ENV_CONTROLS` plus `IDE_SKIP_AUTO_INSTALL_KEY` and read by every place that handles the three together) to the OS writer and every other entry, nulls included, to `generate_env_loader_files()`. A machine-wide control never enters a loader file: an unset line there would strip the control from the profile's sessions after another profile pinned a version. `create_launcher_script()` injects guarded source lines in all 6 launcher variants so commands auto-load env vars.

**Fish Dual-Mechanism:** `set_os_env_variable_unix()` writes `set -gx` to `config.fish` (durable persistence) AND calls `set -Ux` via subprocess (instant propagation to all running Fish sessions). For deletions, `set -Ue` removes the universal variable. The `config.fish` write is authoritative; `set -Ux` is complementary.

**WM_SETTINGCHANGE Broadcast:** `_broadcast_wm_settingchange()` in `setup_environment.py` uses the dummy `setx CLAUDE_CODE_TOOLBOX_TEMP temp` + `reg delete` pattern to trigger `WM_SETTINGCHANGE`. Called from `add_directory_to_windows_path()`, `cleanup_temp_paths_from_registry()`, `set_os_env_variable_windows()` (after `reg delete` for deletions), and `set_all_os_env_variables()` (batch broadcast after all operations). `install_claude.py` has its own independent copy at `ensure_local_bin_in_path_windows()` (standalone script policy).

### Component Selection (`components`)

The top-level `components:` key defines author-controlled selectable groups of items from `SELECTABLE_SECTIONS = {agents, slash-commands, rules, skills, files-to-download, mcp-servers, dependencies, hooks}` (byte-identical frozensets in `setup_environment.py` and `environment_config.py`; parity enforced by `tests/scripts/models/test_selectable_sections_parity.py`, which also locks the model's `_download_selector_identity` to the runtime's `_files_download_identity`). An item claimed by at least one component installs only when a selected component claims it; unclaimed items are mandatory and never appear in any picker. `components` is a `KNOWN_CONFIG_KEYS` member and the 12th `MERGEABLE_CONFIG_KEYS` entry (merged by `name` via `_merge_named_list`/`_name_identity`).

**Selector identities** mirror each section's merge identity: exact string (agents/slash-commands/rules/dependencies across all platform lists), entry `name` (skills/mcp-servers), dual key `dest` OR normalized final path (files-to-download; distinct entries sharing a final path are a fail-fast error because they make selectors ambiguous), and `hooks.events[].id` or a `hooks.files` path (hooks). `hooks.events[].id` exists solely as a selector identity; `_build_hooks_json()` is a whitelist builder, so the id never reaches generated JSON (regression: `TestHookIdNotInGeneratedJson`). Both validation layers strip whitespace on both sides of the comparison. A config declaring `inherit` is model-validated WITHOUT the cross-reference checks (selector resolution, `requires`/`bundles` references, duplicate final-path) because its full item set exists only post-resolution; the runtime twin enforces them on the resolved config. Within-file invariants (duplicate names, duplicate hook ids) stay enforced on every file.

**Resolution** happens ONCE at the single choke point in `main()`: after inheritance resolution, BEFORE `request_admin_elevation_if_needed()` and remote file validation, so deselected items never trigger UAC elevation, network fetches, or auth prompts. Sequence: `validate_components()` (runtime twin of the Pydantic validation; emits the hook-claim asymmetry warning) and `validate_hooks_files_consistency()` (runtime twin of the model validator of the same name; both error lists print together before a single exit 1) → `_validate_component_selector_args()` → `--list-components` exit → `resolve_component_selection()` → `apply_component_selection()` (in-place filter; section keys never deleted) → post-selection `validate_hooks_files_consistency(config, require_all_files_used=False)` recheck (a deselection-stranded event/status-line reference exits 1 with guidance; unused files are tolerated residue covered by the asymmetry warning). The algorithm: author defaults (`default: true` when omitted) → `--select` (sentinels `all`/`none`) → `--with` → soft `_bundle_closure` → `--without` → interactive picker → hard `_requires_closure` (BFS over registry-ordered seeds so `[auto: required by '...']` cause attribution is deterministic; wins over `--without` with a warning). CLI flags `--select`/`--with`/`--without`/`--list-components` have `CLAUDE_CODE_TOOLBOX_SELECT`/`_WITH`/`_WITHOUT` env fallbacks in `resolve_args()`. A profile's manifest remembers the delta a run typed or took from the environment (`ComponentSelection.delta`/`origin`/`remembered`/`defaults`; a picker choice that changed the seed is recorded as typed), and `apply_remembered_component_delta()` feeds it to a later run that gives no selector, so a `--yes` re-run keeps the components instead of deselecting them; the summary's `Components:` header carries the origin marker. The resolved `ComponentSelection` threads into `collect_installation_plan(selection=...)` and renders a summary Components block with `[x]`/`[ ]` rows and a copy-pasteable replay line (`--select` plus `--without` for skipped components, so bundle edges do not re-add deselected targets on replay). `collect_deselected_items()` captures the removal plan from the UNFILTERED config at the same choke point (an item is deselected when claimed by at least one component and kept by none of the selected ones; dependencies excluded as irreversible); the plan threads into the summary as `[REMOVE]` rows (`deselected=`/`deselected_items`) and executes as Step 22 of both branches (`execute_deselection_cleanup()`, followed by the Step 23 dependent refresh): `claude mcp remove` per non-profile scope, deletion of deselected skill dirs and agent/command/rule/hook/downloaded files (installer-mirroring path resolution, absent targets skipped silently, nothing inside a linked entry), and `_strip_hooks_from_settings()` reconciliation of the shared `settings.json` hook union via `_hook_entries_equal()` (quote-insensitive on file-reference commands so pre-quoting installs still match, exact on everything else; non-isolated only; the isolated `config.json` is rebuilt atomically each run).

**Picker** (`prompt_component_selection()`): Tier 1 questionary checkbox (lazy import), Tier 2 numbered toggle loop via `_read_user_input()` on ImportError OR any console exception (mintty's `NoConsoleScreenBufferError` is not an `OSError` — the catch is deliberately broad), Tier 3 returns `None` keeping the non-interactive set. Queued terminal input is flushed via `_flush_pending_terminal_input()` twice: once before the tiers, and again at the numbered picker's entry, because the questionary tier can fail mid-render with its own terminal query replies still queued and an empty first line would silently confirm the untouched seed; in-loop iterations stay flush-free so type-ahead between toggle prompts survives, and an all-garbage line surfaces as the contaminated-input marker (invalid input, re-prompt) rather than an Enter. Ctrl-C cancels with exit 0 in BOTH interactive tiers: `_read_user_input()` propagates `KeyboardInterrupt` while its `_get_user_confirmation()` wrapper converts it to `''` (deny) for confirmation prompts. Runs only when no selector flag is given, neither `--yes` nor `--dry-run` is set, and a TTY (or `/dev/tty`) is available; prints its own two-line context banner because `header()` renders later. `questionary` is declared in THREE places: the PEP 723 block of `setup_environment.py` (standalone `uv run` path), `[project].dependencies` (wheel/`uvx` path), and `[dependency-groups].dev` (`uv run pytest` provisions from pyproject, not the PEP 723 header).

### Global Config (`global-config`)

Writes exactly one file, resolved by `global_config_target_file(artifact_base_dir)`: `~/.claude.json` for a base run, `~/.claude/{cmd}/.claude.json` for an isolated run (Claude Code CLI resolves `getGlobalClaudeFile()` via `CLAUDE_CONFIG_DIR` with no fallback, and the base file belongs to the base profile). The `global-config` write of an isolated run never touches the base file (the base file receives only the `installMethod` record of the Step 1 installer), so a configuration whose `global-config` deletes `oauthAccount` or `userID` signs out only the profile it installs. Arrays merge differently per layer. The writer (`write_global_config()` -> `_write_merged_json()`, the helper `write_user_settings()` shares) deep-merges into the target file and unions every array at every depth with the array that file already holds (existing elements first, new ones appended, structural dedupe), because the CLI keeps its own arrays there: a YAML array only adds elements, and `key: null` deletes the whole key. The `inherit` layer with `merge-keys: [global-config]` (`_merge_config_key()` -> `deep_merge_settings(array_union_keys=set(), preserve_nulls=True)`) deep-merges objects but lets a child array replace the parent's at every depth; without `merge-keys` the child's section replaces the parent's whole. Against `user-settings`: its `inherit` layer unions `permissions.allow/deny/ask` (`DEFAULT_ARRAY_UNION_KEYS`) and replaces every other array, its base-mode writer unions every array in `~/.claude/settings.json` exactly as above, and its isolated `config.json` is rebuilt from the resolved YAML each run, so the arrays there are exactly the resolved ones. Only `oauthAccount` blocked from non-null values (`GLOBAL_CONFIG_EXCLUDED_KEYS`); `null` allowed for clearing OAuth. `install_claude.py`'s `update_install_method_config()` also writes to `~/.claude.json` via the same read-merge-write pattern (values `'native'`/`'global'`/`'winget'` -- see Native Claude Code Installation Support).

**installMethod propagation:** `_propagate_install_method()` runs at Step 15 just before `write_global_config()`. When `command-names` creates an isolated environment, it reads `installMethod` from the base `~/.claude.json` and injects it into `global-config` (creating the dict when the YAML lacks the section, so the empty-config short-circuit does not skip the Step 15 write), letting the Step 15 write carry the machine-baseline value to the isolated `.claude.json`; the base file is read, never written. WARN-but-Respect: a user-declared YAML `installMethod` wins with a warning when it differs; when the base file or key is absent (or the base JSON is invalid), nothing is propagated. Because propagation runs at Step 15 -- after the pre-confirmation summary has rendered and after Claude Code is installed (so the base `installMethod` exists) -- the propagated value is announced with an `info()` message at injection time and appended to the run's auto-injected list for the record, rather than shown in the pre-confirmation summary.

**Profile-confined writes:** an isolated run writes inside its profile directory and nowhere else, apart from the machine-wide items one machine holds once. `.claude.json` and `settings.json` are both single-write with scope-based routing: the CLI resolves `.claude.json` via `getGlobalClaudeFile()` and `settings.json` via `getClaudeConfigHomeDir()`, both under `CLAUDE_CONFIG_DIR` when it is set and under the home directory otherwise, with no fallback or inheritance, so each profile reads its own pair and a write into another profile's pair reaches nothing that profile's sessions use. The only base-file write an isolated run can cause is `installMethod` in `~/.claude.json`, recorded by `install_claude.py`'s `update_install_method_config()` when Step 1 installs, upgrades or migrates the binary. Every write that leaves the profile directory is named in the installation summary before consent: `collect_machine_wide_writes()` fills `InstallationPlan.machine_wide_writes` for an isolated run (the binary install or kept version with the `installMethod` record, a version pin, the IDE extension Step 2 installs at that pin -- `main()` passes the CLI names from the read-only `_detect_vscode_family_ides()` as `ide_clis` only under Step 2's own gate, pinned and not `--skip-install`, so the row names the detected IDEs and is absent when none is detected -- each OS-level `MACHINE_WIDE_ENV_CONTROLS` set or deletion, the `~/.local/bin` wrappers, project-scope MCP servers in the working directory's `.mcp.json`, `files-to-download` destinations outside the profile, and the dependency commands), rendered as a `Machine-wide writes` block with `[machine-wide]` rows; a base run's `OS environment variables` row is labeled `(machine-wide)` instead. `account_key_deletion_warnings(global_config, target_file, profile_label)` fills `InstallationPlan.account_key_warnings` when the resolved `global-config` sets a `GLOBAL_CONFIG_ACCOUNT_KEYS` member (`oauthAccount`, `userID`) to null and the `.claude.json` this run writes holds a non-null value for it; the warning names the profile and the file in the `[!] ATTENTION` block (and therefore in `--dry-run`), never prints the values, and blocks nothing. The final summary prints `Global config: configured in <target file>` and, for an isolated run, `User settings: built into <profile>/config.json` (Step 18 builds them into `config.json` while Step 14 skips the write); a base run prints `User settings: configured in ~/.claude/settings.json`. `tests/e2e/test_profile_confinement.py` drives every one of these cases through `main()` and also sources the generated loaders for real: `env.sh` under bash on every platform, `env.cmd` and `env.ps1` on Windows, proving that a null entry removes a variable the session inherited; `tests/e2e/shells.py` holds the shared bash and PowerShell lookups those tests use.

**Null-as-delete (RFC 7396):** `null` values in `user-settings`/`global-config` delete the key from the target JSON. `_merge_recursive()` runs in two modes. The on-disk writers APPLY the patch: `target.pop(key, None)`, and a subtree landing on a key the file lacks (or on a non-object member) is merged into a fresh empty object, so `null` members at every depth are dropped and a literal JSON `null` is never written -- Claude Code copies a null `env` member into the process environment as the string `'null'`, so a leaked `ANTHROPIC_AUTH_TOKEN: null` would send the token `null`. The `inherit` layer COMPOSES patches (`preserve_nulls=True` in `_merge_config_key()` for `user-settings` and `global-config`, and the shallow `{**parent, **child}` merge for `os-env-variables`): a child `null` is stored as `None` so the deletion request reaches the writer even when the parent declared a value (applying the resolved config equals applying the parent and then the child). Null in arrays is NOT deletion. Bare YAML keys (`key:` with no value) also trigger deletion -- use `key: ""` for empty strings. Dry-run shows `[DELETE]` markers in RED. `user-settings.env` and `os-env-variables` values support the same convention (`dict[str, str | None]`): a null `user-settings.env` entry deletes the variable -- `create_profile_config()` strips per-key nulls before the atomic isolated `config.json` write (absence equals deletion; the literal JSON null is never written for env entries, and the `env` key is dropped entirely when every entry is null) while the base-mode merge writer deletes `env.VAR` from `~/.claude/settings.json` -- and a null `os-env-variables` entry deletes the OS-level variable.

### Two-File Architecture for Command Environments

When `command-names` is specified, the setup creates an isolated directory `~/.claude/{cmd}/` containing one toolbox-written configuration file delivered to Claude Code at the command-line settings layer:

| File          | Priority         | Content                                                                                          | Write Mechanism                                |
|---------------|------------------|--------------------------------------------------------------------------------------------------|------------------------------------------------|
| `config.json` | 2 (flagSettings) | YAML `user-settings` content merged with toolbox-built `statusLine` and `hooks` entries          | Atomic overwrite via `create_profile_config()` |

The toolbox does NOT write `~/.claude/{cmd}/settings.json` in isolated mode. The `user-settings` section (raw `settings.json` keys with camelCase names) is merged directly into `config.json` by `create_profile_config()` alongside the `statusLine` and `hooks` entries built from the root-level YAML keys. The two sources are disjoint by construction: `statusLine` and `hooks` are rejected inside `user-settings`.

Scope-based routing: `command-names` presence in the final resolved config determines where `write_user_settings()` writes. Present: Step 14 prints an info message and skips the write (user settings are built into `config.json` in Step 18 instead). Absent: `write_user_settings()` deep-merges into `~/.claude/settings.json`. Never dual-write.

The launcher (`launch.sh`) passes `config.json` via `--settings` flag, passes `--strict-mcp-config --mcp-config <mcp.json>` through the `MCP_FLAGS` bash array (one argument per element, so a path with spaces survives), and sets `export CLAUDE_CONFIG_DIR` to the isolated directory.

**Launcher and wrapper paths:** `create_launcher_script()` and `register_global_command()` spell every path a launcher or wrapper reads (the exported `CLAUDE_CONFIG_DIR`, `config.json`, `mcp.json`, the system prompt, the `env.*` loaders, `launch.sh`) from the profile directory `artifact_base_dir`, which a `user-settings.env` `CLAUDE_CONFIG_DIR` can move out of `~/.claude/{cmd}`. `_spell_profile_dir()` returns the bash, CMD and PowerShell spellings: home-relative (`$HOME/...`, `%USERPROFILE%\...`, `Join-Path $env:USERPROFILE "..."`) when the directory lies below `get_real_user_home()` -- compared component-wise with `os.path.normcase`, so Windows casing does not matter -- so the scripts follow the home each shell resolves at run time, and absolute otherwise (mixed `C:/...` form for bash on Windows). Literal components go through `_escape_bash_double_quoted()`, `_escape_cmd_set_value()` (also used by the env loaders) and `_escape_powershell_double_quoted()`. The launchers and the CMD and Git Bash global commands use those spellings; the PowerShell global commands (`~/.local/bin/{cmd}.ps1` and one per alias) name `start.ps1` by its absolute path, and the Unix global commands are symlinks to the absolute `launch.sh`. The default `~/.claude/{cmd}` renders byte-for-byte as `tests/e2e/expected/launchers.py` pins, and `tests/e2e/test_launcher_profile_paths.py` plus `tests/e2e/test_relocated_profile_setup.py` run every launcher and wrapper of relocated profiles (directly below, deeper below and outside the home, with spaces, and on Windows with the home written in other letter case) under bash, cmd.exe and PowerShell with a stub `claude`.

**Setup-time `CLAUDE_CONFIG_DIR` export (two orthogonal channels):** `main()` exports `os.environ['CLAUDE_CONFIG_DIR'] = str(artifact_base_dir)` (guarded by `if primary_command_name:`) immediately after the `artifact_base_dir` assignment, before deriving artifact directories. This is process-scoped and transient -- never written to `config.json` -- so setup-time child processes (dependency installers, `npx` tooling, `claude mcp ...`, IDE-extension installer) target the isolated profile. This is distinct from the runtime launcher export above (the authoritative runtime source) and from the six per-call MCP `CLAUDE_CONFIG_DIR` injections in `configure_mcp_server()` (load-bearing on the Windows curated-`extra_env` path, which does not inherit `os.environ`; all six are KEPT).

**Ambient `CLAUDE_CONFIG_DIR` guard:** `resolve_artifact_base_dir(primary_command_name, user_settings)` is the single side-effect-free computation of the run's target directory (`~/.claude/{primary}`, the `user-settings.env` override, or the base `~/.claude`), returning `(base_dir, uses_user_config_dir)`; both the guard and `main()`'s later `artifact_base_dir` assignment call it, and the assignment site owns the `info()` message and the `user-settings.env` pop. The `command-names` parse and validation sit directly after the `--list-components` exit so `check_ambient_claude_config_dir(primary_command_name, artifact_base_dir)` can run on the resolved target before the component picker, the Windows elevation check and the installation summary -- no prompt precedes a refusal, and `--dry-run` reports it. A NON-isolated run with ANY ambient `CLAUDE_CONFIG_DIR` exits 1: the CLI resolves the variable ahead of the home directory with no fallback, so `claude mcp add` and `_claude_global_config_file(None)` would use `$CLAUDE_CONFIG_DIR/.claude.json` while `write_global_config()` writes `~/.claude.json` -- a value equal to `~/.claude` splits the run just as much, hence no equality exemption. `_ambient_claude_config_dir()` is the single definition of "set" (any non-empty value, whitespace included, matching the CLI) shared by the guard and `_claude_global_config_file()`. An ISOLATED run whose ambient value differs from its target directory warns that the value is replaced for setup-time child processes; equal values print nothing. Comparison goes through `_normalize_config_dir_key()` (expanduser + `os.path.abspath` + `_normalize_project_dir_key`), so separators, trailing slashes, and Windows casing do not produce false warnings. `tests/conftest.py`'s autouse `_isolate_claude_config_dir` clears the variable for every test, because `export_setup_time_config_dir()` leaks it into the session and a developer running the suite from inside an isolated profile would inherit it.

### MCP Server Permissions

When `command-names` creates an isolated environment, `configure_mcp_server()` propagates `CLAUDE_CONFIG_DIR` to the subprocess for `scope: user` servers, ensuring they are written to the isolated `.claude.json`.

**Strict-mode scope warning:** the launcher enables `--strict-mcp-config --mcp-config mcp.json` by a runtime file-existence test, so the isolated sessions read ONLY that file whenever it exists. `configure_all_mcp_servers(..., command_names=...)` collects every server whose normalized scopes are non-profile-only into `strict_hidden` during the loop and reports them AFTER the profile-config write/remove block, gated on `profile_mcp_config_path.exists()` -- the same question the launcher asks, so a failed write (or a stale config that could not be removed) cannot leave the report out of step with runtime. One `warning()` per server names the server, its scope, every command name sharing the launcher, where the registration actually ended up (`_strict_hidden_registration_note()`: `project` scope stays in the setup directory's `.mcp.json` and still loads elsewhere, while `user`/`local` scope lands in the isolated profile's own `.claude.json` and therefore loads nowhere), and the `scope: [<scope>, profile]` fix. `stats['strict_hidden_count']` carries the count into the completion summary. `normalize_scope()` forbids combining two non-profile scopes, so the named scope is always singular.

### Idempotent MCP Configuration

`claude mcp remove` deletes the stored MCP OAuth tokens and client config of http/sse servers (keyed `<name>|sha256(JSON.stringify({type,url,headers}))[:16]` in `.credentials.json`), and `claude mcp add` restores only the connection config -- so an unconditional remove/add cycle de-authenticates every authenticated remote server on every run. `configure_all_mcp_servers()` therefore plans per (server, scope) via `_plan_mcp_server_action()`: `_read_live_mcp_entries()` reads the files the CLI mutates (`.claude.json` top-level `mcpServers` for user scope, `projects[<cwd>].mcpServers` for local -- Windows path keys matched case-insensitively with forward slashes via `_find_project_entry()` -- and `<cwd>/.mcp.json` for project scope; `CLAUDE_CONFIG_DIR`/`artifact_base_dir` resolves the isolated file), `_build_expected_mcp_entry()` predicts the exact entry `claude mcp add` writes per platform (stdio: tilde expansion, Windows backslash conversion + `cmd /c` npx wrapper, `env` dict; http/sse: url + parsed `headers`), and `_mcp_entries_equal()` compares toolbox-controlled fields with absent-equals-empty normalization. `env` is a stdio-only field (`MCPServerHTTP` has none): the stdio paths send `--env` and write the `env` dict, while the http/sse paths carry url and headers only. Skip happens only on positive proof of equality at the DECLARED scope; removal (`_remove_mcp_server_from_cli_scopes()`, also used via `configure_mcp_server(remove_scopes=...)`) is always narrowed to scopes that actually hold the name; unreadable config falls back to the full three-scope remove+add; a changed http/sse server still loses tokens (key is config-derived -- inherent) with a re-authenticate warning. `stats['unchanged_count']` reports skips. Per-project `/mcp` disable state (`projects[*].disabledMcpServers`) lives outside server entries and is untouched by add/remove. Real-binary E2E (`tests/e2e/test_real_claude_binary.py`; marker and CI contract under E2E Testing) locks serialization parity and skip behavior against the actual CLI in an isolated `CLAUDE_CONFIG_DIR`.

### Automatic Auto-Update Management

`setup_environment.py` automatically blocks Claude Code's own update paths (the background updater, `claude update`, `claude install`) when a specific Claude Code version is pinned via `claude-code-version` in YAML, and removes the controls when using latest/absent version (see Unpinned removal semantics). Manages 3 in-memory dict targets via `apply_auto_update_settings()`: `global-config` gets `autoUpdates: false`; `user-settings.env` and `os-env-variables` each get every `AUTO_UPDATE_ENV_CONTROLS` entry in tuple order -- `DISABLE_AUTOUPDATER_KEY` (`DISABLE_AUTOUPDATER`, stops only the background updater) then `DISABLE_UPDATES_KEY` (`DISABLE_UPDATES`, also makes `claude update`/`claude install` print `Updates are disabled by your administrator` and exit 0). Both env keys are written because Claude Code releases before 2.1.118 recognize only `DISABLE_AUTOUPDATER`; a pin to such a release blocks only the background updater. Moving a pinned machine to another release means changing `claude-code-version` and re-running the setup, whose GCS direct download is not gated by `DISABLE_UPDATES` (an official-installer run it refuses is a failed attempt -- see DISABLE_UPDATES refusal above). WARN-but-Respect semantics (per key): if the user explicitly sets a contradicting value in their YAML configuration (e.g., `autoUpdates: true` in `global-config` while pinning a version), the user value is preserved and a warning is emitted. For the `AUTO_UPDATE_ENV_CONTROLS` keys and `CLAUDE_CODE_IDE_SKIP_AUTO_INSTALL`, `_env_control_enabled()` decides the match: a value Claude Code treats as enabled (`ENV_CONTROL_TRUTHY_VALUES` -- `1`/`true`/`yes`/`on`, trimmed, case-insensitive) matches the pin's intent silently, and any other value warns. Injection is membership-gated (`key not in dict`), so an explicit user `null` (a deletion request) also counts as a user declaration and is respected with a warning, never overwritten. The `[auto]` marker in the installation summary shows auto-injected values. Auto-update management is solely the responsibility of `setup_environment.py`; `install_claude.py` does not participate in auto-update configuration.

**Machine-wide pin gate:** The machine has ONE Claude Code binary, so its auto-update and IDE-extension controls are machine-global and shared by every installed profile. Removal is therefore gated on `machine_pinned = is_pinned or other_profile_pinned`, computed once in `main()` before `apply_auto_update_settings()`. `_other_profile_pins(home_dir, primary_command_name)` reads `~/.claude/manifest.json` plus every `~/.claude/*/manifest.json` via `_read_profile_pin()`, skips the manifest whose `name` equals this run's `primary_command_name` (`None` identifies the base profile, so a profile relocated by a user-set `CLAUDE_CONFIG_DIR` is still matched as its own), and returns a `_ProfilePinScan` carrying the sorted display names of the rest that record a non-empty `claude_code_version`, an `undetermined` flag, and the sorted distinct `pinned_versions` those profiles record. The scan FAILS CLOSED: an absent manifest is a definite "no pin", but a manifest that exists and cannot be read (`OSError`, invalid JSON, non-object JSON) or a profile directory that cannot be listed sets `undetermined`, and `_ProfilePinScan.other_profile_pinned` is true for either -- sweeping machine-global controls on a registry the run could not read in full can break a pin it never saw. When this run is unpinned and `other_profile_pinned` is true, `main()` prints the `_pinned_elsewhere_message()` info line naming those profiles, or stating that a manifest could not be read. `machine_pinned` threads into `_run_stale_controls_cleanup()`; `other_profile_pinned` threads into `apply_auto_update_settings()` / `apply_ide_extension_settings()` as a REQUIRED keyword-only argument, because the value that skips removal must never be supplied by default. The binary is held the same way: right after the scan, `main()` computes `_decide_claude_install(claude_code_version_normalized, scan, *, installed_version=...)`, which Step 1 follows; `installed_version` comes from `_installed_claude_version()` (resolves claude via `find_command()`, runs `claude --version` with a 30-second timeout, extracts the version with install_claude.py's own `(\d+\.\d+\.\d+)` regex, and returns `None` for a missing, non-executing, timed-out, failing, or version-less binary) and is probed only for an unpinned run while `other_profile_pinned` is true. A pinned run installs its own pin and an unpinned run with no pinned sibling installs or upgrades to latest; an unpinned run while `other_profile_pinned` is true hands `install_claude(version, keep_installed=True)` the installed version (`kept=True`), so `ensure_claude()` finds the requested version already installed and keeps it (its same-version npm->native migration is `exact_version_only`) while the installer's usual checks still run -- `ensure_claude()`'s corrupt-binary quarantine and `install_claude.py` `main()`'s Git Bash check on Windows -- which is also why the Windows admin gate needs no special case. A missing or non-working binary is installed at the one known pinned version (warning when the scan is also undetermined), or at latest with a warning when the pins disagree or none is known. The probe is skipped under `--skip-install`. `plan.claude_code_version`, `plan.keep_installed_claude`, `plan.claude_install_reason` (appended to the keep and install lines), and `plan.claude_install_warning` carry the decision into the installation summary (the warning shows before consent and in `--dry-run`), and the final summary reports a kept binary as `Kept at <version> (<reason>)`.

**Profile manifests:** `write_manifest()` records, beside `name`, `version`, `claude_code_version` (the normalized pin, or `null`), `config_source` (the RESOLVED source: absolute path or URL), `config_source_url`, `config_source_type` and `installed_at`: `config_identity` (`config_identity_of()`), `config_digest` (sha256 of `resolved-config.yaml`, written beside the manifest from `resolved_config_snapshot()` -- the component-selected configuration without `PROFILE_IDENTITY_CONFIG_KEYS`, taken in `main()` right after selection and before auto-injection), `command_names`, `components` (the typed `select`/`with`/`without` delta, a picker choice that changed the set in the same form, or `null`), `link` (`LinkSpec.record()`: `dirs`, `source` and per-key `origins`, or `null` when the run links nothing or installs the base profile), `origins` (`command_names`: `cli`/`env`/`yaml`/`default`/`null`; `components`: `cli`/`env`/`yaml`), `yaml_values` (the configuration's own `command_names` captured before the effective names overwrite `config['command-names']`, its `link_dirs` and `link_from`, and the default component names), `machine_wide_destinations` (`machine_wide_download_records()`: `files-to-download` outside `~/.claude` with resolved source and on-disk sha256), `os_env_written` (OS-level variables set), `settings_keys_written` (`written_settings_keys()`: non-null top-level keys, and one `env.<VAR>` entry (`SETTINGS_ENV_ENTRY_PREFIX`) per non-null env variable, so a switch can remove one entry and keep the rest), `mcp_servers` (`mcp_server_records()`) and `files_written` (`planned_profile_files()`, installer-mirroring relative paths). `main()` builds these once as `manifest_records` after Step 16 and both Step 19 branches pass them through; `tests/e2e/expected/common.py` pins the field set and `validate_manifest()` checks identity, digest and record shapes. Every toolbox-managed profile gets a manifest: the isolated branch writes `~/.claude/{cmd}/manifest.json` (`name` = primary command name) and the non-isolated branch writes `~/.claude/manifest.json` (`name` null, `command_names` empty) at the same Step 19 position.

**Write-remove symmetry:** Auto-update controls are written to the running profile's own files via scope-based routing, and removal sweeps the same two files. `_run_stale_controls_cleanup(machine_pinned, user_declared_keys, profile_dir)` runs as a post-write pass in `main()` (Step 16), passing `machine_pinned`, the running profile's directory (`None` for the base profile), and the user-declared control keys -- collected by `_collect_user_declared_control_keys(user_settings, global_config=...)` BEFORE injection: every `MACHINE_WIDE_ENV_CONTROLS` key `user-settings.env` sets to a non-null value (a null is a deletion request and never shields a stale copy) plus each `MACHINE_WIDE_JSON_CONTROLS` key (`autoUpdates`, `autoInstallIdeExtension`) that `global-config` sets to `false` -- to both `cleanup_stale_auto_update_controls()` and `cleanup_stale_ide_extension_controls()`. Both return immediately when `machine_pinned` is true, so nothing is swept and a pinned profile's controls are never stripped by any run. Otherwise they sweep ONLY the pair `_profile_control_files(home_dir, profile_dir)` returns -- `~/.claude/settings.json` and `~/.claude.json` for a base run, `settings.json` and `.claude.json` inside the profile directory for an isolated run -- except that the `settings.json` sweep is skipped for an environment control key the current YAML sets to a non-null value in `user-settings.env`, and the `.claude.json` sweep for `autoUpdates`/`autoInstallIdeExtension` when the YAML sets it to `false` in `global-config` (the removal counterpart of WARN-but-Respect; without this gate Step 16 would delete a declared `autoUpdates: false` that Step 15 just wrote). Other profiles' files are never edited: `find_stale_controls_in_other_profiles(home_dir, profile_dir=..., machine_pinned=..., user_declared_keys=...)` scans the base pair and every `~/.claude/*/` pair except the running profile's under the same two gates and returns `StaleControlCopy(profile, file, keys)` entries (`'base'` or the directory name; env keys present in a `settings.json`, keys holding `false` in a `.claude.json`); `main()` lists them in the pre-consent summary (`Stale update controls in other profiles (not edited by this run):`, each row from `_stale_control_copy_line()`, which ends with the `--profile <name>` command that removes the copy, plus `STALE_CONTROLS_RERUN_NOTE`), Step 16 prints them again as warnings, and the final summary repeats them with the note to re-run each listed profile with `--profile`. `cleanup_stale_auto_update_controls()` and `cleanup_stale_ide_extension_controls()` take the keyword-only `user_declared_keys: frozenset[str]` and `profile_dir: Path | None`; the former decides each `AUTO_UPDATE_ENV_CONTROLS` key independently (declaring `DISABLE_AUTOUPDATER` still sweeps a stale `DISABLE_UPDATES`, and the reverse); `_cleanup_settings_json_env_controls(path, keys)` deletes every present undeclared key in one null-as-delete `_write_merged_json()` write and drops an emptied `env` object; `cleanup_stale_ide_extension_controls()` sweeps its `settings.json` through the same helper with `(IDE_SKIP_AUTO_INSTALL_KEY,)`. Every cleanup helper skips a file whose JSON is not an object. Removal of `autoUpdates` from a `.claude.json` is value-conditional: only `false` is removed, `true` (user preference) is preserved, and a `global-config` declaration of `false` keeps it.

**Unpinned removal semantics:** On an unpinned run nothing is auto-injected, so `_remove_auto_update_controls()` and its counterpart `_remove_ide_extension_controls()` preserve every user-declared control in the three in-memory dicts (the removal counterpart of WARN-but-Respect). Their only mutation schedules an OS-level deletion entry per managed variable (`os_env_variables[KEY] = None` for each `AUTO_UPDATE_ENV_CONTROLS` key, respectively `CLAUDE_CODE_IDE_SKIP_AUTO_INSTALL`, gated on `KEY not in os_env_variables` so it is skipped only when the user declares that variable in `os-env-variables` specifically) because OS-level variables have no filesystem sweep; the deletions reach the OS writer from a base run and from an isolated run alike, because the three keys are `MACHINE_WIDE_ENV_CONTROLS` and never routed to a profile loader. Stale on-disk artifacts in the running profile are removed by the Step 16 sweep instead. Both removers are skipped entirely when another installed profile pins a version, so no OS-level deletion is scheduled while the machine-global variables are still needed. Removal does not track who set a value: when nothing on the machine pins a version, a run removes every `DISABLE_AUTOUPDATER` and `DISABLE_UPDATES` its YAML does not declare from the OS environment and from its own `settings.json`, including values set by hand outside the toolbox; a declaration in `os-env-variables` keeps the OS-level variable, and one in `user-settings.env` with a non-null value keeps it in the running profile's `settings.json` (a null there is a deletion request, so the sweep removes it there). Provenance gating is deliberately absent, because an interrupted pinned run or a deleted pinned profile would otherwise leave an orphaned `DISABLE_UPDATES` silently blocking every update; a copy left in another profile is reported, and that profile's own re-run removes it.

### Sudo Handling (Three-Tier Fallback)

`install_claude.py`'s `install_claude_npm()`/`remove_npm_claude()` AND `setup_environment.py`'s global-npm dependency retries and Node.js installers delegate to the shared `_run_with_sudo_fallback()` helper (intentionally identical copies in both scripts -- see Standalone Script Policy) for elevated permissions:

1. **Tier 1 -- Interactive:** `sys.stdin.isatty()` → sudo directly (user enters password via stdin)
2. **Tier 2 -- Cached credentials:** `sudo -n true` probe → sudo without prompting if cached
3. **Tier 3 -- `/dev/tty` fallback:** `_dev_tty_sudo_available()` → sudo with stdin from `/dev/tty` (enables password entry in piped mode like `curl | bash`; default `tty_timeout=60`)

If all tiers exhausted, returns `None` (caller provides guidance). Catches `FileNotFoundError`/`TimeoutExpired` at each tier. `remove_npm_claude()` captures npm output to suppress noisy stack traces.

**Dependency escalation (setup_environment.py):** In `install_dependencies()`'s non-Windows branch, a failed dependency is retried via `_run_with_sudo_fallback(shlex.split(expanded_dep), capture_output=False, timeout=600)` ONLY when ALL of: `_is_global_npm_install(dep)` (the `'npm install -g' in dep` predicate, also reused by `admin_elevation_reasons()`, which feeds the Windows elevation banner and its dry-run report), the expanded command contains no shell control characters (`_contains_shell_control_chars()`: `;`, `&`, `|`, `<`, `>`, `$`, backquote, newline -- user-authored compound shell strings are never run as root), and `needs_sudo_for_npm()` reports the npm global prefix is not user-writable. An informational "sudo may be requested" note prints before the first attempt; when the fallback returns `None` or fails, actionable guidance prints (manual sudo command, `npm config set prefix ~/.npm-global` + PATH export, node version manager). The macOS pkg installer (`_install_nodejs_direct()` Darwin branch) and the Debian/Ubuntu apt/NodeSource path (`_install_nodejs_apt()`) route their sudo invocations through the same helper (600-second timeouts) and fail cleanly with guidance in piped non-interactive runs instead of hanging.

**Dependency failure surfacing:** `install_dependencies()` returns `list[str]` of failed dependency commands (empty list = success; continue-on-failure preserved). `main()` lists failures in a dedicated "The following dependencies failed to install:" section of the "Setup Completed with Errors" block and exits 1, parallel to `download_failures`.

### Download Retry Configuration

Retry logic for GitHub API rate limiting: 10 attempts with linear additive backoff (1s, 3s, 5s, 7s, ..., capped at 60s) plus random 0-25% jitter. Concurrent downloads use 0.5s stagger delay between threads. `RateLimitCoordinator` shares rate-limit state across threads. `Retry-After` and `x-ratelimit-reset` headers used as minimum floor.

`AuthHeaderCache` provides thread-safe per-origin auth header caching (modeled after `RateLimitCoordinator`). `get_origin()` normalizes URL variants (GitHub web/raw/API, GitLab web/API) to a single cache key. A single instance is created in `main()` and shared across both the validation phase (`FileValidator`) and all download functions, so auth discovered during validation is reused during downloads. The first request per origin probes unauthenticated; on auth resolution, subsequent requests for the same origin skip the probe. `resolve_and_cache()` uses double-checked locking for thread safety. `_fetch_url_core()` (DRY refactor of the former near-duplicate `fetch_url_with_auth`/`fetch_url_bytes_with_auth`) implements auth resolution priority: explicit `auth_headers` param > `auth_cache` hit > unauthenticated probe with cache population. GitHub API transport headers (`Accept: application/vnd.github.raw+json`, `X-GitHub-Api-Version`) are managed independently from cached auth headers via `github_api_headers` dict and `_build_request()` helper in `_fetch_url_core()`, applied to every `Request` construction in `_do_fetch()` when `'api.github.com' in url`.

**Lazy-auth invariant (validation + download parity):** Both `FileValidator.validate_remote_url` and `_fetch_url_core._do_fetch` MUST honor the "try unauthenticated first; escalate to authentication only on HTTP 401, 403, or 404" contract. Non-auth failures (SSL, DNS, 5xx, timeout, 416 Range Not Satisfiable) MUST NOT trigger auth prompts. Successful unauthenticated probes cache a `None` sentinel in `AuthHeaderCache` for downstream consumers. When `auth_cache` is available, route escalation through `AuthHeaderCache.resolve_and_cache(url)` (double-checked locking) to serialize prompts across parallel validation threads. Helper functions `_check_with_head` and `_check_with_range` return `tuple[bool, int | None]` where the second element is the HTTP status code (or `None` for non-HTTP failures) used to gate the escalation decision.

**Authentication SRP:** `get_auth_headers(url, auth_param)` is a thin orchestrator that delegates to `resolve_credentials(url, auth_param)` (pure, non-interactive -- reads CLI param + env vars only) and then escalates to `prompt_for_credentials(url, tokens_checked=[...])` (interactive, guarded by `sys.stdin.isatty()`). The split is transparent to existing callers (`get_auth_headers` preserves its original signature and behavior), but enables non-interactive callers to opt into credential resolution without risking user prompts. The interactive prompt uses the wording `Authentication required for {url}` (both the `warning(...)` on interactive terminals and the `info(...)` fallback on non-interactive terminals emit this URL-qualified message); the earlier `Private {RepoType} repository detected but no authentication found` wording has been removed.

**Repository type classification (`detect_repo_type`):** Uses hostname-based matching via `urllib.parse.urlparse`. GitHub Pages URLs (hostname ending in `.github.io`) are explicitly classified as `None` (not `'github'`) because GitHub Pages sites are static HTTP hosts with no repository auth model. `github.com`, `raw.githubusercontent.com`, and `api.github.com` are classified as `'github'`. GitLab classification uses both hostname substring (`'gitlab' in host`) and the API path marker (`/api/v4/projects/`).

**GitHub 404 disambiguation (UX polish):** When a GitHub URL returns HTTP 404 during validation, before escalating to an auth prompt, the validator probes `GET https://api.github.com/repos/{owner}/{repo}` unauthenticated. If the repo endpoint returns 200, the original 404 is classified as a **genuine missing file** (typo) and the auth prompt is skipped (returns failure directly). If the repo endpoint returns 404 (private-hidden or nonexistent -- GitHub does not distinguish), the validator conservatively escalates to the auth prompt. Rate-limiting or network errors from the repo probe also trigger conservative escalation. The `/contents/{path}` endpoint intentionally cannot distinguish private-hidden from missing, which is why `/repos/{owner}/{repo}` is used instead.

### Hooks Configuration Structure

Hooks support five types matching the official Claude Code hooks specification:

| Type       | Required Fields  | Description                                        |
|------------|------------------|----------------------------------------------------|
| `command`  | `command`        | Executes a shell command or script (default)       |
| `http`     | `url`            | Sends an HTTP POST request                         |
| `prompt`   | `prompt`         | Single-turn LLM evaluation (no tool access)        |
| `agent`    | `prompt`         | Spawns a subagent with tool access for evaluation  |
| `mcp_tool` | `server`, `tool` | Calls a tool on an already-configured MCP server   |

Common fields available on all types: `if`, `status-message`, `once`, `timeout` (must be positive; non-positive values fail model validation and are warn-skipped at runtime).

Only `command` hooks reference files from `hooks.files`. Other types are pure pass-through. `_apply_common_hook_fields()` applies shared fields to all types. Event names are checked against `HOOK_EVENT_NAMES` (31 names Claude Code 2.1.238 recognizes; byte-identical frozensets in `setup_environment.py` and `environment_config.py`, parity enforced by `tests/scripts/models/test_hook_event_names_parity.py`): an unknown name warns but still installs, so configs written for newer Claude Code releases keep working. `_build_hooks_json()` also warns about (and ignores) YAML keys a hook type does not support; the `HookEvent` model rejects them outright (`extra='forbid'`).

**`hooks.helpers`** carries shared modules the hook scripts import. `download_hook_files()` concatenates `files` and `helpers` into one `process_resources()` call, so helpers land in the SAME directory as the scripts (`artifact_base_dir/hooks` in isolated mode, `~/.claude/hooks` in base mode) and a script reaches them through `Path(__file__).parent` in either mode -- which a literal `files-to-download` dest cannot do. Helpers are never registered as a command: `_build_hooks_json()`'s `listed_basenames` reads `hooks.files` only, so no helper name reaches the generated JSON or `statusLine`. `_merge_hooks()` deduplicates `helpers` through `_merge_string_list()` alongside `files`. Helpers are NOT a component identity (`_component_section_identities` and `apply_component_selection` read `hooks.files` and `hooks.events[].id` only), so no selector can claim one and deselection never deletes one. `FILE_REFERENCE_KEYS` carries `hooks.helpers` alongside `hooks.files`; path resolution and remote validation treat the two lists identically, except that helpers contribute no selector mapping. `InstallationPlan.hooks_helpers` feeds `total_resources` and the summary's `Hook helpers` row.

**Consistency validation:** the model's `validate_hooks_files_consistency` (skipped under `inherit`) and its runtime twin of the same name in `setup_environment.py` (running on the resolved config at the `main()` choke point) enforce the same rules: every `hooks.files` entry is referenced by a command hook or `status-line`, every command hook's `command`/`config` and the `status-line` `file`/`config` exist in `hooks.files` (`command` and `status-line.file` are exact basename matches; `config` references match after query-strip plus basename extraction), `status-line` without `hooks` is an error, and no basename appears in both `hooks.files` and `hooks.helpers`. `hooks.helpers` entries are exempt from the unused-files rule (they exist to be unreferenced); a reference resolving only to a helper basename produces the misplaced-declaration error instead of the generic not-found one, via the `_hook_helper_overlap_message`/`_hook_helper_reference_message` twins whose wording parity is locked by `test_hooks_consistency_parity.py`.

**Command construction:** the shared `_build_file_command()` builds hook and `statusLine` command strings identically (launcher selection via `_hook_launcher_args()`: Python via `uv run`, JavaScript via `node`, anything else executes directly) with built paths double-quoted so spaced hooks directories survive shell word-splitting. In `_build_hooks_json()`, a command is a file reference when it matches a `hooks.files` basename (even with spaces) or contains no spaces; anything else passes through as-is. When a command hook declares `args`, `_build_file_exec_command()` produces the exec form instead: the launcher executable becomes `command` and the launcher arguments, resolved script path, config path, and user `args` become the unquoted `args` list (no shell is involved; `shell` is warned about and dropped). The exec-form fold applies ONLY to commands listed in `hooks.files`; any unlisted command -- bare name or absolute path, with or without spaces -- stays verbatim as the executable (the shell form's no-space heuristic never reroutes it into the hooks directory).

```yaml
hooks:
    files: [my-hooks/linter.py]  # For command hooks only
    helpers: [my-hooks/hook_config_loader.py]  # Imported by the scripts, never launched
    events:
        - {event: PostToolUse, matcher: "Edit|MultiEdit|Write", type: command, command: linter.py}
        - {event: PostToolUse, matcher: Write, type: http, url: "http://localhost:8080/hooks/write",
           headers: {Authorization: "Bearer $API_TOKEN"}, allowed-env-vars: [API_TOKEN]}
        - {event: PreToolUse, matcher: Bash, type: prompt, prompt: "Check if this bash command is safe"}
        - {event: PreToolUse, matcher: "Bash(rm *)", type: agent,
           prompt: "Verify security implications of: $ARGUMENTS", once: true}
```

Type-specific fields (setting a field on the wrong type produces a validation error):
- **command**: `command` (required), `config`, `args` (exec form; conflicts with `shell`), `async`, `async-rewake` (emitted as `asyncRewake`), `shell`
- **http**: `url` (required; must be an http/https URL), `headers`, `allowed-env-vars`
- **prompt/agent**: `prompt` (required), `model`; prompt only: `continue-on-block` (emitted as `continueOnBlock`)
- **mcp_tool**: `server` (required), `tool` (required), `input`

### Two-Layer Naming Convention (Sub-Keys)

Sub-keys in structured sections (`hooks.events[]`) use kebab-case in YAML and are translated to camelCase for Claude Code JSON output by the setup script. Sub-keys in free-form sections (`user-settings`, `global-config`) pass through as-is and must match Claude Code's native camelCase.

### System Prompt Configuration

```yaml
command-defaults:
  system-prompt: "prompts/my-prompt.md"
  mode: "replace"  # "replace" (default, --system-prompt) or "append" (--append-system-prompt)
```

`command-defaults` and `version` are independent of `command-names`: the model validates each without the others, and neither key fails a run. Only an isolated profile's launcher passes the system prompt to Claude Code. A run without command names still installs the prompt file into `~/.claude/prompts/`, and because no launcher applies it, `InstallationPlan.command_defaults_isolated_only` (a non-empty `command-defaults` on such a run) makes the installation summary and `--dry-run` print `COMMAND_DEFAULTS_ISOLATED_ONLY_NOTE`, and the closing summary reports the system prompt as not applied via `system_prompt_completion_line()`. `version` is recorded in the manifest of either kind of run (see Profile manifests).

### Step Numbering Convention

Step comments/print statements in `main()` MUST use continuous whole integers (no gaps, no fractions like `Step 14.5`). When inserting a new step, renumber all subsequent steps and update ALL references (comments, print statements, test assertions, skip-range messages).

### Testing Traps

**Mock target alignment:** When refactoring call sites (e.g., `find_command()` → `shutil.which()`), ALL test `@patch` targets MUST be updated. When `shutil.which` replaces `find_command`, also mock `Path.exists()` for common-path checks.

**Windows-style paths:** Tests with Windows paths MUST use `@pytest.mark.skipif(sys.platform != 'win32', ...)`. `Path(r'C:\...')` on Linux becomes a single component -- `Path` uses the running OS's semantics.

**Platform detection mocks:** Mock ALL detection methods (`sys.platform`, `platform.system()`, `os.name`) in the code path. Mocking only one passes on that platform's CI but fails on others. Prefer ONE method per function (`sys.platform` recommended).

| Platform | `sys.platform` | `platform.system()` | `os.name` |
|----------|----------------|---------------------|-----------|
| Windows  | `'win32'`      | `'Windows'`         | `'nt'`    |
| Linux    | `'linux'`      | `'Linux'`           | `'posix'` |
| macOS    | `'darwin'`     | `'Darwin'`          | `'posix'` |

**Machine-state isolation:** `tests/conftest.py`'s autouse `_guard_real_home_writes` fails a unit test that writes, creates a directory, or unlinks a file under the real `~/.claude/` or `~/.local/bin/`, or writes `~/.claude.json` or a shell config file, and it fails through `pytest.fail`, which a writer's own `except OSError` does not catch. Every function that would make a unit test touch those locations is therefore isolated: the ones many unit tests reach without meaning to are replaced by autouse mocks -- the stale-controls sweeps (`cleanup_stale_auto_update_controls()`, `cleanup_stale_ide_extension_controls()`), `_propagate_install_method()`, `write_manifest()`, `generate_env_loader_files()`, and `_cleanup_old_claude_files()` -- and every other one, such as `install_claude.py`'s `update_install_method_config()` (writes `~/.claude.json`), is isolated in each test that reaches it, by patching the writer or by redirecting `get_real_user_home()`/`Path.home()` to `tmp_path`. `_mock_old_binary_cleanup` is one of those autouse mocks: `install_claude_native_windows()` first runs `_cleanup_old_claude_files()`, which on Windows deletes the `claude.exe.old*` files that replacing a running binary leaves in the real `~/.local/bin`, so the fixture replaces it in both module objects the installer is imported as (`install_claude` and `scripts.install_claude`). The tests of `_cleanup_old_claude_files()` itself call the reference `tests/test_install_claude.py` captures at import time, the same bypass the stale-controls and `installMethod`-propagation mocks use.

**Session PATH:** the setup code rewrites `os.environ['PATH']` in place -- `refresh_path_from_registry()` rebuilds it from the Windows registry (`main()` Step 13 among other places) and the installers prepend the directories they create -- so `tests/conftest.py`'s autouse `_restore_session_path` records PATH through `monkeypatch` and restores it after every test. Without it a `main()`-flow test hands its PATH to every later test, and a registry rebuild drops each directory only the process PATH holds, such as the uv directory a CI runner adds, which leaves later lookups of `uv` empty. `tests/e2e/test_session_path_isolation.py` proves the restore inside its own pytester sessions (`tests/conftest.py` loads the `pytester` plugin): a writer test changes PATH the way the setup code does and a reader test must then see the starting PATH, which holds with the fixture in the inner conftest and fails in a control session without it, so each outer test passes alone and in any selection.

### Agent Development Pitfalls

Recurring patterns that cause CI failures. Every item below has caused at least one real CI failure. Read this section before modifying `setup_environment.py` or its tests.

**Cross-platform test verification:** Local `uv run pytest` skips tests targeting other platforms (`@pytest.mark.skipif`). Developing on Windows means Unix-only tests are SKIPPED locally but WILL RUN in CI on Linux/macOS (and vice versa). A 100% local pass rate does NOT guarantee CI success. Before committing, review skipped tests to verify they would pass on their target platform. NEVER report a clean test run as definitive when platform-skipped tests exist.

**Tests must match implementation:** Every test assertion MUST correspond to actually implemented behavior. Do NOT write tests that assert behavior which has not been coded yet. If a test is for a new feature, implement the feature BEFORE or SIMULTANEOUSLY with the test. Tests that pass only because they are platform-skipped on the development machine will fail in CI on the target platform. This is the single most common cause of CI failures in this project.

**Parallel mock side effects:** Tests calling functions that use `execute_parallel()` (which uses `ThreadPoolExecutor`) MUST NOT use `mock.side_effect = [list]` with distinct values per item. The list is consumed in thread-scheduling order, not submission order. This causes non-deterministic failures depending on OS thread scheduling. Use either:

- `@patch.dict(os.environ, {'CLAUDE_CODE_TOOLBOX_SEQUENTIAL_MODE': '1'})` to force sequential execution in tests that verify logic (not parallelism)
- Function-based `side_effect` that maps inputs to deterministic outputs for tests that must run in parallel

**Shell escape sequence levels:** Modifying shell template strings (especially ANSI escape sequences like `\\\\033`) requires tracking three escaping layers: Python source string, generated shell script file, and final shell execution. A change that appears correct in Python source may produce wrong output in the generated `.sh` file. After modifying escape sequences, always verify the generated file content matches expectations.

**Multi-phase implementation counting:** When implementing multi-phase changes that introduce intermediate test failures, ALL failures MUST be explicitly counted including BOTH unit tests AND E2E tests. Agents have historically undercounted by omitting E2E failures. Each phase validation MUST confirm the exact failure count matches expectations before proceeding.

### GitHub Actions Security Policy

**NEVER use mutable branch references** (`@main`, `@master`) for third-party actions -- pin to immutable version tags (`@v5`, `@v0.35.0`). First-party actions (`actions/*`, `github/*`) and composite/docker actions may use major version tags. Version tag pinning (not SHA pinning) is the project standard.

**Verify action runtimes** before updating for Node.js 24 compatibility:
```bash
gh api repos/{owner}/{repo}/contents/action.yml?ref={tag} \
  --jq '.content' | base64 -d | grep -A1 "^runs:"
```
`node24` (preferred) | `composite`/`docker` (always compatible) | `node20` (deprecated, stops June 2, 2026). Note: some actions use `action.yaml` instead of `action.yml`.
