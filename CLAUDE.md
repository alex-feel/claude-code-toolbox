# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository Purpose

This is the Claude Code Toolbox - a community project providing automated installers and environment configuration tools for Claude Code across Windows, macOS, and Linux. The toolbox enables users to quickly set up specialized environments with custom agents, MCP servers, slash commands, and hooks.

## Key Architecture

### Two-Tier Installation System

1. **Platform-specific bootstrap scripts** (minimal)
   - Windows: PowerShell scripts in `scripts/windows/`
   - Linux/macOS: Bash scripts in `scripts/linux/` and `scripts/macos/`
   - These install `uv` (Astral's Python package manager) and run Python scripts
   - When `uv run` exits non-zero, each `setup-environment` and `install-claude` wrapper runs `uv python find` for the Python version it keeps in one variable (`PYTHON_VERSION` in bash, `$pythonVersion` in PowerShell) with the output discarded and, only when that fails too, prints the Step 19 repair `uv python install --reinstall 3.12` in `[FAIL]` lines naming the setup or the installer, exiting with the code `uv run` returned either way (`tests/e2e/test_bootstrap_wrappers_interpreter_hint.py`).

2. **Cross-platform Python scripts** (comprehensive installers)
   - `scripts/install_claude.py`: Installs Git Bash (Windows) and Claude Code via native installers with npm fallback
   - `scripts/setup_environment.py`: Configuration-driven environment setup from YAML (sources: repo name, local file path, or remote URL)

**Setup-time installer dispatch:** `install_claude()` in `setup_environment.py` runs the sibling `install_claude.py` (shipped in the wheel and staged by every bootstrap wrapper) with `sys.executable` on every platform, and downloads the platform bootstrap script only when no sibling exists. The sibling is NEVER launched through `uv run`: under `uvx` it lives inside uv's cache, and uv >= 0.11.21 refuses to run a script whose directory is inside the cache (`The project directory ... is inside the cache directory ...`). The installer needs only the standard library, so the interpreter already running the setup always suffices. The `package-smoke` CI job proves the dispatch inside a real `uvx` environment via `tests/fixtures/packaging_smoke_step1.py`.

### Native Claude Code Installation Support

The installer uses a native-first approach with automatic npm fallback. Entry point: `ensure_claude()` → `install_claude_native_cross_platform()` → platform-specific `install_claude_native_{windows,macos,linux}()`. Platform-specific fallback chains: Windows uses Native installer (with HTTP retry) → GCS direct download → npm; macOS/Linux use Native installer → GCS direct download → npm. In `native` mode, npm is excluded from the chain. A specific version otherwise falls back to the official installer at `latest` when the exact-version methods fail; `install_claude_native_cross_platform(..., exact_version_only=True)` (threaded to every per-OS function) uses the direct download alone -- on Windows it also skips winget, whose install is not native -- and returns `False` instead, and `ensure_claude()` uses it for the npm->native migration when the installed version already equals `CLAUDE_CODE_TOOLBOX_VERSION`, so a failed exact download keeps the npm installation at its version (migration-failed warning) rather than moving it to the latest release.

**DISABLE_UPDATES refusal:** the official `install.ps1`/`install.sh` scripts run `<binary> install [target]`, which Claude Code (>= 2.1.118) refuses under `DISABLE_UPDATES` -- read from the process environment AND from the `env` block of every settings source it loads at startup, including the user settings file (`$CLAUDE_CONFIG_DIR/settings.json`, else `~/.claude/settings.json`), project settings in the working directory (`.claude/settings.json`, `.claude/settings.local.json`), managed settings, the global config (`$CLAUDE_CONFIG_DIR/.claude.json`, else `~/.claude.json`), and a `--settings` file -- by printing `Updates are disabled by your administrator` and exiting 0, so the script reports success having installed nothing and a previously installed binary still verifies. `_install_claude_native_{windows,macos,linux}_installer()` therefore check every exit-0 run with `_installer_refused_by_disable_updates()` (`CLAUDE_UPDATES_DISABLED_MESSAGE` in stdout or stderr) and, on a refusal, call `_warn_installer_refused_by_disable_updates()` and return `False` before the success line, PATH update, verification, recovery, and finalization, so the caller continues its chain (every latest/`None` request -- Windows CASE 1 and macOS/Linux latest, which also serve unpinned fresh installs and the npm→native migration -- falls through to GCS direct download; the pinned last-resort `'latest'` fallback falls through to npm in `auto` mode). `_warn_installer_refused_by_disable_updates()` also sets the module flag `_disable_updates_refusal_observed`; once it is set, the failure guidance of `ensure_claude()` (item 1) and `install_claude_npm()` (item 3 on Windows, item 4 elsewhere; both lists name the platform's installer command, `irm ... | iex` on Windows and `curl ... | bash` elsewhere) prints `_info_official_installer_blocked()` in place of the recommendation to run the official installer directly (which the same `DISABLE_UPDATES` refuses): change the pin and re-run the setup when a setup configuration pins `claude-code-version`, otherwise remove `DISABLE_UPDATES` first; without a recorded refusal the plain recommendation prints. The installer never removes `DISABLE_UPDATES` from the installer's environment: a settings-sourced value would survive such a scrub, and the fallback chain already reaches methods `DISABLE_UPDATES` does not gate. The toolbox's own pinned install (GCS direct download) never runs `claude install`, and every `DISABLE_*` write in `setup_environment.py` happens after Step 1, so a pin cannot block its own installation. The real-binary E2E locks the refusal text against the actual CLI for both the process-environment and the settings-`env` source.

**Corrupt-binary detection and quarantine:** `get_claude_version()` delegates to `_probe_claude_version()`, which classifies exec-format launch failures via `_is_exec_format_error()` (Windows `winerror` 193/216, POSIX `errno.ENOEXEC`) as a WARNING ("cannot execute on this machine (corrupt or architecture mismatch)") instead of the generic `[FAIL]`; `FileNotFoundError` is never classified as corruption. `run_command()` is untouched (its contract for other callers is preserved). `ensure_claude()`'s initial probe runs `get_claude_version(quarantine_corrupt=True)`, so a corrupt native binary is moved aside via `_quarantine_corrupt_native_binary()` BEFORE any installation dispatch -- Windows renames to `.exe.old` (swept by `_cleanup_old_claude_files()` on the next run), Unix unlinks -- so it can no longer shadow npm installs through `find_command()`'s native-first priority. Quarantine acts only on the native target `~/.local/bin/claude[.exe]`. Post-install verification executes the installed binary via `_verify_installed_binary_executes()` (probe + quarantine on corruption) on the native-installer and all GCS install paths across Windows, macOS, and Linux; on the Windows native-installer primary path a non-executing binary enters the existing recovery chain.

**GCS download integrity and architecture selection:** `_download_claude_direct_from_gcs()` verifies the downloaded binary against `{gcs_base}/{version}/manifest.json` from the same GCS bucket (`_verify_gcs_download_integrity()`: exact byte size + streamed sha256 via `_sha256_file()`). Fail-closed: a manifest fetch failure or any size/checksum mismatch rejects the download and deletes the temp file. `_get_gcs_platform_path()` returns `tuple | None`: Windows ARM64 (`arm64`/`aarch64`) → `win32-arm64`, Alpine/musl Linux (detected via `/etc/alpine-release`) → `linux-{arch}-musl`, and any unrecognized architecture produces an explicit error and `None` (the caller aborts the GCS download instead of fetching a wrong-architecture binary).

**installMethod values:** `update_install_method_config()` writes `installMethod` to `~/.claude.json` with values `'native'` (native installer or GCS direct download), `'global'` (npm `-g` fallback installs), or `'winget'`. Claude Code itself recognizes `'native'`/`'global'`/`'local'` and reports a missing value as `'unknown'`.

### Standalone Script Policy

`install_claude.py` and `setup_environment.py` MUST be fully standalone -- NEVER import from each other. Users may run either script without the other being present.

`scripts/cli.py` is the packaging dispatcher and the ONLY module permitted to import both standalone scripts; neither standalone script may import it (CI enforced via `TestNoCliImports`, which checks import statements, not substrings -- `setup_environment.py` legitimately builds a `<package>.cli` module path as a runtime string for its UAC relaunch). `cli.py` uses relative imports so the same file serves as `scripts.cli` in-repo and `cc_toolbox.cli` inside the wheel; it is NOT a standalone script.

**Identical Code** (CI enforced via `tests/test_standalone_policy.py`): `Colors` class, `find_command()`, `_prefer_windows_executable()`, `get_real_user_home()`, `_dev_tty_sudo_available()`, `_run_with_sudo_fallback()`, `needs_sudo_for_npm()`, `_line_buffer_output_streams()` (EXACT body match), shell config file list (7 files + conditional filtering), Fish config detection (`'fish' in str()`), marker block constants (`# >>> claude-code-toolbox >>>`).

**Output order:** each script's `main()` first calls `_line_buffer_output_streams()`, which reconfigures `sys.stdout` and `sys.stderr` to line buffering (a stream without `reconfigure()`, such as an in-memory buffer a test put in its place, is left as it is), so a run whose output goes to a file or a pipe writes every line when it is printed. Python buffers stdout in blocks there, while every child process a run starts (the Step 1 installer, dependency commands, uv, the Step 24 dependent runs and every other child run) writes straight to the inherited descriptors and stderr writes each line at once, so without the call the log shows a run's lines after the output of children started later and after its own later error lines, and a failing dependent's errors land above its `=== Dependent profile NAME ===` header. `tests/e2e/test_redirected_output_order.py` starts a source run with a failing dependent, and the installer, as processes whose stdout and stderr go to one file and reads the order back; `tests/test_output_stream_buffering.py` covers the helper itself.

**Intentionally Different** (MUST NOT synchronize): `info()`/`success()`/`warning()`/`error()` (different formatting), `run_command()` (different encoding/error handling), `find_bash_windows()` (setup_environment.py has debug_log), `is_admin()` (different implementations).

**Native Path Priority:** `find_command()` and `verify_claude_installation()` check the native path (`~/.local/bin/claude[.exe]`) first, before `shutil.which()` PATH search. This ensures native binary is preferred even when PATH would resolve to npm first. Validates file exists with `st_size > 1000` to skip empty/corrupt files.

**Windows Executable Resolution:** On Windows, `shutil.which()` can resolve a command (e.g. `npm`/`npx`) to the extensionless Unix shell shim Node.js ships beside its `.cmd` wrapper; `subprocess.run(shell=False)` launches resolved paths via `CreateProcess`, which cannot execute that shim and raises `WinError 193` (`%1 is not a valid Win32 application`). This bites on Python builds before the gh-109590 fix (Windows `shutil.which` on CPython 3.12.0 and every 3.11-or-earlier release), which probe the bare name ahead of the PATHEXT variants. The shared `_prefer_windows_executable(cmd, resolved)` helper (identical in both scripts) swaps a non-executable resolution for the `.exe`/`.cmd`/`.bat`/`.com` wrapper and is applied in `find_command()`'s primary search and in `setup_environment.py`'s `run_command()` Windows resolution. `setup_environment.py`'s `run_command()` also catches `OSError` (alongside `FileNotFoundError`) so a single non-launchable command is recorded as a failure instead of aborting the whole run.

**Environment Variables:** `CLAUDE_CODE_TOOLBOX_INSTALL_METHOD` (`auto`/`native`/`npm`, default `auto` -- unknown sources → native-first with npm fallback), `CLAUDE_CODE_TOOLBOX_VERSION` (installs a specific Claude Code version; all methods support version pinning -- native via GCS download and npm; winget is used only for specific version requests and the upgrade_source=='winget' branch), `CLAUDE_CODE_TOOLBOX_ALLOW_ROOT` (`1` only -- see Root Detection Guard).

**Native Path Detection:** `verify_claude_installation()` classifies the binary location for upgrade strategy:

| Path Pattern                                      | Source               | Upgrade Method                        |
|---------------------------------------------------|----------------------|---------------------------------------|
| Contains `npm` or `.npm-global`                   | `npm`                | npm directly                          |
| Contains `.local/bin` or `.claude/bin`            | `native`             | Native installer                      |
| Windows: `Programs\claude` (legacy winget/native) | `winget` or `native` | Via `_classify_localappdata_claude()` |
| Windows: `WinGet\Links` or `WinGet\Packages`      | `winget`             | winget upgrade, then npm fallback     |
| Other / `/usr/local/bin`                          | `unknown`            | Native-first, npm fallback            |
| Not found                                         | `none`               | Fresh install                         |

In `auto` mode, `native` and `unknown` sources attempt native first with npm fallback. Confirmed `npm` sources go directly to npm. Confirmed `winget` sources try `winget upgrade` first, falling back to npm on failure.

### PyPI Distribution

The repository publishes to PyPI as `cc-toolbox` via an in-place hatchling remap: `[tool.hatch.build.targets.wheel]` `only-include`s exactly four files (`scripts/{__init__,cli,setup_environment,install_claude}.py`) and `[tool.hatch.build.targets.wheel.sources]` rewrites `scripts` → `cc_toolbox`, so the wheel ships `cc_toolbox/` while not one byte moves on disk and the curl|bash bootstrap path stays untouched. `scripts/models` is excluded from the wheel, keeping the runtime dependency closure to `pyyaml`, `questionary` and `truststore` (`pydantic` lives in the dev group). The single console script `cc-toolbox = "cc_toolbox.cli:main"` dispatches `setup`/`install` subcommands (`uvx cc-toolbox setup <config>`). The PEP 723 headers are inert comment blocks when the files are imported as modules, so identical bytes serve both `uv run --no-project` and the wheel.

**Editable-install limitation:** hatchling refuses dev-mode installs when `sources` changes a path prefix, so `[tool.uv] package = false` keeps `uv sync` from installing the project; the dev venv imports via pytest's `pythonpath = ["."]` (`scripts.cli`), and the packaged import path is exercised by `uv build` plus the `package-smoke` CI job (`uvx --from dist/*.whl` on Linux and Windows, and on macOS when the change needs it; deliberately NOT skipped on release-please branches, where it runs on all three OSes; see Continuous Integration).

**UAC relaunch under entry points:** `_elevation_launch_args(__name__, sys.argv[0])` in `setup_environment.py` relaunches elevation via `-m <package>.cli setup` when the module runs from an installed package with a non-`.py` `argv[0]` (a console-script shim `python.exe` cannot re-run); every direct-script invocation keeps relaunching through `sys.argv[0]`.

**Publishing:** `.github/workflows/publish.yml` (same pattern as mcp-context-server) triggers on `release: published`; a `build` job (checkout defaults to the release tag, `uv build`, version assert, artifact upload) is permission-isolated from a `publish-to-pypi` job (`id-token: write`, `environment: pypi`, `pypa/gh-action-pypi-publish` with trusted publishing). The PyPI trusted publisher is registered against workflow `publish.yml`, environment `pypi`.

### Node.js Compatibility

`ensure_nodejs(check_claude_compat=True)` checks Node.js v25+ SlowBuffer incompatibility for npm Claude Code; `False` checks only minimum >= 18.0.0. `install_claude.py` uses `True`; `setup_environment.py` uses `False` (needs Node.js for MCP servers/npx, not Claude Code).

`CLAUDE_NPM_SLOWBUFFER_FIXED_VERSION`: when `None` (default), v25+ always rejected; when set to a version string, v25+ accepted if installed Claude Code npm version meets threshold. Monitor [#9628](https://github.com/anthropics/claude-code/issues/9628).

**LTS-line upgrade (Step 5):** with `install-nodejs: true`, `_run_setup()` decides `plan_node_upgrade()` once, right after the scheduled-update plan and before `request_admin_elevation_if_needed()`, for a run whose Step 5 has the Node.js step (`runs_nodejs_step`: not a dependent that leaves the work to its source) or whose stale source it refreshes first (`source_runs_nodejs_step`, from `SourceRefresh.snapshot`); the one `NodeUpgradePlan` drives the summary (`InstallationPlan.node_upgrade`, `summary_lines()`), the elevation reasons (`elevation_reason()`), the machine-wide writes (`machine_wide_row()`), Step 5 and the completion summary. `_locate_node()` finds the node Step 5 checks without changing PATH (`%ProgramFiles%\nodejs` first on Windows when it exists and PATH lacks it, the rule `_prepend_windows_nodejs_dir()` applies in Step 5 and `_ensure_nodejs()`) and resolves it through `os.path.realpath`. Without a node, without a version, or below `MIN_NODE_VERSION` the plan is `install` (`_node_install_plan()`), whose `installs` names what Step 5's `_ensure_nodejs(homebrew_formula=...)` tries, in order, for the summary and the machine-wide row (`install_text()`): winget's `OpenJS.NodeJS.LTS`, then the official MSI of the newest LTS release, on Windows; on macOS the `homebrew_formula` that `_homebrew_node_formula()` picks -- it reads the schedule and `NODE_HOMEBREW_FORMULA_URL` for each supported line, newest first, and takes the first `node@<major>` Homebrew answers (HTTP 404: not carried yet; an unreadable document, or none carried, skips Homebrew with the reason inside the `installs` entry) -- installed and linked by `_install_nodejs_homebrew()` (Homebrew itself first when `_check_homebrew_available()` is false), then the official installer package; the NodeSource LTS repository on Debian and Ubuntu; nothing elsewhere (empty `installs`, no machine-wide row). Otherwise `_fetch_node_release_json()` reads `NODE_RELEASE_INDEX_URL` and `NODE_RELEASE_SCHEDULE_URL` (an unreadable one is an `unchanged` plan with the reason, exit status unaffected); `_node_release_lines()` and `NodeReleaseLine.supported()` (`lts <= today < end`, today from `_node_release_today()`) decide the line, and `_node_line_unsupported_reason()` names an odd, end-of-life, not-yet-LTS or unlisted line with the active LTS line (`unchanged`). The newest release of the line (`_newest_node_releases()`) equal to the installed one is `current`; a newer active LTS line only adds `notice` (`Node.js 26 is the active LTS line; 24 is supported until 2028-04-30`). An older release goes to `_node_installation_owner()`: a `NODE_VERSION_MANAGERS` entry (nvm, nvm-windows, fnm, volta, asdf, mise: a path component of the executable or its real path, or the directory its root variable names; the plan's `remedy` is the manager's command) and an unrecognized location (a distribution's nodejs package, Homebrew's unversioned `node` formula, anything else) are `unchanged`; the upgrade channels are `windows-msi` (real path in `_windows_nodejs_dir()`: `_winget_nodejs_command('upgrade', '--version', X)`, falling back to the MSI of X; `needs_elevation`), `homebrew` (`Cellar/node@<major>`: `brew upgrade node@<major>`), `macos-pkg` (`/usr/local/bin/node` on macOS: the `node-vX.pkg` through `sudo installer`) and `nodesource` (`/usr/bin/node` on Debian or Ubuntu whose `dpkg-query` version names nodesource: `apt-get update` and `apt-get install --only-upgrade -y nodejs` with sudo). `_upgrade_nodejs()` re-reads the version first (already at the target: current), skips with the `remedy` when the plan needs elevation and `is_admin()` is false or when sudo cannot run (no failure), runs the channel, and checks `node --version` again: a channel failure, or an exact channel (`windows-msi`, `macos-pkg`) reporting another release, is `NodeStepResult.failure` with `retry` (the run continues, the errors block lists `The Node.js upgrade failed:`, exit 1); Homebrew or NodeSource without the newest release yet is a warning; a node that no longer runs makes `available` false and the run raises like a failed install. `main()` marks a plan `elevation_unavailable` (`replace()`) under `--no-admin` without administrator rights; `performs_upgrade` (an `upgrade` not so marked) decides both the summary's `skipped:` line and whether `machine_wide_row()` lists the upgrade, so the summary never names a skipped upgrade among the machine-wide writes. Every command that changes the Node.js installation (winget, msiexec, the macOS installer, brew, apt-get, the NodeSource script) runs through `_run_nodejs_command()`, and the official installers download through `_download_nodejs_installer()`. `tests/conftest.py`'s autouse `_mock_node_upgrade_planning` makes unit tests plan `install`; `tests/test_setup_environment_nodejs_upgrade.py` and `tests/test_setup_environment_nodejs_install.py` call the planner captured at import time. `tests/e2e/conftest.py`'s autouse `node_command_recorder` (with `tests/e2e/node_upgrade_support.py`, also applied by `tests/e2e/fixtures/setup_child.py`) serves the release documents from `tests/e2e/fixtures/nodejs/` (Homebrew's formulae from its `homebrew/` directory, HTTP 404 for a formula without one) against a fixed day, counts a node outside the pytest base temporary directory as absent, and records every command and download; `tests/e2e/test_nodejs_lts_upgrade.py` drives the upgrade through `main()` against a stub official Windows installation (a `PROGRAMFILES` in the temporary directory and a winget entry) and a stub Homebrew `node@24` keg elsewhere.

**Shadowing global-prefix npm:** Step 5 of `setup_environment.py` calls `report_shadowing_global_npm()` right after `install_nodejs_if_requested()`, on every run whether or not `install-nodejs` is set, so it runs before the Step 6 dependency commands (Step 1's installer may already have run npm to detect, migrate or install an npm-installed Claude Code). `find_shadowing_global_npm()` reads the version of the npm the Node.js on PATH bundles (`_bundled_npm_dir()`: `<node dir>/node_modules/npm` on Windows, `<node dir>/../lib/node_modules/npm` elsewhere), runs `npm --version`, and only when that reports an older version runs `npm config get prefix`; it returns a `ShadowingNpm` when the global-prefix copy (`_global_prefix_npm_dir()`: `<prefix>/node_modules/npm` on Windows, `<prefix>/lib/node_modules/npm` elsewhere) declares exactly the reported version. The npm.cmd shim of Node.js runs that copy whenever `<prefix>\node_modules\npm\bin\npm-cli.js` exists, and on Linux and macOS it runs when `<prefix>/bin` precedes the Node.js bin directory on PATH. The probes go through `run_command()` with `NPM_PROBE_TIMEOUT_SECONDS` (30) and `NPM_PROBE_ENVIRONMENT` (`NPM_CONFIG_UPDATE_NOTIFIER=false`, `NPM_CONFIG_LOGS_MAX=0`: no registry query, no debug log). `ShadowingNpm.lines()` (both versions, both package directories, `npm uninstall -g npm` and `npm install -g npm@<bundled>`) prints in Step 5 through `print_shadowing_npm_warning()` and again in the completion summary or the "Setup Completed with Errors" block; setup changes neither copy, and a value it cannot determine (no node on PATH, no or unreadable bundled `package.json`, npm missing, failing, timing out, or the older npm not being the prefix copy) yields no warning and leaves the run's outcome alone. `tests/conftest.py`'s autouse `_mock_npm_shadowing_check` replaces the finder in unit tests because it runs the machine's npm; `tests/e2e/test_npm_shadowing.py` runs it through `main()` against layouts built by `tests/e2e/npm_layout_support.py` from `EXPECTED_NPM_LAYOUT`, and against the machine's own Node.js with a copy of its bundled npm in a test-owned prefix.

### Root Detection Guard

All Linux/macOS scripts refuse to run as root/sudo by default (`id -u == 0` in shell, `os.geteuid() == 0` in Python). Applies to all 6 entry points. Override: `CLAUDE_CODE_TOOLBOX_ALLOW_ROOT=1` (only exact value `1`; `true`/`yes` do NOT work). Rationale: root creates config under `/root/` instead of user's home. Use override for Docker/CI environments.

### Single Interface Invariant (Scripts, CLI, Wrappers)

The standalone Python scripts, the `cc-toolbox` CLI, and the platform bootstrap wrappers expose ONE interface: identical flags, identical environment variables, identical behavior. The wrappers forward ALL user arguments to `setup_environment.py` verbatim -- no allowlists, no wrapper-built flags, and `CLAUDE_CODE_TOOLBOX_ENV_CONFIG` never placed on the command line, because `resolve_args()` reads the variable through `ENV_TWINS` and records `origins['config']` as `env`, which the switch guard's remedy and the `--profile all` conflict message depend on. The wrappers only check that a configuration is present (a non-flag first argument, else the variable, the precedence argparse applies) and run without one when `--profile` (or `--profile=NAME`) is among the arguments or `CLAUDE_CODE_TOOLBOX_PROFILE` is set, because a `--profile` re-run reads its configuration from the manifest. Anything expressible in one entry path MUST be expressible identically in every other, and any interface change lands in all entry paths (Python scripts, `cli.py`, all three wrappers, docs) in the same PR.

**Present-tense only, no backward compatibility:** code, comments, docstrings, and docs describe ONLY the current interface -- never prior behavior, removed elements, migrations, or compatibility notes. Superseded interface elements are deleted outright, never kept as shims, aliases, or deprecated fallbacks. The conventional commit message is the only record of change.

### Installation Confirmation

The setup script requires explicit user confirmation before installing. CLI flags: `--yes`/`-y` (auto-confirm), `--dry-run` (preview and exit), `--skip-install` (skip Claude Code installation), `--no-admin` (skip Windows admin elevation), `--command-names NAME[,ALIAS...]` (install as the isolated profile `~/.claude/NAME` under these command names, `NAME,none` under the one command; see Command names below), `--profile NAME` (re-run the installed profile NAME from its manifest with no configuration argument; `base` for the base profile, `all` for every installed profile, each as a child run with `--yes`, the hidden `--child-run` and, outside `--dry-run`, `--no-admin`, after the parent decided Windows elevation once for all of them), `--switch-config` (accept a different configuration for an existing profile and remove its leftovers as `--remove-leftovers` does), `--remove-leftovers` (remove in Step 23 what earlier runs installed and the configuration no longer installs; `--profile all`, a source's Step 24 and the refresh of a stale source hand it to every child in argv, and a scheduled run switches it off; see Leftovers of earlier runs below), `--link-dirs ENTRIES` and `--link-from SOURCE` (take entries of the isolated profile through a directory link from another profile; see Profile links below), `--run-all-commands` (make a profile that links content from a source install Claude Code, the IDE extension and Node.js and run every dependency command itself instead of leaving the work its source's run does for the machine to that run; see Profile links below), `--env KEY=VALUE` (repeatable; sets an environment variable for the run before any env read, identically in every shell, and is forwarded through UAC elevation). ### Environment Configuration System

YAML configs define complete environments: dependencies, agents, MCP servers, slash commands, system prompts (append/replace modes), hooks, OS environment variables, user settings (`settings.json` content via `user-settings`), global config (`~/.claude.json` via `global-config`), and selective inheritance via `merge-keys` directive.

**List Inherit (`inherit: [list]`):** `inherit` accepts `str | list[str | InheritEntry] | None`. Single-element plain-string lists normalize to string (recursive resolution -- the entry's own `inherit` IS resolved). Single-element structured lists (`[{config: ..., merge-keys: [...]}]`) route to `_resolve_list_inherit()` (composition mode). Multi-element lists use flat left-to-right composition via `_resolve_list_inherit()`. Four mandatory rules:

1. **Own inherit stripped (Rule 1):** Each listed file's own `inherit` key is completely ignored in list composition mode. Users must explicitly include all configs in the desired order.
2. **Separate-file equivalence (Rule 2):** `inherit: [A, B, C]` behaves identically to a virtual chain where C inherits B which inherits A. First entry = base (lowest priority), last entry overrides earlier ones, leaf overrides everything.
3. **Own merge-keys stripped, per-entry from leaf (Rule 3):** Each listed file's own `merge-keys` key is stripped and ignored. Per-entry merge-keys are specified in the leaf config using structured `{config: ..., merge-keys: [...]}` entries. merge-keys are a property of the relationship between the leaf and each listed entry, not an intrinsic property of the listed config.
4. **Leaf merge-keys for final step (Rule 4):** The leaf config's top-level `merge-keys` applies to the final composition step (leaf on top of accumulated base). Orthogonal to per-entry merge-keys.

`_validate_merge_keys()` is a DRY helper extracted from the former inline validation, reused for both leaf and per-entry merge-keys validation. `InheritEntry` is a Pydantic model (`config: str`, `merge_keys: list[str] | None` with alias `merge-keys`, `extra='forbid'`) containing an inline `mergeable` frozenset (DRY violation covered by parity test `test_mergeable_config_keys_parity.py`). `_resolve_list_inherit()` threads `auth_param` through `load_config_from_source()` for each entry, extends the existing `visited` set for circular dependency detection, and builds `InheritanceChainEntry` entries for each loaded config.

**Env Loader Files:** `generate_env_loader_files()` creates Rustup-style shell scripts containing the `os-env-variables` of an isolated run (distinct from the session-scoped `user-settings.env` written into `config.json`). Per-command files in the profile directory (`~/.claude/{cmd}/` by default): `env.sh`, `env.fish` (if Fish installed), `env.ps1` (Windows), `env.cmd` (Windows). Files are generated only when `command_names` is provided; without `command_names`, the function returns `{}`. A `None`-valued (deletion) entry is rendered as an unset line in each shell's syntax (`unset NAME`, `set -q NAME; and set -e NAME`, `Remove-Item -Path Env:NAME -ErrorAction SilentlyContinue`, `SET "NAME="`), so a value the profile's sessions inherit from the OS environment is removed at session start. Loader files are toolbox-owned and rebuilt on every run, header-only when the dict is empty, so stale lines from a prior run stop being applied by the launcher. `main()` Step 7 first splits the resolved `os-env-variables` with `partition_os_env_variables(os_env_variables, isolated=...)`: a base run hands every entry to `set_all_os_env_variables()` (shell profiles, Windows registry) and generates no loader; an isolated run hands ONLY the `MACHINE_WIDE_ENV_CONTROLS` entries (`DISABLE_AUTOUPDATER`, `DISABLE_UPDATES`, `CLAUDE_CODE_IDE_SKIP_AUTO_INSTALL` -- the controls holding the one Claude Code binary, built from `AUTO_UPDATE_ENV_CONTROLS` plus `IDE_SKIP_AUTO_INSTALL_KEY` and read by every place that handles the three together) to the OS writer and every other entry, nulls included, to `generate_env_loader_files()`. A machine-wide control never enters a loader file: an unset line there would strip the control from the profile's sessions after another profile pinned a version. Only `launch.sh` applies a loader: `create_launcher_script()` puts the guarded `env.sh` source line into every `launch.sh` variant (Windows and Unix, with and without a prompt), so the bash process that `exec`s Claude Code receives the sets and unsets, and every entry point reaches a session through `launch.sh`. `start.cmd`, `start.ps1` and the `~/.local/bin` `.cmd`/`.ps1` wrappers reference no loader: a batch file executes inside the cmd.exe that calls it and `$env:` is process-wide in PowerShell, so a loader applied there would stay in the window after the session ends and reach a plain `claude` started next; the `.cmd` files also run under `setlocal`, so the calling shell's environment is left exactly as it was. `tests/e2e/test_profile_confinement.py::TestWindowsEntryPointsLeaveTheCallingShellAlone` runs each entry point under cmd.exe and PowerShell, compares the caller's environment before and after, and reads what a stub `claude` recorded for the session. `env.cmd`, `env.ps1` and `env.fish` are generated for sourcing by hand.

**Fish Dual-Mechanism:** `set_os_env_variable_unix()` writes `set -gx` to `config.fish` (durable persistence) AND calls `set -Ux` via subprocess (instant propagation to all running Fish sessions). For deletions, `set -Ue` removes the universal variable. The `config.fish` write is authoritative; `set -Ux` is complementary.

**WM_SETTINGCHANGE Broadcast:** `_broadcast_wm_settingchange()` in `setup_environment.py` uses the dummy `setx CLAUDE_CODE_TOOLBOX_TEMP temp` + `reg delete` pattern to trigger `WM_SETTINGCHANGE`. Called from `add_directory_to_windows_path()`, `cleanup_temp_paths_from_registry()`, `set_os_env_variable_windows()` (after `reg delete` for deletions), and `set_all_os_env_variables()` (batch broadcast after all operations). `install_claude.py` has its own independent copy at `ensure_local_bin_in_path_windows()` (standalone script policy).

### Component Selection (`components`)

The top-level `components:` key defines author-controlled selectable groups of items from `SELECTABLE_SECTIONS = {agents, slash-commands, rules, skills, files-to-download, mcp-servers, dependencies, hooks}` (byte-identical frozensets in `setup_environment.py` and `environment_config.py`; parity enforced by `tests/scripts/models/test_selectable_sections_parity.py`, which also locks the model's `_download_selector_identity` to the runtime's `_files_download_identity`). An item claimed by at least one component installs only when a selected component claims it; unclaimed items are mandatory and never appear in any picker. `components` is a `KNOWN_CONFIG_KEYS` member and the 12th `MERGEABLE_CONFIG_KEYS` entry (merged by `name` via `_merge_named_list`/`_name_identity`).

**Selector identities** mirror each section's merge identity: exact string (agents/slash-commands/rules/dependencies across all platform lists), entry `name` (skills/mcp-servers), dual key `dest` OR normalized final path (files-to-download; distinct entries sharing a final path are a fail-fast error because they make selectors ambiguous), and `hooks.events[].id` or a `hooks.files` path (hooks). `hooks.events[].id` exists solely as a selector identity; `_build_hooks_json()` is a whitelist builder, so the id never reaches generated JSON (regression: `TestHookIdNotInGeneratedJson`). Both validation layers strip whitespace on both sides of the comparison. A config declaring `inherit` is model-validated WITHOUT the cross-reference checks (selector resolution, `requires`/`bundles` references, duplicate final-path) because its full item set exists only post-resolution; the runtime twin enforces them on the resolved config. Within-file invariants (duplicate names, duplicate hook ids) stay enforced on every file.

**Resolution** happens ONCE at the single choke point in `main()`: after inheritance resolution, BEFORE `request_admin_elevation_if_needed()` and remote file validation, so deselected items never trigger UAC elevation, network fetches, or auth prompts. Sequence: `validate_components()` (runtime twin of the Pydantic validation; emits the hook-claim asymmetry warning), `validate_hooks_files_consistency()` (runtime twin of the model validator of the same name), and `validate_status_line()` (runtime twin of the `StatusLine` field validation; the three error lists print together before a single exit 1) → `_validate_component_selector_args()` → `--list-components` exit → `resolve_component_selection()` → `apply_component_selection()` (in-place filter; section keys never deleted) → post-selection `validate_hooks_files_consistency(config, require_all_files_used=False, declared_files=...)` recheck (a deselection-stranded event/status-line reference exits 1 with guidance, an exec-form event naming a dropped script included: `declared_files` is `configured_hook_files()` of the configuration taken before the filter, so a command naming a script the selection dropped stays a dangling reference instead of passing as a program on PATH; `replay_source_snapshot()` rechecks a replayed selection the same way; unused files are tolerated residue covered by the asymmetry warning). The algorithm: author defaults (`default: true` when omitted) → `--select` (sentinels `all`/`none`) → `--with` → soft `_bundle_closure` → `--without` → interactive picker → hard `_requires_closure` (BFS over registry-ordered seeds so `[auto: required by '...']` cause attribution is deterministic; wins over `--without` with a warning). CLI flags `--select`/`--with`/`--without`/`--list-components` have `CLAUDE_CODE_TOOLBOX_SELECT`/`_WITH`/`_WITHOUT` env fallbacks in `resolve_args()`. A profile's manifest remembers the delta a run typed or took from the environment (`ComponentSelection.delta`/`origin`/`remembered`/`defaults`; a picker choice that changed the seed is recorded as typed), and `apply_remembered_component_delta()` feeds it to a later run that gives no selector, so a `--yes` re-run keeps the components instead of deselecting them; the summary's `Components:` header carries the origin marker. The resolved `ComponentSelection` threads into `collect_installation_plan(selection=...)` and renders a summary Components block with `[x]`/`[ ]` rows and a copy-pasteable replay line (`--select` plus `--without` for skipped components, so bundle edges do not re-add deselected targets on replay). `collect_deselected_items()` captures the removal plan from the UNFILTERED config at the same choke point (an item is deselected when claimed by at least one component and kept by none of the selected ones; dependencies excluded as irreversible); the plan threads into the summary as `[REMOVE]` rows (`deselected=`/`deselected_items`) and executes as Step 23 of both branches (`execute_deselection_cleanup()`, followed by the Step 24 dependent refresh): `claude mcp remove` per non-profile scope, deletion of deselected skill dirs and agent/command/rule/hook/downloaded files (installer-mirroring path resolution, absent targets skipped silently, nothing inside a linked entry), and `_strip_hooks_from_settings()` reconciliation of the shared `settings.json` hook union, which rebuilds the deselected events with `_build_hooks_json()` against the configuration's full `hooks.files` list (`hook_files=`: the surviving entries plus the deselected ones, so an exec-form hook naming a listed script is rebuilt exactly as it was written) and removes matching entries via `_hook_entries_equal()` (quote-insensitive on file-reference commands so pre-quoting installs still match, exact on everything else; non-isolated only; the isolated `config.json` is rebuilt atomically each run).

**Picker** (`prompt_component_selection()`): Tier 1 questionary checkbox (lazy import), Tier 2 numbered toggle loop via `_read_user_input()` on ImportError OR any console exception (mintty's `NoConsoleScreenBufferError` is not an `OSError` — the catch is deliberately broad), Tier 3 returns `None` keeping the non-interactive set. Queued terminal input is flushed via `_flush_pending_terminal_input()` twice: once before the tiers, and again at the numbered picker's entry, because the questionary tier can fail mid-render with its own terminal query replies still queued and an empty first line would silently confirm the untouched seed; in-loop iterations stay flush-free so type-ahead between toggle prompts survives, and an all-garbage line surfaces as the contaminated-input marker (invalid input, re-prompt) rather than an Enter. Ctrl-C cancels with exit 0 in BOTH interactive tiers: `_read_user_input()` propagates `KeyboardInterrupt` while its `_get_user_confirmation()` wrapper converts it to `''` (deny) for confirmation prompts. Runs only when no selector flag is given, neither `--yes` nor `--dry-run` is set, and a TTY (or `/dev/tty`) is available; prints its own two-line context banner because `header()` renders later. `questionary` is declared in THREE places: the PEP 723 block of `setup_environment.py` (standalone `uv run` path), `[project].dependencies` (wheel/`uvx` path), and `[dependency-groups].dev` (`uv run pytest` provisions from pyproject, not the PEP 723 header).

### Global Config (`global-config`)

Writes exactly one file, resolved by `global_config_target_file(artifact_base_dir)`: `~/.claude.json` for a base run, `~/.claude/{cmd}/.claude.json` for an isolated run (Claude Code CLI resolves `getGlobalClaudeFile()` via `CLAUDE_CONFIG_DIR` with no fallback, and the base file belongs to the base profile). The `global-config` write of an isolated run never touches the base file (the base file receives only the `installMethod` record of the Step 1 installer), so a configuration whose `global-config` deletes `oauthAccount` or `userID` signs out only the profile it installs. Arrays merge differently per layer. The writer (`write_global_config()` -> `_write_merged_json()`, the helper `write_user_settings()` shares) deep-merges into the target file and unions every array at every depth with the array that file already holds (existing elements first, new ones appended, structural dedupe), because the CLI keeps its own arrays there: a YAML array only adds elements, and `key: null` deletes the whole key. The `inherit` layer with `merge-keys: [global-config]` (`_merge_config_key()` -> `deep_merge_settings(array_union_keys=set(), preserve_nulls=True)`) deep-merges objects but lets a child array replace the parent's at every depth; without `merge-keys` the child's section replaces the parent's whole. Against `user-settings`: its `inherit` layer unions `permissions.allow/deny/ask` (`DEFAULT_ARRAY_UNION_KEYS`) and replaces every other array, its base-mode writer unions every array in `~/.claude/settings.json` exactly as above, and its isolated `config.json` is rebuilt from the resolved YAML each run, so the arrays there are exactly the resolved ones. Only `oauthAccount` blocked from non-null values (`GLOBAL_CONFIG_EXCLUDED_KEYS`); `null` allowed for clearing OAuth. `install_claude.py`'s `update_install_method_config()` also writes to `~/.claude.json` via the same read-merge-write pattern (values `'native'`/`'global'`/`'winget'` -- see Native Claude Code Installation Support).

**installMethod propagation:** `_propagate_install_method()` runs at Step 15 just before `write_global_config()`. When `command-names` creates an isolated environment, it reads `installMethod` from the base `~/.claude.json` and injects it into `global-config` (creating the dict when the YAML lacks the section, so the empty-config short-circuit does not skip the Step 15 write), letting the Step 15 write carry the machine-baseline value to the isolated `.claude.json`; the base file is read, never written. WARN-but-Respect: a user-declared YAML `installMethod` wins with a warning when it differs; when the base file or key is absent (or the base JSON is invalid), nothing is propagated. Because propagation runs at Step 15 -- after the pre-confirmation summary has rendered and after Claude Code is installed (so the base `installMethod` exists) -- the propagated value is announced with an `info()` message at injection time and appended to the run's auto-injected list for the record, rather than shown in the pre-confirmation summary.

**Profile-confined writes:** an isolated run writes inside its profile directory and nowhere else, apart from the machine-wide items one machine holds once. `.claude.json` and `settings.json` are both single-write with scope-based routing: the CLI resolves `.claude.json` via `getGlobalClaudeFile()` and `settings.json` via `getClaudeConfigHomeDir()`, both under `CLAUDE_CONFIG_DIR` when it is set and under the home directory otherwise, with no fallback or inheritance, so each profile reads its own pair and a write into another profile's pair reaches nothing that profile's sessions use. The only base-file write an isolated run can cause is `installMethod` in `~/.claude.json`, recorded by `install_claude.py`'s `update_install_method_config()` when Step 1 installs, upgrades or migrates the binary. Every write that leaves the profile directory is named in the installation summary before consent: `collect_machine_wide_writes()` fills `InstallationPlan.machine_wide_writes` for an isolated run (the binary install or kept version with the `installMethod` record, a version pin, the IDE extension Step 2 installs at that pin -- `main()` passes the CLI names from the read-only `_detect_vscode_family_ides()` as `ide_clis` only under Step 2's own gate, pinned and not `--skip-install`, so the row names the detected IDEs and is absent when none is detected -- the Node.js installation or the upgrade Step 5 performs (`node_upgrade=`, `NodeUpgradePlan.machine_wide_row()`; no row for an upgrade `--no-admin` skips), each OS-level `MACHINE_WIDE_ENV_CONTROLS` set or deletion, the `~/.local/bin` wrappers, project-scope MCP servers in the working directory's `.mcp.json`, `files-to-download` destinations outside the profile, the dependency commands, and the leftover destinations outside `~/.claude` Step 23 removes under `--remove-leftovers`), rendered as a `Machine-wide writes` block with `[machine-wide]` rows; a base run's `OS environment variables` row is labeled `(machine-wide)` instead. `account_key_deletion_warnings(global_config, target_file, profile_label)` fills `InstallationPlan.account_key_warnings` when the resolved `global-config` sets a `GLOBAL_CONFIG_ACCOUNT_KEYS` member (`oauthAccount`, `userID`) to null and the `.claude.json` this run writes holds a non-null value for it; the warning names the profile and the file in the `[!] ATTENTION` block (and therefore in `--dry-run`), never prints the values, and blocks nothing. The final summary prints `Global config: configured in <target file>` and, for an isolated run, `User settings: built into <profile>/config.json` (Step 18 builds them into `config.json` while Step 14 skips the write); a base run prints `User settings: configured in ~/.claude/settings.json`. The sessions of an isolated profile read nothing from the base config home either, wherever they start (see Isolation from the base config home under Two-File Architecture). `tests/e2e/test_profile_confinement.py` drives every one of these cases through `main()`, sources the generated loaders for real (`env.sh` under bash on every platform, `env.cmd` and `env.ps1` on Windows, proving that a null entry removes a variable the session inherited), and runs the Windows entry points for real with the launchers and wrappers written by `main()` (see Env Loader Files); `tests/e2e/shells.py` holds the shared bash and PowerShell lookups those tests use.

**Re-rooting (isolated runs only):** `ConfigHomeReroot(profile_dir, home_dir, profile_names)` is the one function that moves base config-home paths into the profile; `rewrite(value)` substitutes `_CONFIG_HOME_PATTERN`, which matches a home token (`~`, `$HOME`, `${HOME}`, `"$HOME"`, `$env:USERPROFILE`, `%USERPROFILE%`; a lookbehind keeps a glued `foo~/.claude` out), a `/` or `\` separator, `.claude`, then a `~/.claude.json` sibling suffix (`.json`, `.json.backup`, `.json.corrupted.*`) or a boundary (a lookahead keeps `~/.claude-backup` and `~/.claudex` out). The replacement keeps the author's home token and separator and inserts the profile path below `.claude` when the profile directory lies below the home (`_relative_inside`), and spells the absolute profile directory otherwise, posix for `/` and Windows for `\`; a sibling becomes `<profile><sep>.claude<suffix>`. A path whose first component after `.claude` casefolds to one of `profile_names` -- this run's primary name plus every `installed_profiles()` directory name other than `base` -- is returned unchanged, which keeps another profile's directory as written and makes the rewrite idempotent; a path outside the config home never matches. `main()` builds the rerooter right after `target_config_dir` is known, because `compute_profile_leftovers()` runs before the rewrite and `planned_records(config, profile_dir, reroot=...)` passes it to `planned_profile_files()`, so the leftovers (and the switch guard that lists them) compare the previous records with the new configuration's files at their re-rooted paths; `reroot.apply(config, deselected)` then runs right after `resolved_config_snapshot()` (so `resolved-config.yaml` and `config_digest` keep the paths as authored and a re-run or a `--profile` run rewrites them again) and before `request_admin_elevation_if_needed()`, the summary, the installers and the manifest records. `apply()` rewrites in place every `files-to-download` dest, every command of every `dependencies` platform list, every `TILDE_EXPANSION_KEYS` value of `user-settings` (ahead of `_expand_tilde_keys_in_settings()`, so the Windows expansion lands inside the profile; on Windows through `rewrite_for_cmd()`, which double-quotes each word holding a re-rooted path, see Platform-Conditional Tilde Expansion in Settings), and the dests of the deselected `files-to-download` entries, so `execute_deselection_cleanup()`'s download-target resolution and the `[REMOVE]` row both name the profile file and the base copy survives; it returns one `RerootedPath(section, label, original, rewritten)` per rewritten configuration value (none for the removal plan), which `InstallationPlan.rerooted_paths` carries into the `Re-rooted into the profile (base config-home paths of an isolated run):` block of `[re-rooted]` rows (`_rerooted_path_line()`) and into a `[re-rooted]` marker on the matching `Dependencies (shell commands)` rows. A re-rooted dest lies inside the profile, so `planned_profile_files()` records it in `files_written`, `machine_wide_download_records()` and `collect_machine_wide_writes()` skip it, and `shared_destination_warnings()` never sees it. Right after `apply()`, `main()` runs `split_downloads_by_linked_entries(config['files-to-download'], target_config_dir, linked_entries)` ONCE on the rewritten destinations, before the summary, and Step 4 downloads only the kept entries: a destination inside a linked entry (`~/.claude/hooks/x.py` re-rooted into a linked `hooks/`) is left to the link, because the source's run wrote it into the shared directory and a write would go through the link into the source -- Step 4 prints `Skipping <dest>: <entry>/ is linked from profile "<source>"`, `planned_profile_files(linked_entries=...)` leaves it out of `files_written`, `InstallationPlan.linked_downloads` renders it as a `[linked]` row of the `Provided by links (files-to-download destinations inside linked entries, written by the source):` block (`_linked_download_line()`, the same text as the Step 4 line) in the summary and in `--dry-run`, and `plan.files_to_download` counts only the entries the run writes. A dependent's deselected entries go through the same `apply()` rewrite, so `execute_deselection_cleanup(linked_entries=...)` keeps a re-rooted target inside a linked entry; a re-rooted dependency command runs as before, a destination outside every linked entry is written as before, and a profile that links only `projects` writes everything it re-roots. A base run builds no rerooter. `tests/test_setup_environment_reroot.py` covers the pattern and the consumers; `tests/e2e/test_reroot_config_home.py` runs the real dependency commands in bash and PowerShell against the isolated home, so the rewritten `$HOME` and `$env:USERPROFILE` cleanup lines are seen to reach the profile and leave the base `~/.claude` tree and `~/.claude.json` byte-identical, and installs a source -- an isolated profile, and the base profile whose own run wrote the same destinations as written -- with a dependent linking `all`, `hooks` alone and `projects` alone (plus the Step 24 refresh of each source), where an edit made to the source's copy of the linked file survives the dependent's run; a dependent of the base may add only the empty link-target directories Step 3 creates for entries the base run never made.

**Null-as-delete (RFC 7396):** `null` values in `user-settings`/`global-config` delete the key from the target JSON. `_merge_recursive()` runs in two modes. The on-disk writers APPLY the patch: `target.pop(key, None)`, and a subtree landing on a key the file lacks (or on a non-object member) is merged into a fresh empty object, so `null` members at every depth are dropped and a literal JSON `null` is never written -- Claude Code copies a null `env` member into the process environment as the string `'null'`, so a leaked `ANTHROPIC_AUTH_TOKEN: null` would send the token `null`. The `inherit` layer COMPOSES patches (`preserve_nulls=True` in `_merge_config_key()` for `user-settings` and `global-config`, and the shallow `{**parent, **child}` merge for `os-env-variables`): a child `null` is stored as `None` so the deletion request reaches the writer even when the parent declared a value (applying the resolved config equals applying the parent and then the child). Null in arrays is NOT deletion. Bare YAML keys (`key:` with no value) also trigger deletion -- use `key: ""` for empty strings. Dry-run shows `[DELETE]` markers in RED. `user-settings.env` and `os-env-variables` values support the same convention (`dict[str, str | None]`): a null `user-settings.env` entry deletes the variable -- `create_profile_config()` strips per-key nulls before the atomic isolated `config.json` write (absence equals deletion; the literal JSON null is never written for env entries, and the `env` key is dropped entirely when every entry is null) while the base-mode merge writer deletes `env.VAR` from `~/.claude/settings.json` -- and a null `os-env-variables` entry deletes the OS-level variable.

### Two-File Architecture for Command Environments

When `command-names` is specified, the setup creates an isolated directory `~/.claude/{cmd}/` containing one toolbox-written configuration file delivered to Claude Code at the command-line settings layer:

| File          | Priority         | Content                                                                                                           | Write Mechanism                                |
|---------------|------------------|-------------------------------------------------------------------------------------------------------------------|------------------------------------------------|
| `config.json` | 2 (flagSettings) | YAML `user-settings` content, the base config home exclusions, and toolbox-built `statusLine` and `hooks` entries | Atomic overwrite via `create_profile_config()` |

The toolbox does NOT write `~/.claude/{cmd}/settings.json` in isolated mode. The `user-settings` section (raw `settings.json` keys with camelCase names) is merged directly into `config.json` by `create_profile_config()` alongside the `statusLine` and `hooks` entries built from the root-level YAML keys. The two sources are disjoint by construction: `statusLine` and `hooks` are rejected inside `user-settings`.

Scope-based routing: `command-names` presence in the final resolved config determines where `write_user_settings()` writes. Present: Step 14 prints an info message and skips the write (user settings are built into `config.json` in Step 18 instead). Absent: `write_user_settings()` deep-merges into `~/.claude/settings.json`. Never dual-write.

The launcher (`launch.sh`) passes `config.json` via `--settings` flag, passes `--strict-mcp-config --mcp-config=<mcp.json>` through the `MCP_FLAGS` bash array (one argument per element, so a path with spaces survives), passes `--setting-sources user` through the `SOURCES` array when the session starts in the home folder (see Home-folder settings guard below), and sets `export CLAUDE_CONFIG_DIR` to the isolated directory; every start puts these options first and the user's arguments last (see Argument order below).

**Isolation from the base config home:** Claude Code reads the working directory's `.claude` as the project settings of a session and the `.claude` of every directory above it as project memory, and the home folder's `.claude` IS the base profile. A session of an isolated profile started in the home folder would therefore take `~/.claude/settings.json` and `settings.local.json` as project settings (their `env`, `apiKeyHelper`, `model` and hooks all apply), a session started anywhere below the home loads `~/.claude/CLAUDE.md` and `~/.claude/rules/` as ancestor memory, and a session started inside `~/.claude` itself or inside the profile directory loads `~/.claude/CLAUDE.local.md` as well (the only start locations that reach it); project `.claude/skills`, `agents` and `commands` are not read from `~/.claude` (Claude Code skips the home folder's `.claude` for those), and a project's `settings.json` is read from the working directory only, never from an ancestor. Three mechanisms close every channel for every isolated profile, with no configuration change. (1) `apply_base_config_home_exclusions(user_settings, home_dir=..., links_rules_from_base=...)` runs in `main()` for an isolated run only, after `apply_skills_sync_settings()`, and unions `base_config_home_exclusions()` -- `<home>/.claude/CLAUDE.md`, `<home>/.claude/CLAUDE.local.md` and `<home>/.claude/rules/**`, spelled with forward slashes from `get_real_user_home()` and with every ASCII letter as a case class through `_letter_case_classes()` (`[cC]:/[uU][sS][eE][rR][sS]/...`), because Claude Code matches the patterns case-sensitively against paths it builds from the working directory as the shell spelled it: a session started below the home from `c:\Users\...` (cmd.exe keeps the drive letter it was given after `cd /d c:\...`) or from a path typed in another case would otherwise load the base files; on Windows `_config_home_spellings()` repeats the three patterns for the home's 8.3 short spelling (`_windows_short_path()`: `GetShortPathNameW` through `ctypes`; nothing is added when the call fails or when the short spelling equals the long one beyond letter case, and the other platforms never make the call), because Windows spells a home whose account name is longer than eight characters short in `%TEMP%` and `%TMP%` (`C:\Users\CHRIST~1\...`) and a session started under such a path hands Claude Code ancestor paths the long spelling misses, whether the components below the home are spelled long (the `%TEMP%` shape) or short; a working directory that spells a component above the home short while the home itself stays long (`C:\DOCUME~1\Me\...`) matches neither set and is the one spelling the patterns do not cover, which mechanism (3) closes for a launcher-started session, so only `claude` started without the launcher under such a path loads the base memory -- into `user-settings.claudeMdExcludes` (`CLAUDE_MD_EXCLUDES_KEY`): the configuration's own patterns stay first, only missing base patterns are appended, a declared non-list is replaced with a warning, and the added patterns show as one `[auto] user-settings.claudeMdExcludes: ...` line in the `Settings added by the setup:` block of the summary and `--dry-run`. Claude Code matches an exclusion against the target of a link too, so when the profile's `rules/` entry is linked from the base profile (`RULES_PROFILE_DIR in linked_entries and link_spec.source == LINK_SOURCE_BASE`) the rules pattern is left out under both spellings: the base rules are the profile's own rules then. The patterns never name the profile directory (`~/.claude/<name>/...`, or a directory a `user-settings.env` `CLAUDE_CONFIG_DIR` relocates it to), so the profile's own `CLAUDE.md` and rules keep loading, as do a project's `CLAUDE.md`, `CLAUDE.local.md`, `.claude/CLAUDE.md` and `.claude/rules` below the home. `resolved-config.yaml` is snapshotted before the injection, so a dependent computes its own exclusions. (2) `launch.sh` passes `--setting-sources user` when the session starts in the home folder (see Home-folder settings guard), which keeps `~/.claude/settings.json` and `settings.local.json` out while the profile's own `settings.json`, the `--settings config.json`, `--mcp-config` and the system prompt still apply. Claude Code offers no settings source finer than `project` (settings, memory and `.mcp.json` together), so the same flag keeps the home folder's own `~/CLAUDE.md`, `~/CLAUDE.local.md` and `~/.mcp.json` out of a session started in the home folder itself, where the home folder is the project; those three files lie outside the base config home and load below the home as the home folder's own project files (a profile with profile-scoped MCP servers runs with `--strict-mcp-config` and reads no `.mcp.json` anywhere). (3) Claude Code tells the home folder's `.claude` apart from a project's `.claude` by spelling (letter case aside) when it skips it for project skills, agents and commands, so a session started under the home's 8.3 short spelling loads the base profile's `skills/`, `agents/` and `commands/` as a project's, and no exclusion setting reaches them; every Windows `launch.sh` therefore runs `WINDOWS_WORKING_DIRECTORY_SPELLING_GUARD` before the home-folder guard (see Working-directory spelling guard), which changes to the long spelling of the working directory, so Claude Code receives the working directory spelled long whatever spelling the shell handed the launcher and skips the base profile's directories as it does below a home spelled long. A session started with `claude` itself under the short spelling has the short spelling's patterns as its only protection: the base memory stays out, the base skills, agents and commands load; under a spelling that shortens only a component above the home, the base memory loads as well. A base run injects nothing. A session started inside `~/.claude` itself or inside the profile directory reads that directory as its project and the exclusions cover both; a session started inside another profile's directory reads that profile's `CLAUDE.md` as the project's. Unit tests: `tests/test_setup_environment_base_home_isolation.py`; E2E: `tests/e2e/test_base_home_isolation_settings.py` (through `main()`), `tests/e2e/test_launcher_home_folder_guard.py` and `tests/e2e/test_launcher_working_directory.py` (every entry point with a stub `claude`) and `tests/e2e/test_real_binary_base_home_isolation.py` (the real binary, see Real-binary modules).

**Launcher and wrapper paths:** `create_launcher_script()` and `register_global_command()` spell every path a launcher or wrapper reads (the exported `CLAUDE_CONFIG_DIR`, `config.json`, `mcp.json`, the system prompt, the `env.sh` loader, `launch.sh`) from the profile directory `artifact_base_dir`, which a `user-settings.env` `CLAUDE_CONFIG_DIR` can move out of `~/.claude/{cmd}`. `_spell_profile_dir()` returns the bash, CMD and PowerShell spellings: home-relative (`$HOME/...`, `%USERPROFILE%\...`, `Join-Path $env:USERPROFILE "..."`) when the directory lies below `get_real_user_home()` -- compared component-wise with `os.path.normcase`, so Windows casing does not matter -- so the scripts follow the home each shell resolves at run time, and absolute otherwise (mixed `C:/...` form for bash on Windows). Literal components go through `_escape_bash_double_quoted()`, `_escape_cmd_set_value()` (also used by the env loaders) and `_escape_powershell_double_quoted()`. The launchers and the CMD and Git Bash global commands use those spellings; the PowerShell global commands (`~/.local/bin/{cmd}.ps1` and one per alias) name `start.ps1` by its absolute path, and the Unix global commands are symlinks to the absolute `launch.sh`. The default `~/.claude/{cmd}` renders byte-for-byte as `tests/e2e/expected/launchers.py` pins, and `tests/e2e/test_launcher_profile_paths.py` plus `tests/e2e/test_relocated_profile_setup.py` run every launcher and wrapper of relocated profiles (directly below, deeper below and outside the home, with spaces, and on Windows with the home written in other letter case) under bash, cmd.exe and PowerShell with a stub `claude`.

**Argument order:** every line of every `launch.sh` variant (Windows and Unix; no prompt, replace and append; every `HAS_CONTINUE` and version branch) that starts a session runs `claude "${MCP_FLAGS[@]}" "${SOURCES[@]}" [prompt flag] --settings "$SETTINGS..." "$@"`: the profile's options first, the user's arguments last. Claude Code's option parser reads an option placed before a subcommand as a root option and one placed after it as the subcommand's own, so `<profile> mcp add -s user -t http NAME URL` and every other subcommand (`mcp`, `plugin`, `doctor`, `auth`, `update`, `agents`, ...) receive every profile option as a root option and run with the profile's `config.json` and `CLAUDE_CONFIG_DIR`. `MCP_FLAGS` spells the config as `--mcp-config=<path>`, so the variadic option ends at its own value and never takes a user argument (a positional prompt, a subcommand name) as another config file. A user option with the same name as a launcher option comes later and wins, and nothing warns about it: a user `--settings FILE` replaces the profile's `config.json` for that run (its hooks, `statusLine`, `env`, permissions and the `claudeMdExcludes` base-home exclusions with it), a user `--setting-sources` replaces `SOURCES`, and a user `--system-prompt-file` or `--append-system-prompt-file` replaces the profile's file of the same name. `--mcp-config` is the exception: Claude Code loads every config it is given, so a user's MCP config adds to the profile's `mcp.json`. A `--system-prompt` beside the profile's `--system-prompt-file` (or `--append-system-prompt` beside `--append-system-prompt-file`) is refused by Claude Code with `Cannot use both ...`. `FIRST_ARGUMENT_COMMANDS_GUARD`, rendered by `FirstArgumentCommands.render_guard()` from the one definition `CLAUDE_FIRST_ARGUMENT_COMMANDS`, runs in every variant after the env loader, the `CLAUDE_CONFIG_DIR` export and the guards (Windows: working-directory spelling, home folder, slash arguments; Unix: home folder) and before the prompt check, the version detection and every start with the profile's options. Claude Code dispatches some commands before its option parser runs, only when they open its command line, and behind any option their words become a prompt or are refused: `logs`, `attach`, `stop`, `kill`, `respawn`, `rm`; `remote-control`, `rc`, `remote`, `sync`, `bridge`; `self-hosted-runner`; `plugin test`; `daemon`, also after any number of `--dangerously-skip-permissions` and `--allow-dangerously-skip-permissions`; `--update` or `--upgrade` only as the sole argument. For those the guard runs `exec claude "$@"` with no profile option, so such a command runs with the env loader and `CLAUDE_CONFIG_DIR` but without the profile's `config.json`, system prompt and MCP flags (Claude Code does not carry `--settings` over to the sessions Remote Control starts and refuses to start Remote Control behind it). `--bg` and `--background` are found anywhere on the command line, so they keep the profile's options: Claude Code hands the background session its whole command line minus `--bg`, `--background` and `--session-id`, and `CLAUDE_CONFIG_DIR` in its environment; no test starts a background session. `validate_launcher_passes_caller_arguments_last()`, which `validate_launcher_script()` runs on every `launch.sh`, checks that the guard runs once before every other start, that each other start ends with `"$@"` after `--settings`, and the `--mcp-config=` spelling. Unit tests: `tests/test_setup_environment_launcher_first_argument.py` (the guard under bash for every form and near miss); E2E: `tests/e2e/test_launcher_subcommands.py` (every entry point and both renderings with a stub `claude`) and `tests/e2e/test_real_binary_launcher_subcommands.py` (see Real-binary modules).

**Home-folder settings guard:** every `launch.sh` variant (Windows and Unix, with and without a prompt) runs `HOME_FOLDER_SETTINGS_GUARD` right after the MCP block: `SOURCES=()`, then `SOURCES=(--setting-sources user)` when `[ "$PWD" -ef "$HOME" ]`, and every line that starts claude with the profile's options passes `"${MCP_FLAGS[@]}" "${SOURCES[@]}"` ahead of the prompt flag, `--settings` and the user's `"$@"`, so a `--setting-sources` the user passes comes later and wins (see Argument order). ### Platform-Conditional Tilde Expansion in Settings

`_expand_tilde_keys_in_settings()` handles tilde (`~`) paths in settings keys defined in `TILDE_EXPANSION_KEYS` (`apiKeyHelper`, `awsCredentialExport`), for the base `settings.json` (Step 14, `write_user_settings()`) and the isolated `config.json` (Step 18, `create_profile_config()`) alike:

- **Windows:** Claude Code runs both values through cmd.exe (`cmd.exe /d /s /c "<value>"`), which resolves no `~`, so `expand_tildes_for_cmd()` expands every tilde path to an absolute path. It reads the value as cmd.exe does, as the double-quoted runs found from the left and the text between them (`_map_cmd_line()`): a tilde path outside double quotes is double-quoted from the tilde to the end of its argument (`--config=~/x` becomes `--config="C:\...\x"`); a quoted run that opens with a tilde is one path, its spaces included, and expands whole up to its closing quote (`_expand_quoted_run()`); a tilde further inside a quoted run expands in place; a path inside double quotes gains no quotes. Every expanded path is quoted, not only one holding a space: a home folder may hold a space, which splits an unquoted path into two arguments (uv then answers `Failed to spawn: C:\Users\First`), or one of the characters cmd.exe treats as syntax (`&`, `^`, `(`, `)`), and one shape on every machine means a home without a space runs the same code a spaced one does. `normpath` leaves no trailing backslash, so no closing quote is escaped. In an isolated run `ConfigHomeReroot.apply()` sends a `TILDE_EXPANSION_KEYS` value through `rewrite_for_cmd()` on Windows before the write: the profile path a rewrite inserts may hold a space whether it is spelled below the home (a profile relocated to `~/My Profiles/NAME`) or absolute (a profile outside the home), so each word outside the author's quotes that holds a re-rooted path is double-quoted from the first such path to the end of the word, once however many paths it holds (`uv run ~/.claude/x.py` becomes `uv run "~/.claude/NAME/x.py"`, which the write then expands whole), and the `[re-rooted]` summary row shows the quoted value.
- **Linux/macOS/WSL:** Tildes PRESERVED as-is and nothing quoted (Claude Code resolves at runtime)

Preserved on non-Windows to avoid WSL HOME contamination (`os.path.expanduser('~')` on WSL can return Windows paths). `normalize_tilde_path()` uses `Path.home()` instead. `is_wsl()` detects WSL via `/proc/version` and warns about expanded Windows paths.

**Dependency and MCP commands keep the author's quoting:** `expand_tildes_in_command()` expands tilde paths without quoting them for its other callers, and not every dependency form reaches it. On Windows `execute_dependency()` starts a command whose first word is `winget`, `npm`, `pip` or `pipx`, or that begins with `uv tool install` (which gains `--force`), directly from `dep.split()`, with no shell and no tilde expansion: a double quote reaches the program as a literal character, a `~` stays unresolved, and a path holding a space becomes two arguments. Every other Windows command runs through `powershell -NoProfile -Command` with its tilde paths expanded; there a quoted argument stays whole, while a quoted path in command position is a string expression rather than a call and needs the call operator (`& "~/.local/bin/tool.exe" install`). Quoting every expanded path would therefore turn a working `~/.local/bin/tool.exe install` into a string, and telling command position from argument position would need a PowerShell parser; the re-rooting of dependency commands adds no quotes either. On Linux and macOS every dependency command runs through `bash -c` after the expansion, and the MCP stdio commands are split with `shlex`; both honor the author's double quotes, as PowerShell does. Unit tests: `tests/test_setup_environment_cmd_paths.py`; E2E: `tests/e2e/test_windows_command_paths.py` (Windows: installs through `main()` under the `e2e_spaced_home` fixture's home `Test User` as the base profile, an isolated profile, one relocated below the home into a folder whose name holds a space (`~/My Profiles/p1`, `~/profiles/tilde work`) and one relocated outside the home, and runs the written values through cmd.exe as Claude Code starts them, with the real uv; the same command with its quotes removed fails) and `tests/e2e/test_real_binary_api_key_helper.py` (see Real-binary modules).

### Cross-Shell Command Registration (Windows)

Global commands (e.g., `claude-python`) work across all Windows shells: shared POSIX launcher (`launch.sh` in the profile directory, `~/.claude/{command}/` unless `user-settings.env` relocates it) + wrappers for PowerShell (`start.ps1`), CMD (`start.cmd`) in the same directory, and global entry points in `~/.local/bin/` (`{command}.cmd`, `{command}.ps1`, extensionless Git Bash `{command}`, the same set per alias) whose paths follow the Launcher and wrapper paths rules above. On Linux/macOS the entry points are symlinks to `launch.sh`. Every entry point hands its arguments to `launch.sh` verbatim (`%*`, `@args`, `"$@"`, the symlink), so the argument order and the first-argument commands of `launch.sh` (see Argument order under Two-File Architecture) hold for each of them.

**Slash arguments (Windows):** Git Bash rewrites every argument that looks like a POSIX path when it starts the native `claude.exe` (`my-profile -p "/review src"` would hand Claude Code `C:/Program Files/Git/review src`), so the Windows `launch.sh` of every variant runs `WINDOWS_SLASH_ARGUMENTS_GUARD` before any `exec claude`: each user argument that starts with exactly one `/` and names no existing path (`[ -e ]` as Git Bash resolves it) is appended to `MSYS2_ARG_CONV_EXCL`, the `;`-separated prefix list Git Bash passes unchanged, after any entries the caller set. A slash command therefore reaches Claude Code byte for byte, while an existing path such as `/c/work` keeps converting and the toolbox-built `--settings`, `--mcp-config` and prompt-file arguments are untouched. The variable is exported only for a launch that has such an argument, and the session inherits it: a single entry reaches `claude.exe` in its Windows spelling (the `cygpath -m` form, `C:/Program Files/Git/<text>`), several arrive as the listed `;`-joined texts, and a Git Bash started from the session, as the Bash tool starts it, keeps converting every path that starts with none of the listed texts, such as `/tmp/...`. The quoting rules of cmd.exe and Windows PowerShell apply before `launch.sh` sees an argument (Windows PowerShell 5.1 can drop the double quotes inside an argument or split it), so the guard guarantees only that Git Bash leaves a listed argument as `launch.sh` received it. An argument starting with `//` keeps Git Bash's own escape, and one holding `;` gets no entry because Git Bash never converts it (the list cannot name it either). Adding an extra leading `/` cannot replace the list: Git Bash keeps `//cmd OWNER/NAME` whole as a UNC-style path and turns backslashes in a `//` argument into `/`. Exporting `MSYS2_ARG_CONV_EXCL='*'` or `MSYS_NO_PATHCONV=1` for the whole launch is excluded, because every session would inherit it and the Bash tool would hand unconverted `/tmp/...` paths to native programs. Unix launchers carry no guard. `tests/e2e/test_launcher_slash_arguments.py` runs `launch.sh` and every Windows entry point (`start.cmd`, `start.ps1`, and the CMD, PowerShell and Git Bash wrappers of a command and its alias) under the real Git Bash in every prompt variant, with and without an `mcp.json` so both `MCP_FLAGS` forms start claude; the stub `claude` of `tests/e2e/launcher_support.py` hands its arguments to a recorder run by the test interpreter, a native program on Windows, so Git Bash converts them exactly as it converts those of `claude.exe`. With `LAUNCHER_SESSION_BASH` naming a bash, the recorder also starts that Git Bash from its own environment and records what a native program receives for `/tmp/session-probe.py`, which proves the inherited list leaves the session's path conversion on (a blanket `MSYS2_ARG_CONV_EXCL='*'` fails it).

### Continuous Integration

`.github/workflows/test.yml` (Test & Coverage) runs on every pull request and on `workflow_dispatch`. Its `plan` job (Plan Test Matrix) chooses the operating systems of the four matrix jobs, which read them as `fromJSON(needs.plan.outputs.os)` (`test`, `test-install-scripts`, `e2e-tests`) and `fromJSON(needs.plan.outputs.package-os)` (`package-smoke`). Linux and Windows run on every pull request. macOS joins when `git diff --name-only --no-renames -z <base>...<head>` of the pull request, which also names a moved file under its old path, lists a file under `scripts/` outside `scripts/windows/` and `scripts/linux/`, a file under `tests/`, or `pyproject.toml`, `uv.lock`, `.python-version` or `.github/workflows/test.yml`. The release-please pull request runs `package-smoke` on macOS whatever it changes (the other three jobs skip on it), and a `workflow_dispatch` run puts every job on all three operating systems. A pull request that changes only documentation, another workflow, or the Windows and Linux bootstrap scripts therefore runs no macOS job. The `summary` job (Test Summary) runs after all of them on every run, writes the plan's reason and one row per job with its result and its operating systems, and fails when any job ended with a result other than `success` or `skipped`; a macOS entry the plan leaves out is no job at all, so it fails nothing. Such an entry reports no check run either, so never make a macOS check a required status check: a required check that never reports blocks the merge. The plan and summary steps take every input from `env:`, and `tests/test_ci_test_workflow.py` runs both scripts from `test.yml` under bash, the plan against a scratch git repository holding representative changes, so the path set and the summary stay under test.

**macOS runs are spent deliberately:** macOS runner minutes cost the most, so an agent NEVER dispatches `test.yml` or reruns a macOS job routinely. Run macOS only when a change needs macOS coverage its pull request's plan does not give it, such as a change outside the path set that still reaches macOS behavior: start the workflow on the branch (`gh workflow run test.yml --ref <branch>`) and name that reason in the pull request. A failed macOS job is read and fixed like any other failure, never rerun in the hope of a green result.

## Critical Implementation Details

### Configuration Loading Priority (setup_environment.py)

`load_config_from_source()` determines source: (1) URL if starts with `http://`/`https://`, (2) local file if contains path separators or starts with `.`, (3) repository config otherwise (`.yaml` added if missing). Private repos: set `GITLAB_TOKEN` or `GITHUB_TOKEN` env var with PAT; script auto-detects and applies auth headers.

### MCP Server Permissions

When `command-names` creates an isolated environment, `configure_mcp_server()` propagates `CLAUDE_CONFIG_DIR` to the subprocess for `scope: user` servers, ensuring they are written to the isolated `.claude.json`.

**Strict-mode scope warning:** the launcher enables `--strict-mcp-config --mcp-config=mcp.json` by a runtime file-existence test, so the isolated sessions read ONLY that file whenever it exists. `configure_all_mcp_servers(..., command_names=...)` collects every server whose normalized scopes are non-profile-only into `strict_hidden` during the loop and reports them AFTER the profile-config write/remove block, gated on `profile_mcp_config_path.exists()` -- the same question the launcher asks, so a failed write (or a stale config that could not be removed) cannot leave the report out of step with runtime. One `warning()` per server names the server, its scope, every command name sharing the launcher, where the registration actually ended up (`_strict_hidden_registration_note()`: `project` scope stays in the setup directory's `.mcp.json` and still loads elsewhere, while `user`/`local` scope lands in the isolated profile's own `.claude.json` and therefore loads nowhere), and the `scope: [<scope>, profile]` fix. `stats['strict_hidden_count']` carries the count into the completion summary. `normalize_scope()` forbids combining two non-profile scopes, so the named scope is always singular.

### Idempotent MCP Configuration

`claude mcp remove` deletes the stored MCP OAuth tokens and client config of http/sse servers (keyed `<name>|sha256(JSON.stringify({type,url,headers}))[:16]` in `.credentials.json`), and `claude mcp add` restores only the connection config -- so an unconditional remove/add cycle de-authenticates every authenticated remote server on every run. `configure_all_mcp_servers()` therefore plans per (server, scope) via `_plan_mcp_server_action()`: `_read_live_mcp_entries()` reads the files the CLI mutates (`.claude.json` top-level `mcpServers` for user scope, `projects[<cwd>].mcpServers` for local -- Windows path keys matched case-insensitively with forward slashes via `_find_project_entry()` -- and `<cwd>/.mcp.json` for project scope; `CLAUDE_CONFIG_DIR`/`artifact_base_dir` resolves the isolated file), `_build_expected_mcp_entry()` predicts the exact entry `claude mcp add` writes per platform (stdio: tilde expansion, Windows backslash conversion + `cmd /c` npx wrapper, `env` dict; http/sse: url + parsed `headers`), and `_mcp_entries_equal()` compares toolbox-controlled fields with absent-equals-empty normalization. `env` is a stdio-only field (`MCPServerHTTP` has none): the stdio paths send `--env` and write the `env` dict, while the http/sse paths carry url and headers only. Skip happens only on positive proof of equality at the DECLARED scope; removal (`_remove_mcp_server_from_cli_scopes()`, also used via `configure_mcp_server(remove_scopes=...)`) is always narrowed to scopes that actually hold the name; unreadable config falls back to the full three-scope remove+add; a changed http/sse server still loses tokens (key is config-derived -- inherent) with a re-authenticate warning. `stats['unchanged_count']` reports skips. Per-project `/mcp` disable state (`projects[*].disabledMcpServers`) lives outside server entries and is untouched by add/remove. Real-binary E2E (`tests/e2e/test_real_claude_binary.py`; marker and CI contract under E2E Testing) locks serialization parity and skip behavior against the actual CLI in an isolated `CLAUDE_CONFIG_DIR`.

### Automatic Auto-Update Management

`setup_environment.py` automatically blocks Claude Code's own update paths (the background updater, `claude update`, `claude install`) when a specific Claude Code version is pinned via `claude-code-version` in YAML, and removes the controls when using latest/absent version (see Unpinned removal semantics). Manages 3 in-memory dict targets via `apply_auto_update_settings()`: `global-config` gets `autoUpdates: false`; `user-settings.env` and `os-env-variables` each get every `AUTO_UPDATE_ENV_CONTROLS` entry in tuple order -- `DISABLE_AUTOUPDATER_KEY` (`DISABLE_AUTOUPDATER`, stops only the background updater) then `DISABLE_UPDATES_KEY` (`DISABLE_UPDATES`, also makes `claude update`/`claude install` print `Updates are disabled by your administrator` and exit 0). Both env keys are written because Claude Code releases before 2.1.118 recognize only `DISABLE_AUTOUPDATER`; a pin to such a release blocks only the background updater. Moving a pinned machine to another release means changing `claude-code-version` and re-running the setup, whose GCS direct download is not gated by `DISABLE_UPDATES` (an official-installer run it refuses is a failed attempt -- see DISABLE_UPDATES refusal above). WARN-but-Respect semantics (per key): if the user explicitly sets a contradicting value in their YAML configuration (e.g., `autoUpdates: true` in `global-config` while pinning a version), the user value is preserved and a warning is emitted. For the `AUTO_UPDATE_ENV_CONTROLS` keys and `CLAUDE_CODE_IDE_SKIP_AUTO_INSTALL`, `_env_control_enabled()` decides the match: a value Claude Code treats as enabled (`ENV_CONTROL_TRUTHY_VALUES` -- `1`/`true`/`yes`/`on`, trimmed, case-insensitive) matches the pin's intent silently, and any other value warns. Injection is membership-gated (`key not in dict`), so an explicit user `null` (a deletion request) also counts as a user declaration and is respected with a warning, never overwritten. The `[auto]` marker in the installation summary shows auto-injected values. Auto-update management is solely the responsibility of `setup_environment.py`; `install_claude.py` does not participate in auto-update configuration.

**Machine-wide pin gate:** The machine has ONE Claude Code binary, so its auto-update and IDE-extension controls are machine-global and shared by every installed profile. Removal is therefore gated on `machine_pinned = is_pinned or other_profile_pinned`, computed once in `main()`, after the dependent branches and before `apply_auto_update_settings()`. `_other_profile_pins(home_dir, primary_command_name, *, pending=frozenset())` reads `~/.claude/manifest.json` plus every `~/.claude/*/manifest.json` via `_read_profile_pin()`, skips the manifest whose `name` equals this run's `primary_command_name` (`None` identifies the base profile, so a profile relocated by a user-set `CLAUDE_CONFIG_DIR` is still matched as its own) and every manifest whose display name (`base` for the base profile, compared with `casefold()`) is in `pending` -- the stale source a dependent run refreshes first and the dependents that refresh covers (`SourceRefresh.covered_profiles()`), whose manifests the run's pipeline rewrites to this configuration's pin before this profile installs -- and returns a `_ProfilePinScan` carrying the sorted display names of the rest that record a non-empty `claude_code_version`, an `undetermined` flag, and the sorted distinct `pinned_versions` those profiles record. The scan FAILS CLOSED: an absent manifest is a definite "no pin", but a manifest that exists and cannot be read (`OSError`, invalid JSON, non-object JSON) or a profile directory that cannot be listed sets `undetermined`, and `_ProfilePinScan.other_profile_pinned` is true for either -- sweeping machine-global controls on a registry the run could not read in full can break a pin it never saw. When this run is unpinned and `other_profile_pinned` is true, `main()` prints the `_pinned_elsewhere_message()` info line naming those profiles, or stating that a manifest could not be read. `machine_pinned` threads into `_run_stale_controls_cleanup()`; `other_profile_pinned` threads into `apply_auto_update_settings()` / `apply_ide_extension_settings()` as a REQUIRED keyword-only argument, because the value that skips removal must never be supplied by default. The binary is held the same way: right after the scan, `main()` computes `_decide_claude_install(claude_code_version_normalized, scan, *, installed_version=...)`, which Step 1 follows; `installed_version` comes from `_installed_claude_version()` (resolves claude via `find_command()`, runs `claude --version` with a 30-second timeout, extracts the version with install_claude.py's own `(\d+\.\d+\.\d+)` regex, and returns `None` for a missing, non-executing, timed-out, failing, or version-less binary) and is probed only for an unpinned run while `other_profile_pinned` is true. A pinned run installs its own pin and an unpinned run with no pinned sibling installs or upgrades to latest; an unpinned run while `other_profile_pinned` is true hands `install_claude(version, keep_installed=True)` the installed version (`kept=True`), so `ensure_claude()` finds the requested version already installed and keeps it (its same-version npm->native migration is `exact_version_only`) while the installer's usual checks still run -- `ensure_claude()`'s corrupt-binary quarantine and `install_claude.py` `main()`'s Git Bash check on Windows -- which is also why the Windows admin gate needs no special case. A missing or non-working binary is installed at the one known pinned version (warning when the scan is also undetermined), or at latest with a warning when the pins disagree or none is known. The probe is skipped under `--skip-install` and when the run leaves the install to its source. `plan.claude_code_version`, `plan.keep_installed_claude`, `plan.claude_install_reason` (appended to the keep and install lines), and `plan.claude_install_warning` carry the decision into the installation summary (the warning shows before consent and in `--dry-run`), and the final summary reports a kept binary as `Kept at <version> (<reason>)`.

**Profile manifests:** `write_manifest()` records, beside `name`, `version`, `claude_code_version` (the normalized pin, or `null`), `config_source` (the RESOLVED source: absolute path or URL), `config_source_url`, `config_source_type` and `installed_at`: `config_identity` (`config_identity_of()`), `config_digest` (sha256 of `resolved-config.yaml`, written beside the manifest from `resolved_config_snapshot()` -- the component-selected configuration without `PROFILE_IDENTITY_CONFIG_KEYS`, taken in `main()` right after selection and before auto-injection), `command_names`, `components` (the typed `select`/`with`/`without` delta, a picker choice that changed the set in the same form, or `null`), `link` (`LinkSpec.record()`: `dirs`, `source` and per-key `origins`; `dirs` is empty for a typed or environment `none`, which a re-run remembers ahead of the configuration's `link-dirs`; `null` for the base profile and for a run that links nothing under a configuration or default value), `origins` (`command_names`: `cli`/`env`/`yaml`/`default`/`null`; `components`: `cli`/`env`/`yaml`), `yaml_values` (the configuration's own `command_names` captured before the effective names overwrite `config['command-names']`, its `link_dirs` and `link_from`, and the default component names), `machine_wide_destinations` (`destination_records()` over `machine_wide_download_records()`: `files-to-download` outside `~/.claude` with resolved source and on-disk sha256), `os_env_written` (`os_env_records()`: one `{name, sha256}` record per OS-level variable a base run set, the sha256 being `leftover_digest()` of the value as written, the machine-wide controls never among them; `[]` for an isolated profile), `settings_written` (`SETTINGS_WRITTEN_KEY`, `written_settings_records()`: one digest record per value, list element and hook group Steps 14 and 18 merged into the base `settings.json`, the status line one value, the machine-wide controls never among them; `[]` for an isolated profile; see Leftovers of earlier runs), `mcp_servers` (`mcp_server_records(servers, live_entries=)`: each server's `name`, normalized `scopes` and a `sha256` object with one digest per non-profile scope of the entry `_read_live_mcp_entries()` finds after Step 13, `null` unless that entry is `_mcp_entries_equal()` to `_build_expected_mcp_entry()`), `files_written` (`file_records()` over `planned_profile_files(..., linked_entries=...)`, with `hook_helpers=planned_hook_helpers(config)`: one `{path, sha256}` record, `hook_helper: true` added for a `hooks.helpers` module, per installer-mirroring relative path outside the run's linked entries, so a dependent never claims the files it sees through a link and a later `--switch-config` cannot remove them from the source), `dependency_entries` (`DependencyAttribution.records`: one `{command, entries}` record per Step 6 command with entries, each entry a `{path, identity}` record; see Dependency entries), `auto_update` (`auto_update_manifest_record()`: `time`, `command` and `job` while the profile keeps a scheduled update job, else `null`; see Scheduled Profile Updates) and `leftovers` (`leftovers_manifest_record()`, see Leftovers of earlier runs under Installation Confirmation; `write_manifest()` writes the empty record of a first install when none is given). A run with `download_failures` records a file or destination digest only when it equals the one the previous manifest recorded for that path (`_trusted_digest()`), else `null`, because a failed download may leave bytes the run did not write. `main()` builds the other records once as `manifest_records` after Step 16, and each Step 20 branch adds `written_profile_records()` (the files and destinations, computed after the last content download of the run) and the `leftovers` record; `tests/e2e/expected/common.py` pins the field set and `validate_manifest()` checks identity, digest and record shapes. Every toolbox-managed profile gets a manifest: the isolated branch writes `~/.claude/{cmd}/manifest.json` (`name` = primary command name) and the non-isolated branch writes `~/.claude/manifest.json` (`name` null, `command_names` empty) at the same Step 20 position.

**Write-remove symmetry:** Auto-update controls are written to the running profile's own files via scope-based routing, and removal sweeps the same two files. `_run_stale_controls_cleanup(machine_pinned, user_declared_keys, profile_dir)` runs as a post-write pass in `main()` (Step 16), passing `machine_pinned`, the running profile's directory (`None` for the base profile), and the user-declared control keys -- collected by `_collect_user_declared_control_keys(user_settings, global_config=...)` BEFORE injection: every `MACHINE_WIDE_ENV_CONTROLS` key `user-settings.env` sets to a non-null value (a null is a deletion request and never shields a stale copy) plus each `MACHINE_WIDE_JSON_CONTROLS` key (`autoUpdates`, `autoInstallIdeExtension`) that `global-config` sets to `false` -- to both `cleanup_stale_auto_update_controls()` and `cleanup_stale_ide_extension_controls()`. Both return immediately when `machine_pinned` is true, so nothing is swept and a pinned profile's controls are never stripped by any run. Otherwise they sweep ONLY the pair `_profile_control_files(home_dir, profile_dir)` returns -- `~/.claude/settings.json` and `~/.claude.json` for a base run, `settings.json` and `.claude.json` inside the profile directory for an isolated run -- except that the `settings.json` sweep is skipped for an environment control key the current YAML sets to a non-null value in `user-settings.env`, and the `.claude.json` sweep for `autoUpdates`/`autoInstallIdeExtension` when the YAML sets it to `false` in `global-config` (the removal counterpart of WARN-but-Respect; without this gate Step 16 would delete a declared `autoUpdates: false` that Step 15 just wrote). Other profiles' files are never edited: `find_stale_controls_in_other_profiles(home_dir, profile_dir=..., machine_pinned=..., user_declared_keys=...)` scans the base pair and every `~/.claude/*/` pair except the running profile's under the same two gates and returns `StaleControlCopy(profile, file, keys)` entries (`'base'` or the directory name; env keys present in a `settings.json`, keys holding `false` in a `.claude.json`); `main()` lists them in the pre-consent summary (`Stale update controls in other profiles (not edited by this run):`, each row from `_stale_control_copy_line()`, which ends with the `--profile <name>` command that removes the copy, plus `STALE_CONTROLS_RERUN_NOTE`), Step 16 prints them again as warnings, and the final summary repeats them with the note to re-run each listed profile with `--profile`. `cleanup_stale_auto_update_controls()` and `cleanup_stale_ide_extension_controls()` take the keyword-only `user_declared_keys: frozenset[str]` and `profile_dir: Path | None`; the former decides each `AUTO_UPDATE_ENV_CONTROLS` key independently (declaring `DISABLE_AUTOUPDATER` still sweeps a stale `DISABLE_UPDATES`, and the reverse); `_cleanup_settings_json_env_controls(path, keys)` deletes every present undeclared key in one null-as-delete `_write_merged_json()` write and drops an emptied `env` object; `cleanup_stale_ide_extension_controls()` sweeps its `settings.json` through the same helper with `(IDE_SKIP_AUTO_INSTALL_KEY,)`. Every cleanup helper skips a file whose JSON is not an object. Removal of `autoUpdates` from a `.claude.json` is value-conditional: only `false` is removed, `true` (user preference) is preserved, and a `global-config` declaration of `false` keeps it.

**Unpinned removal semantics:** On an unpinned run nothing is auto-injected, so `_remove_auto_update_controls()` and its counterpart `_remove_ide_extension_controls()` preserve every user-declared control in the three in-memory dicts (the removal counterpart of WARN-but-Respect). Their only mutation schedules an OS-level deletion entry per managed variable (`os_env_variables[KEY] = None` for each `AUTO_UPDATE_ENV_CONTROLS` key, respectively `CLAUDE_CODE_IDE_SKIP_AUTO_INSTALL`, gated on `KEY not in os_env_variables` so it is skipped only when the user declares that variable in `os-env-variables` specifically) because OS-level variables have no filesystem sweep; the deletions reach the OS writer from a base run and from an isolated run alike, because the three keys are `MACHINE_WIDE_ENV_CONTROLS` and never routed to a profile loader. Stale on-disk artifacts in the running profile are removed by the Step 16 sweep instead. Both removers are skipped entirely when another installed profile pins a version, so no OS-level deletion is scheduled while the machine-global variables are still needed. Removal does not track who set a value: when nothing on the machine pins a version, a run removes every `DISABLE_AUTOUPDATER` and `DISABLE_UPDATES` its YAML does not declare from the OS environment and from its own `settings.json`, including values set by hand outside the toolbox; a declaration in `os-env-variables` keeps the OS-level variable, and one in `user-settings.env` with a non-null value keeps it in the running profile's `settings.json` (a null there is a deletion request, so the sweep removes it there). Provenance gating is deliberately absent, because an interrupted pinned run or a deleted pinned profile would otherwise leave an orphaned `DISABLE_UPDATES` silently blocking every update; a copy left in another profile is reported, and that profile's own re-run removes it.

### Scheduled Profile Updates (`auto-update`)

The top-level `auto-update` key (`AUTO_UPDATE_SCHEDULE_KEY`; a `KNOWN_CONFIG_KEYS` member, not mergeable; `{time: "HH:MM", command: optional}`, validated by `validate_auto_update()` and parsed into an `AutoUpdateSpec(hour, minute, command)` by `parse_auto_update()`) gives each profile installed from the configuration ONE daily job in the OS scheduler, named `scheduled_update_job_name(profile)` = `cc-toolbox-update-<profile>` (`cc-toolbox-update-base` for the base profile). The job runs `scheduled_update_command()`: `[<absolute uvx>, 'cc-toolbox@latest', 'setup', '--profile', NAME, '--yes', '--no-admin', '--scheduled-run']` (`uv tool run cc-toolbox@latest ...` when only `uv` resolves; `SchedulerError` when neither does, reported as a plan problem), so every scheduled run installs the latest toolbox release. `AUTO_UPDATE_KEY` is the unrelated `global-config` key `autoUpdates` of the pin controls above; the two names MUST stay distinct, because a module-level redefinition shadows the first at import time.

**Planning (`_run_setup()`, before the elevation gate and the summary):** `validate_auto_update()` exits 1 on errors; `default_scheduler_platform()` builds the frozen `SchedulerPlatform(name, home, state, runner, environ, which)` whose `runner` is `_run_scheduler_command()`, the ONE function that runs `schtasks`, `launchctl`, `systemctl`, `crontab` and `id` (every test replaces it: see Testing below); `plan_scheduled_update(platform_, profile_name=, spec=, linked_from=, manifest=, scheduled_run=)` returns a `ScheduledUpdatePlan(action, name, spec, command, reason, problems, state_dir)` with `action` in `register` (no job registered), `update` (the registration differs from `jobs/<name>.json` in time, command or OS command; `_registration_difference()` is the reason), `unchanged` (registered as recorded), `remove` (the manifest's `auto_update.job` or a job record exists while the configuration drops the key or the profile links content, `linked_from`), `deferred` (a scheduled run never changes or removes its own job -- a launchd `bootout` would kill the running job -- so a changed registration AND a removal the configuration now asks for are both left to the next manual run; for the removal case the plan carries the spec `_spec_from_record()` rebuilds from the manifest's `auto_update` or the job record, so Step 20 keeps recording the job and the next manual run plans `remove`) or `none`; a content-linked profile never gets a job, because its source's Step 24 refreshes it. `changes_registration` (register/update/remove) adds `SCHEDULED_UPDATE_ELEVATION_REASON` through `admin_elevation_reasons(config, args, scheduled_update=plan)` (without a plan, any configuration declaring the key counts), and `collect_machine_wide_writes(..., scheduled_update=plan)` adds the `OS scheduler:` row; `refresh_all_elevation_reasons()` plans each profile's job itself from its `resolved-config.yaml`, its manifest (`content_link_source()`) and the job record -- no fetch, so a time the source changed since the last run is seen by the child, not the parent -- and lists the reason only for a plan that changes a registration, so an unchanged job never prompts a `--profile all` run for UAC; `keeps_job` (register/update/unchanged/deferred) records `auto_update_manifest_record(plan.spec, name)` -- `{time, command, job}` -- in the manifest (`None` otherwise) and triggers `unattended_credential_warnings()`. `display_installation_summary()` renders `Scheduled update (auto-update):` from `scheduled_update_summary_lines()` (`Job NAME: action (reason); runs every day at HH:MM local time`, `Runs:` the OS command line, `Command:`, the Windows rights line, `State: <dir> (jobs, logs of the last 30 runs, the lock)`, `last_scheduled_run_line()`, and `[!]` problems and warnings), identically under `--dry-run`; `InstallationPlan` carries `scheduled_update`, `scheduled_update_warnings` and `last_scheduled_run`.

**Step 25 (`run_scheduled_update_step(platform_, plan, warnings_=, now=, manifest_path=, previous_record=)`, both branches, after Step 24):** `apply_scheduled_update(platform_, plan, now=)` returns the failure text or `None`: nothing for `none`/`unchanged`/`deferred`; `_scheduler_registration_needs_elevation(platform_)` (`platform_.name == 'win32'` and not `is_admin()`; the platform's name, not the host's, so the shaped fakes exercise the real check on every CI OS -- tests patch `is_admin`, never the check) makes register/update/remove fail with the elevated-run remedy, because the task runs with `RunLevel HighestAvailable`; otherwise `plan_job_registration()` renders the backend and `apply_job_registration()` creates its directories, writes its files and runs its commands (`JobRegistration(target, document, files, directories, best_effort, commands)`; `directories` holds `<state>/logs` for launchd and cron, whose registrations redirect the job's output there and which a shell refuses to redirect into before it exists), `write_job_record()` stores `plan.record()`, and `remove` runs `remove_job_registration()` plus `remove_job_record()`. `remove_job_registration()` asks `query_job_registration()` first (an absent job is not removed again, only its leftover files are deleted) and runs every removal command through `_run_checked_scheduler_command()`, so a refused `schtasks /Delete`, `launchctl bootout`, `systemctl --user disable` or `crontab` install is a `SchedulerError`: the step reports `could not be removed`, the job record stays, and `_record_manifest_auto_update()` writes the job (`_spec_from_record()` of the job record or `previous_record`) back into the manifest Step 20 wrote without it, so the next run plans `remove` again. The switch guard only names the job; the removal itself is Step 25's, with its elevation check and its failure reporting. Backends: Windows `windows_update_task_xml()` (UTF-16 XML staged in `state/jobs/<name>.xml`, `schtasks /Create /TN <name> /XML <file> /F`; `CalendarTrigger ScheduleByDay DaysInterval 1` starting at today's slot while it lies ahead, `LogonType InteractiveToken`, `RunLevel HighestAvailable`, `MultipleInstancesPolicy IgnoreNew`, `StartWhenAvailable`, `RunOnlyIfNetworkAvailable`, `ExecutionTimeLimit PT4H`); macOS `launchd_update_plist()` (`~/Library/LaunchAgents/<name>.plist` with `StartCalendarInterval`, the registering PATH in `EnvironmentVariables` and `state/logs/<name>.scheduler.log` as its output; `launchctl bootout gui/<uid>/<name>` best effort, then `launchctl bootstrap gui/<uid> <plist>`); Linux `systemd_update_units()` (oneshot service plus `Persistent=true` timer under `$XDG_CONFIG_HOME/systemd/user`, `daemon-reload` then `enable --now <name>.timer`) when `systemctl --user show-environment` succeeds, else `cron_update_line()` (a `# <name>`-tagged line replacing any earlier one in the user's crontab, installed with `crontab <staged file>`; `scheduler_problems()` reports a machine with neither). `query_job_registration()`/`remove_job_registration()` follow the same split. The failure lands in `scheduled_update_failure`, the error block prints `The scheduled update job (auto-update) was not applied:` and the run exits 1; the completion summary prints `scheduled_update_completion_line()` and the last-run line. `dropped_scheduled_job()` has the switch guard list `scheduled update job: <name> (removed in Step 25)` apart from the leftovers when the manifest records a job the new configuration does not declare; the plan for that run is `remove`, so Step 25 removes it.

**The scheduled run (`--scheduled-run`, `SCHEDULED_RUN_FLAG`; hidden like `--child-run`, so no wrapper or env twin):** `main()` handles it right after `resolve_args()`: it needs `--profile NAME` (not `all`), reads the manifest's `auto_update.command` through `scheduled_custom_command()`, and exits with `run_scheduled_update(args, run_setup=_scheduled_setup, custom_command=)`, where the nested `_scheduled_setup()` calls `switch_off_scheduled_removal(args)` (a `--remove-leftovers` or `CLAUDE_CODE_TOOLBOX_REMOVE_LEFTOVERS=1` is set to `False` with the warning `Leftovers are only listed in a scheduled run; remove them with --profile NAME --remove-leftovers.`, inside the log because the output is redirected by then) and then `_run_setup(args, ...)`; a custom command runs as written in the job's environment, so a setup it starts honors the variable like a manual run. That function takes the machine-wide lock `state/update.lock` through `acquire_update_lock()` (`SCHEDULED_UPDATE_LOCK_WAIT_SECONDS` 1800, polled every `SCHEDULED_UPDATE_LOCK_POLL_SECONDS` 15; a lock older than `SCHEDULED_UPDATE_LOCK_STALE_SECONDS`, six hours, is taken over, and the function returns `(taken, note)` so the takeover is written into the log), writes `state/logs/<name>-YYYYmmdd-HHMMSS.log`, cuts the run off its terminal with `_detach_from_terminal()` -- `_redirect_output_to()` points file descriptors 1 and 2 at the log (so child processes log too) and rebuilds `sys.stdout`/`sys.stderr` as `io.TextIOWrapper(io.FileIO(fd, closefd=False))` on them, because the console streams a Task Scheduler process starts with write through the console handle and the first `print()` after the `dup2` would fail with `The handle is invalid`; `_detach_stdin()` points descriptor 0 at the null device and makes `sys.stdin` an exhausted in-memory stream (the null device is a character device on Windows, which `isatty()` reports as a terminal), so `prompt_for_credentials()` takes its non-interactive branch and an expired token fails the run fast instead of waiting for a keypress under the lock -- and runs the setup in-process, or runs the custom command through the shell with the log as its output (`_run_custom_update_command()`, `_NON_INTERACTIVE_ENVIRONMENT`); ### Sudo Handling (Three-Tier Fallback)

`install_claude.py`'s `install_claude_npm()`/`remove_npm_claude()` AND `setup_environment.py`'s global-npm dependency retries and Node.js installers delegate to the shared `_run_with_sudo_fallback()` helper (intentionally identical copies in both scripts -- see Standalone Script Policy) for elevated permissions:

1. **Tier 1 -- Interactive:** `sys.stdin.isatty()` → sudo directly (user enters password via stdin)
2. **Tier 2 -- Cached credentials:** `sudo -n true` probe → sudo without prompting if cached
3. **Tier 3 -- `/dev/tty` fallback:** `_dev_tty_sudo_available()` → sudo with stdin from `/dev/tty` (enables password entry in piped mode like `curl | bash`; default `tty_timeout=60`)

If all tiers exhausted, returns `None` (caller provides guidance). Catches `FileNotFoundError`/`TimeoutExpired` at each tier. `remove_npm_claude()` captures npm output to suppress noisy stack traces.

**Dependency escalation (setup_environment.py):** In `install_dependencies()`'s non-Windows branch, a failed dependency is retried via `_run_with_sudo_fallback(shlex.split(expanded_dep), capture_output=False, timeout=600)` ONLY when ALL of: `_is_global_npm_install(dep)` (the `'npm install -g' in dep` predicate, also reused by `admin_elevation_reasons()`, which feeds the Windows elevation banner and its dry-run report), the expanded command contains no shell control characters (`_contains_shell_control_chars()`: `;`, `&`, `|`, `<`, `>`, `$`, backquote, newline -- user-authored compound shell strings are never run as root), and `needs_sudo_for_npm()` reports the npm global prefix is not user-writable. An informational "sudo may be requested" note prints before the first attempt; when the fallback returns `None` or fails, actionable guidance prints (manual sudo command, `npm config set prefix ~/.npm-global` + PATH export, node version manager). The macOS pkg installer (`_install_nodejs_direct()` Darwin branch) and the Debian/Ubuntu apt/NodeSource path (`_install_nodejs_apt()`) route their sudo invocations through the same helper (600-second timeouts) and fail cleanly with guidance in piped non-interactive runs instead of hanging.

**Dependency failure surfacing:** `install_dependencies()` returns `list[str]` of failed dependency commands (empty list = success; continue-on-failure preserved); its keyword-only `observer` watches the content directories around each command (see Dependency entries). `main()` lists failures in a dedicated "The following dependencies failed to install:" section of the "Setup Completed with Errors" block and exits 1, parallel to `download_failures`.

### Download Retry Configuration

Retry logic for GitHub API rate limiting: 10 attempts with linear additive backoff (1s, 3s, 5s, 7s, ..., capped at 60s) plus random 0-25% jitter. Concurrent downloads use 0.5s stagger delay between threads. `RateLimitCoordinator` shares rate-limit state across threads. `Retry-After` and `x-ratelimit-reset` headers used as minimum floor.

`AuthHeaderCache` provides thread-safe per-origin auth header caching (modeled after `RateLimitCoordinator`). `get_origin()` normalizes URL variants (GitHub web/raw/API, GitLab web/API) to a single cache key. A single instance is created in `main()` and shared across both the validation phase (`FileValidator`) and all download functions, so auth discovered during validation is reused during downloads. The first request per origin probes unauthenticated; on auth resolution, subsequent requests for the same origin skip the probe. `resolve_and_cache()` uses double-checked locking for thread safety. `_fetch_url_core()` (behind both `fetch_url_with_auth` and `fetch_url_bytes_with_auth`) implements auth resolution priority: explicit `auth_headers` param > `auth_cache` hit > unauthenticated probe with cache population. GitHub API transport headers (`Accept: application/vnd.github.raw+json`, `X-GitHub-Api-Version`) are managed independently from cached auth headers via `github_api_headers` dict and the `_fetch()` helper in `_fetch_url_core()`, applied to every request `_do_fetch()` sends when `'api.github.com' in url`.

**Certificate verification and the unverified fallback:** `main()` first calls `use_os_trust_store()`, which runs `truststore.inject_into_ssl()`: `ssl.SSLContext` becomes truststore's class, so urlopen()'s default context and every `ssl.create_default_context()` verify against the macOS keychain, the Windows certificate store, or OpenSSL's default locations on Linux; without the package (a plain-Python run with only PyYAML) the interpreter's CA bundle verifies. urlopen() keeps the TLS context of its first call for the process, which is why the call precedes every request. Every HTTPS request the setup sends with a certificate fallback goes through `CertificateFallbackOpener.open()`: it verifies first, and a failure whose `URLError.reason` is an `ssl.SSLCertVerificationError` (`_is_certificate_failure()`: the exception type decides, never its text, which the OS trust store words in the system language; an `HTTPError` and every other failure are raised unchanged) prints `CERTIFICATE_FALLBACK_WARNING` (`SSL certificate verification failed, trying with unverified context`, unless `warn_on_fallback=False`) and sends that request and every later request of the same opener over `_unverified_ssl_context()`. That context is built from `_STDLIB_SSL_CONTEXT`, the ssl module's own class read at import, because on macOS a `CERT_NONE` context of truststore still rejects some chains, and its `verify_mode` is set through `_STDLIB_VERIFY_MODE`, the descriptor of the C base class, because the ssl module's own setter looks its class up in the module again and recurses once truststore's class is there. `_fetch_url_core()` creates one opener per fetch, so the unauthenticated probe, the authenticated retry after 401/403/404 and every rate-limit retry of `fetch_with_retry()` share the outcome of the first request, and the HTTP status handling (escalation, the cache, the error messages) is identical over a verified and an unverified connection. The other callers: `FileValidator._check_with_head()` and `_check_with_range()` (one opener per check with `warn_on_fallback=False`: the download of the file warns), `_fetch_node_release_json()` (with its timeout), `_download_nodejs_installer()` (streams into the temporary file and raises `urllib.error.ContentTooShortError` when fewer bytes than `Content-Length` arrive) and the Windows bootstrap download of `install_claude()`. The one request without the fallback is the `api.github.com` probe of `_github_repo_is_public()` (see GitHub 404 disambiguation): it calls `urlopen()` with the default context, so it verifies against the OS trust store the injection set up, and a certificate failure returns `None` like a network error. `install_claude.py` keeps its own copies of the fallback (Standalone Script Policy), and because Step 1 runs it as a process of its own, it verifies with the interpreter's default certificates (`ssl.create_default_context()`: the Windows certificate store, never the macOS keychain), without truststore. Unit tests: `tests/test_setup_environment_certificate_fallback.py`, whose `TestRealCertificateFailures` trusts a test authority through `SSL_CERT_FILE` and serves `tls_support` certificates from `GitLabLikeServer` without `use_os_trust_store()`, so OpenSSL verifies, the verifier on Linux and in a run without truststore: a self-signed certificate, one from an untrusted authority, an expired one, one not yet valid, one issued for another host and one sent without its intermediate certificate each fall back with the warning (the OpenSSL verify code names the cause), while one from the trusted authority, directly or through an intermediate it sends, verifies. A missing intermediate depends on the verifier: OpenSSL never downloads it, while the Windows certificate chain engine and the macOS Security framework (which fetches missing certificates under the SSL policy by default, a setting truststore leaves alone) download it from the caIssuers URL in the Authority Information Access extension of the server certificate, as a browser does. `TestMissingIntermediateWithIssuerAddress` serves, through `tls_support.server_naming_its_issuer()`, a certificate whose caIssuers URL names an `IssuerCertificateServer` holding the intermediate: OpenSSL falls back with the warning and requests nothing on every platform. The Windows download is the E2E `TestWindowsChainEngineDownloadsTheIntermediate`, gated like the real trust-store test because the chain engine keeps the downloaded intermediate and its address in the user's certificate caches (see Real trust store under E2E Testing); no test exercises the macOS download. E2E: `tests/e2e/test_certificate_verification.py`, with `tests/e2e/tls_support.py` (certificates built with the `cryptography` dev dependency, optionally naming a caIssuers URL; `GitLabLikeServer`, a TLS server on 127.0.0.1 that answers GitLab REST API file requests of a private project with 404 without the token, as GitLab does, and handshakes in each connection's own thread; and `IssuerCertificateServer`, a plain HTTP server on 127.0.0.1 publishing an authority's certificate at a path with a random part), drives `main()` against a self-signed server with `GITLAB_TOKEN` set and `run_main(validation_result=None)`, so the real validation runs too; the `real_trust_store` tests (see E2E Testing) prove that the OS trust store verifies and that the Windows chain engine completes a chain whose intermediate the server leaves out.

**Lazy-auth invariant (validation + download parity):** Both `FileValidator.validate_remote_url` and `_fetch_url_core._do_fetch` MUST honor the "try unauthenticated first; escalate to authentication only on HTTP 401, 403, or 404" contract, over a verified and an unverified connection alike. Non-auth failures (TLS failures other than the certificate verification, DNS, 5xx, timeout, 416 Range Not Satisfiable) MUST NOT trigger auth prompts. Successful unauthenticated probes cache a `None` sentinel in `AuthHeaderCache` for downstream consumers. When `auth_cache` is available, route escalation through `AuthHeaderCache.resolve_and_cache(url)` (double-checked locking) to serialize prompts across parallel validation threads. Helper functions `_check_with_head` and `_check_with_range` return `tuple[bool, int | None]` where the second element is the HTTP status code (or `None` for non-HTTP failures) used to gate the escalation decision.

**Authentication SRP:** `get_auth_headers(url, auth_param)` is a thin orchestrator that delegates to `resolve_credentials(url, auth_param)` (non-interactive: the CLI param, then the env vars, then the host CLI's stored login) and then escalates to `prompt_for_credentials(url, tokens_checked=[...])` (interactive, guarded by `sys.stdin.isatty()`); `get_auth_headers()` records the host of every URL it resolved headers for in `_AUTHENTICATED_HOSTS`, which `unattended_credential_warning()` reads. The stored-login step is `cli_stored_token(repo_type, host)`: `_credential_host()` maps the GitHub family to `github.com` and a GitLab URL to its host, `_cli_token_command()` is `gh auth token --hostname HOST` for GitHub and `glab auth status --hostname HOST --show-token` for GitLab, and `_query_cli_token()` runs it once per `(repo_type, host)` (cached in `_CLI_TOKEN_CACHE`; `tests/conftest.py`'s autouse `_reset_credential_lookups` clears the cache and the host set) with stdin closed, `_NON_INTERACTIVE_ENVIRONMENT` and a 30-second timeout, taking the last stdout line from `gh` and the value of the token line from `glab` (an all-asterisk value is a masked token and is skipped); the token is used for the headers and never printed, logged or stored. The split enables non-interactive callers to opt into credential resolution without risking user prompts. The interactive prompt uses the wording `Authentication required for {url}` (both the `warning(...)` on interactive terminals and the `info(...)` fallback on non-interactive terminals emit this URL-qualified message), names the CLI command it checked, and lists `gh auth login --hostname HOST` (`glab auth login`) among the ways to authenticate.

**Repository type classification (`detect_repo_type`):** Uses hostname-based matching via `urllib.parse.urlparse`. GitHub Pages URLs (hostname ending in `.github.io`) are explicitly classified as `None` (not `'github'`) because GitHub Pages sites are static HTTP hosts with no repository auth model. `github.com`, `raw.githubusercontent.com`, and `api.github.com` are classified as `'github'`. GitLab classification uses both hostname substring (`'gitlab' in host`) and the API path marker (`/api/v4/projects/`).

**GitHub 404 disambiguation (UX polish):** When a GitHub URL returns HTTP 404 during validation, before escalating to an auth prompt, the validator probes `GET https://api.github.com/repos/{owner}/{repo}` unauthenticated. If the repo endpoint returns 200, the original 404 is classified as a **genuine missing file** (typo) and the auth prompt is skipped (returns failure directly). If the repo endpoint returns 404 (private-hidden or nonexistent -- GitHub does not distinguish), the validator conservatively escalates to the auth prompt. Rate-limiting or network errors from the repo probe also trigger conservative escalation, and so does a certificate failure: the probe verifies against the OS trust store and has no unverified fallback (see Certificate verification above; `TestGitHubRepositoryProbe` in `tests/test_setup_environment_certificate_fallback.py` asserts one verified request, `None` and no fallback warning). The `/contents/{path}` endpoint intentionally cannot distinguish private-hidden from missing, which is why `/repos/{owner}/{repo}` is used instead.

### Hooks Configuration Structure

Hooks support five types matching the official Claude Code hooks specification:

| Type       | Required Fields  | Description                                                             |
|------------|------------------|-------------------------------------------------------------------------|
| `command`  | `command`        | Runs a `hooks.files` script, or with `args` a program on PATH (default) |
| `http`     | `url`            | Sends an HTTP POST request                                              |
| `prompt`   | `prompt`         | Single-turn LLM evaluation (no tool access)                             |
| `agent`    | `prompt`         | Spawns a subagent with tool access for evaluation                       |
| `mcp_tool` | `server`, `tool` | Calls a tool on an already-configured MCP server                        |

Common fields available on all types: `if`, `status-message`, `once`, `timeout` (must be positive; non-positive values fail model validation and are warn-skipped at runtime).

Only `command` hooks reference files from `hooks.files`, and an exec-form command hook may name a program on PATH instead (see Consistency validation). Other types are pure pass-through. `_apply_common_hook_fields()` applies shared fields to all types. Event names are checked against `HOOK_EVENT_NAMES` (31 names Claude Code 2.1.238 recognizes; byte-identical frozensets in `setup_environment.py` and `environment_config.py`, parity enforced by `tests/scripts/models/test_hook_event_names_parity.py`): an unknown name warns but still installs, so configs written for newer Claude Code releases keep working. `_build_hooks_json()` also warns about (and ignores) YAML keys a hook type does not support; the `HookEvent` model rejects them outright (`extra='forbid'`).

**`hooks.helpers`** carries shared modules the hook scripts import. `download_hook_files()` installs `files` and `helpers` as one set into the SAME directory (`artifact_base_dir/hooks` in isolated mode, `~/.claude/hooks` in base mode), so a script reaches its helpers through `Path(__file__).parent` in either mode; a `files-to-download` dest reaches the scripts only when it names the base config home, which `ConfigHomeReroot` re-roots beside them in an isolated run (see Re-rooting), while a dest outside the config home stays where it is written. The set installs through a staging directory, `hooks_dir / f'{HOOK_STAGING_PREFIX}{os.urandom(8).hex()}'` (`'.staging-'`; inside the hooks directory, so a move never crosses a filesystem) created by `Path.mkdir()` at the default mode, so it inherits the hooks directory's access control list on Windows and the umask mode on POSIX and a moved file keeps the permissions of a file written in place (`tempfile.mkdtemp()` would give it the owner-only protected DACL Python applies to a 0o700 directory, which a non-elevated session cannot read after an elevated run); it receives both lists from `_download_resource_set(..., installed_dir=hooks_dir)`: the download loop `process_resources()` also runs, returning the failed file names in list order (`process_resources()` returns `not failed`). `handle_resource(..., installed=...)` compares against the installed file, so an unchanged file prints `Unchanged: name`, is not staged and keeps its mtime, and `_write_file_atomic(..., mode_of=...)` gives a staged remote download the installed file's POSIX permission bits. Only when no download failed does `_promote_staged_hook_files(staging_dir, hooks_dir, ordered_names)` move the staged files with `os.replace()`, every helper first and then the scripts, each list in its order, so a hook a running session starts never runs a new script beside an old or missing helper; it returns the first name whose move raised `OSError` (on Windows, a file a running hook holds open), after an error naming the file and how many files had moved, and retries nothing. A failed download prints `Hook files failed to download: <names>; the installed hook files were left unchanged` and moves nothing; either failure makes `download_hook_files()` return False, so the Step 17 callers append `'hook files'` to `download_failures` (errors block, exit 1, Step 19 skipped), and a `finally` block removes the staging directory on every outcome. Success prints `N hook files moved into place`; a run that stages nothing prints `Hook files unchanged; nothing moved into place`. Unit tests: `tests/test_setup_environment_hook_staging.py`; E2E: `tests/e2e/test_hook_install_staging.py`. Helpers are never registered as a command: the consistency validation refuses a `command` naming a helper in either form, and `_build_hooks_json()`'s `listed_basenames` reads `hooks.files` only, so no helper name reaches the generated JSON or `statusLine`. `_merge_hooks()` deduplicates `helpers` through `_merge_string_list()` alongside `files`. Helpers are NOT a component identity (`_component_section_identities` and `apply_component_selection` read `hooks.files` and `hooks.events[].id` only), so no selector can claim one and deselection never deletes one. `FILE_REFERENCE_KEYS` carries `hooks.helpers` alongside `hooks.files`; path resolution and remote validation treat the two lists identically, except that helpers contribute no selector mapping. `InstallationPlan.hooks_helpers` feeds `total_resources` and the summary's `Hook helpers` row.

**Consistency validation:** the model's `validate_hooks_files_consistency` (skipped under `inherit`) and its runtime twin of the same name in `setup_environment.py` (running on the resolved config at the `main()` choke point) enforce the same rules: every `hooks.files` entry is referenced by a command hook or `status-line`; a command hook's whitespace-stripped `command` equal to a `hooks.files` basename (exact match) is that script in both forms, one naming a `hooks.helpers` basename is the misplaced-declaration error in both forms, and any other `command` is a program on PATH or an absolute path, accepted ONLY in exec form (`args` set, `args: []` included) -- a shell-form one is refused with `_hook_unlisted_command_message()`, whose text keeps the prefix `hooks.events command "<cmd>" not found in hooks.files` and names `args` (a path-form reference such as `hooks/a.py` with `args` is therefore a program at that relative path, not the listed script); the runtime twin's `declared_files` keyword, which only the post-selection recheck passes (see Resolution under Component Selection), turns a `command` naming a script the selection dropped into the plain `hooks.events command "<cmd>" not found in hooks.files. **Mock target alignment:** When refactoring call sites (e.g., `find_command()` → `shutil.which()`), ALL test `@patch` targets MUST be updated. When `shutil.which` replaces `find_command`, also mock `Path.exists()` for common-path checks.

**Platform detection mocks:** Mock ALL detection methods (`sys.platform`, `platform.system()`, `os.name`) in the code path. Mocking only one passes on that platform's CI but fails on others. Prefer ONE method per function (`sys.platform` recommended).

### Agent Development Pitfalls

Recurring patterns that cause CI failures. Every item below has caused at least one real CI failure. Read this section before modifying `setup_environment.py` or its tests.

**Cross-platform test verification:** Local `uv run pytest` skips tests targeting other platforms (`@pytest.mark.skipif`). Developing on Windows means Unix-only tests are SKIPPED locally but WILL RUN in CI on Linux/macOS (and vice versa); macOS runs for every pull request that touches `scripts/` outside the Windows and Linux bootstrap scripts, `tests/` or packaging (see Continuous Integration). A 100% local pass rate does NOT guarantee CI success. Before committing, review skipped tests to verify they would pass on their target platform. NEVER report a clean test run as definitive when platform-skipped tests exist.

**Tests must match implementation:** Every test assertion MUST correspond to actually implemented behavior. Do NOT write tests that assert behavior which has not been coded yet. If a test is for a new feature, implement the feature BEFORE or SIMULTANEOUSLY with the test. Tests that pass only because they are platform-skipped on the development machine will fail in CI on the target platform. This is the single most common cause of CI failures in this project.

**Parallel mock side effects:** Tests calling functions that use `execute_parallel()` (which uses `ThreadPoolExecutor`) MUST NOT use `mock.side_effect = [list]` with distinct values per item. The list is consumed in thread-scheduling order, not submission order. This causes non-deterministic failures depending on OS thread scheduling. Use either:

- `@patch.dict(os.environ, {'CLAUDE_CODE_TOOLBOX_SEQUENTIAL_MODE': '1'})` to force sequential execution in tests that verify logic (not parallelism)
- Function-based `side_effect` that maps inputs to deterministic outputs for tests that must run in parallel

**Shell escape sequence levels:** Modifying shell template strings (especially ANSI escape sequences like `\\\\033`) requires tracking three escaping layers: Python source string, generated shell script file, and final shell execution. A change that appears correct in Python source may produce wrong output in the generated `.sh` file. After modifying escape sequences, always verify the generated file content matches expectations.

**Multi-phase implementation counting:** When implementing multi-phase changes that introduce intermediate test failures, ALL failures MUST be explicitly counted including BOTH unit tests AND E2E tests. Agents have historically undercounted by omitting E2E failures. Each phase validation MUST confirm the exact failure count matches expectations before proceeding.
